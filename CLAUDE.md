# Правила работы над SAGE-Engine

Файл для Claude Code. Здесь ПОРЯДОК РАБОТЫ, а не описание движка: движок
описан в README.md, и он же — источник правды по архитектуре.

## Порядок внесения изменений (обязателен, без исключений)

Так работаем ВСЕГДА, даже если правка кажется мелкой.

1. **Точка возврата — до начала работы.** Текущее состояние `main`
   закрепляется веткой-резервом:
   `git branch -f claude/backup-main-<ГГГГММДД>-<sha> main && git push origin <она>`
   Веткой, а не тегом: пуш тегов в этом окружении отдаёт 403 (прокси
   пропускает только ветки). Резерв не удаляется — по нему `main`
   возвращается к последнему заведомо рабочему состоянию одной командой.
2. **Работа — в отдельной ветке** от свежего `origin/main`:
   `git fetch origin main && git checkout -B claude/<о-чём-правка> origin/main`.
   Прямо в `main` не коммитим.
3. **Проверка — до слияния.** Полный прогон (см. ниже) обязан быть зелёным
   НА ВЕТКЕ. Не «соберётся — увидим»: в `main` не должно попадать ничего
   непроверенного.
4. **Слияние в main — отдельным шагом и только после проверки.** Сливаем
   `--no-ff`, чтобы в истории осталась граница работы и её можно было
   откатить целиком одним `git revert -m 1`.
5. **Ветка не удаляется** сразу после слияния: пока правка не пожила,
   она — второй путь назад.

Откат, если что-то пошло не так: `git revert -m 1 <коммит слияния>` (мягко,
история сохраняется) или `git reset --hard <резервная ветка>` + пуш с
`--force-with-lease` (жёстко, только по прямой просьбе).

## Что прогнать перед слиянием

```
cmake --build build -j"$(nproc)"                                  # сборка
./build/tests/sage_tests                                          # модульные
xvfb-run -a ./build/tests/render/sage_render_tests \
    --references tests/render/references                          # кадровые
cd build/editor && SAGE_EDITOR_SELFTEST=1 xvfb-run -a ./SageEditor  # самопроверка
bash scripts/ci_smoke_test.sh                                     # smoke
python3 scripts/check_localization.py                             # переводы
python3 scripts/check_rhi_boundary.py                             # граница RHI
cmake --build build-windows -j"$(nproc)"                          # кросс-сборка mingw
```

## Релиз — после каждого слияния в main, всегда

Свежая сборка выкладывается на замену старой КАЖДЫЙ раз, а не «когда
накопится». Причина простая: скачивают её, а не репозиторий, и всё, что не
попало в релиз, для человека не существует — он продолжает видеть старые
ошибки и сообщать о них заново.

Как это устроено: `.github/workflows/windows.yml` собирает Windows-архив на
каждый пуш и **со ссылкой `windows-latest` заменяет прежний релиз — но только
с `main`**. С рабочих и резервных веток архив кладётся артефактом на вкладку
Actions и публичную ссылку не трогает: иначе «последняя сборка» достаётся той
работе, что финишировала последней, а не той, что новее, — и резервная ветка
(заведомо старое состояние) перезаписывала бы релиз. Двух слияний подряд это
тоже касается: перед публикацией работа сверяет свой коммит с вершиной `main`
и уступает дорогу более новой сборке.

Поэтому порядок такой:

1. Слить работу в `main` и запушить `main` (см. порядок выше).
2. Дождаться работы «Сборка редактора для Windows» и убедиться, что она
   ЗЕЛЁНАЯ, а релиз `windows-latest` обновился (дата и коммит в описании).
3. Если работа упала — релиз остался старым, и это надо чинить сразу: молча
   оставить человека со старой сборкой хуже, чем не собрать вовсе.

В описании релиза обязаны быть хеш и тема коммита, из которого он собран, —
иначе «свежая сборка» проверяется только на слово.

**Обе платформы — обязательны, всегда.** Движок, редактор и плеер собираются и
под Linux (`build/`), и под Windows (`build-windows/`, mingw). Не «если
успеется» и не «раз правка мелкая»: половина того, что ломает Windows-сборку, на
Linux не видна вообще — другой компилятор, другие заголовки, `std::filesystem`
с иным разделителем, отсутствующие POSIX-функции. Правка, проверенная на одной
платформе, — это правка, проверенная наполовину. macOS не собираем.


Самопроверка редактора не завершается сама — она пишет в
`build/editor/sage_editor.log` строку `SELFTEST: PASS` или `SELFTEST: FAIL`
и продолжает работать; запускать её надо ИЗ `build/editor` (иначе не найдёт
свои ассеты) и читать вердикт из лога.

## Правила самого кода

- **Комментарии и весь текст интерфейса — по-русски.** Комментарий объясняет
  ПОЧЕМУ так, а не пересказывает код.
- **Каждая строка интерфейса — через `T("...")`**, перевод дописывается в
  `editor/lang/ru.json`, затем `python3 scripts/gen_lang.py`. Проверяет
  `scripts/check_localization.py`.
- **Вызовы `gl*` — только в `engine/src/rhi/`.** Проверяет
  `scripts/check_rhi_boundary.py`.
- **Новый файл в редакторе** дописывается в `editor/CMakeLists.txt`.
- Правка поведения — вместе с проверкой, которая на старом коде падает.
