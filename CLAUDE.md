# Правила работы над SAGE-Engine

Файл для Claude Code. Здесь ПОРЯДОК РАБОТЫ, а не описание движка: движок
описан в README.md, и он же — источник правды по архитектуре.

## Порядок внесения изменений (обязателен, без исключений)

Так работаем ВСЕГДА, даже если правка кажется мелкой.

1. **Точка возврата — до начала работы.** Текущее состояние `main`
   закрепляется веткой-резервом:
   `git branch -f claude/backup-main-<ГГГГММДД>-<sha> main && git push origin <она>`
   Веткой, а не тегом: пуш тегов в этом окружении отдаёт 403 (прокси
   пропускает только ветки). Резерв не удаляется — по нему `main`
   возвращается к последнему заведомо рабочему состоянию одной командой.
2. **Работа — в отдельной ветке** от свежего `origin/main`:
   `git fetch origin main && git checkout -B claude/<о-чём-правка> origin/main`.
   Прямо в `main` не коммитим.
3. **Проверка — до слияния.** Полный прогон (см. ниже) обязан быть зелёным
   НА ВЕТКЕ. Не «соберётся — увидим»: в `main` не должно попадать ничего
   непроверенного.
4. **Слияние в main — отдельным шагом и только после проверки.** Сливаем
   `--no-ff`, чтобы в истории осталась граница работы и её можно было
   откатить целиком одним `git revert -m 1`.
5. **Ветка не удаляется** сразу после слияния: пока правка не пожила,
   она — второй путь назад.

Откат, если что-то пошло не так: `git revert -m 1 <коммит слияния>` (мягко,
история сохраняется) или `git reset --hard <резервная ветка>` + пуш с
`--force-with-lease` (жёстко, только по прямой просьбе).

## Что прогнать перед слиянием

```
cmake --build build -j"$(nproc)"                                  # сборка
./build/tests/sage_tests                                          # модульные
xvfb-run -a ./build/tests/render/sage_render_tests \
    --references tests/render/references                          # кадровые
cd build/editor && SAGE_EDITOR_SELFTEST=1 xvfb-run -a ./SageEditor  # самопроверка
bash scripts/ci_smoke_test.sh                                     # smoke
python3 scripts/check_localization.py                             # переводы
python3 scripts/check_rhi_boundary.py                             # граница RHI
python3 scripts/check_paths.py                                    # пути из окружения
python3 scripts/check_engine_api.py                               # граница движок->игра
cmake --build build-windows -j"$(nproc)"                          # кросс-сборка mingw
```

## Релиз — после каждого слияния в main, всегда

Свежая сборка выкладывается на замену старой КАЖДЫЙ раз, а не «когда
накопится». Причина простая: скачивают её, а не репозиторий, и всё, что не
попало в релиз, для человека не существует — он продолжает видеть старые
ошибки и сообщать о них заново.

Как это устроено: `.github/workflows/windows.yml` собирает Windows-архив на
каждый пуш и **со ссылкой `windows-latest` заменяет прежний релиз — но только
с `main`**. С рабочих и резервных веток архив кладётся артефактом на вкладку
Actions и публичную ссылку не трогает: иначе «последняя сборка» достаётся той
работе, что финишировала последней, а не той, что новее, — и резервная ветка
(заведомо старое состояние) перезаписывала бы релиз. Двух слияний подряд это
тоже касается: перед публикацией работа сверяет свой коммит с вершиной `main`
и уступает дорогу более новой сборке.

Поэтому порядок такой:

1. Слить работу в `main` и запушить `main` (см. порядок выше).
2. Дождаться работы «Сборка редактора для Windows» и убедиться, что она
   ЗЕЛЁНАЯ, а релиз `windows-latest` обновился (дата и коммит в описании).
3. Если работа упала — релиз остался старым, и это надо чинить сразу: молча
   оставить человека со старой сборкой хуже, чем не собрать вовсе.

В описании релиза обязаны быть хеш и тема коммита, из которого он собран, —
иначе «свежая сборка» проверяется только на слово.

**Обе платформы — обязательны, всегда.** Движок, редактор и плеер собираются и
под Linux (`build/`), и под Windows (`build-windows/`, mingw). Не «если
успеется» и не «раз правка мелкая»: половина того, что ломает Windows-сборку, на
Linux не видна вообще — другой компилятор, другие заголовки, `std::filesystem`
с иным разделителем, отсутствующие POSIX-функции. Правка, проверенная на одной
платформе, — это правка, проверенная наполовину. macOS не собираем.

**Пути — не ASCII.** У человека, который скачивает сборку, имя пользователя
запросто написано кириллицей, и все его проекты лежат в
`C:\Users\Владимир\Documents\SAGE Projects`. Значит: значение окружения
превращается в путь только через `sage::EnvPath`/`sage::EnvString`
(`engine/src/sage/core/Paths.h`), а `std::getenv` для путей запрещён — сторожит
`scripts/check_paths.py`. Причина не теоретическая: одна строка
`std::getenv("APPDATA")` не давала редактору запуститься на русской Windows
вообще, потому что `std::filesystem::path` на байтах ANSI не возвращает ошибку,
а БРОСАЕТ исключение. Windows-сборка несёт манифест с `activeCodePage=UTF-8`
(`cmake/windows/sage.manifest`) — без него узкие функции системы (`fopen`, а с
ним `std::ifstream` от `std::string`) не открывают ни одного файла по такому
пути.


Самопроверка редактора не завершается сама — она пишет в
`build/editor/sage_editor.log` строку `SELFTEST: PASS` или `SELFTEST: FAIL`
и продолжает работать; запускать её надо ИЗ `build/editor` (иначе не найдёт
свои ассеты) и читать вердикт из лога.

## Что такое SAGE Engine (это определение, а не лозунг)

**SAGE Engine ≠ игра.** Движок — законченный инструмент разработки: своя
библиотека, свой редактор, свой рантайм, своя командная строка. Он не знает,
какую игру на нём напишут, и не имеет права узнать.

Из этого следуют правила ниже. Они не «пожелания к архитектуре»: каждое
однажды уже было нарушено, и каждое стоило рабочего дня. Проверять их надо
ПЕРЕД тем, как писать код, а не после.

**Движком пользуются тремя способами, и все три равноправны:**

| Способ | Чем | Что обязано работать |
|---|---|---|
| SDK / библиотека | `#include <sage/Sage.h>` + `sage::engine` | всё, без единого запуска редактора |
| Визуальный редактор | `SageEditor` | всё, без единой строчки C++ |
| Оба сразу | одна папка проекта | правки в обе стороны, без импорта и конвертации |

Разработчик выбирает сам, и ни один выбор не должен урезать возможности. Плюс
`SagePlayer` (готовая игра запускается без редактора) и `sage` (командная
строка без окна и без OpenGL — для сборочных машин, ssh и git-хуков).

### Правила, которые нельзя нарушать

**1. Одна реализация на всех.** Редактор, SDK, плеер и командная строка —
ВХОДЫ в один и тот же код, а не четыре похожие программы. Понятие, нужное
двоим, живёт в `engine/`.

Проверочный вопрос перед каждой правкой в `editor/` или `runtime/`: это
политика ИМЕННО этого потребителя (плеер делает chdir, редактор — нет) или
общее понятие? Общее — в движок, немедленно, а не «потом вынесем».

**2. Никакого двойного хранения.** У проекта один источник правды. Файл
`project.sageproj` — ОПИСАНИЕ того же проекта, а не его копия для редактора.
Появилось желание завести «редакторскую версию» данных — это ошибка
проектирования, а не удобство.

**3. Ни импорта, ни конвертации, ни экспорта между SDK и редактором.**
`sage project create MyGame` и `SageEditor MyGame/project.sageproj` работают с
одной папкой. Любая кнопка «Импортировать проект» означает, что правило 1
нарушено. Стережёт smoke-тест 11/11 — он гоняет всю цепочку целиком.

**4. Редактор не обязателен, и игра не обязана его видеть.** Собранная игра
запускается сама. Проект создаётся, читается и правится программно. Если
что-то можно сделать ТОЛЬКО мышью — этого нет в API, и это дыра в API.

**5. Игра не знает, из чего собран движок.** В `games/` не должно быть ни
`<GLFW/...>`, ни `<glm/...>`, ни `<entt/...>`, ни `ImGui::`. Коды клавиш —
`sage::Key`, захват курсора — `Window::SetCursorCaptured`, время —
`Application::Time`, математика — `sage/core/Math.h`, всё сразу —
`<sage/Sage.h>`. Сторожит `scripts/check_engine_api.py`.

Сторонние библиотеки ВНУТРИ движка — его свобода и его дело. Запрет касается
только границы «движок отдаёт игре». Понадобилось игре то, чего в API нет, —
это не повод включить GLFW, это повод добавить метод движку.

**6. В движке нет игровой логики.** `Player`, `Enemy`, `Weapon`, `Quest`,
`Inventory`, правила матча, поведение NPC — это игра. Движок даёт `Entity`,
`Transform`, `Scene`, `Material`, `Mesh`, `Texture`, `Audio`, `UIElement`,
`Resource`, физику, ввод, скриптинг, сохранения, сеть. Система, нужная ровно
одному проекту, живёт в этом проекте.

Полноразмерные игры лежат в СВОИХ репозиториях. В `games/` — только примеры,
и они выключаются одним `SAGE_BUILD_SAMPLES=OFF`.

**7. Всё, что здесь написано, проверяется программой.** Правило, записанное
только словами, живёт до первого дедлайна:

| Правило | Чем проверяется |
|---|---|
| 1, 2, 3 | `tests/test_project.cpp`, smoke 11/11 (SDK → редактор → плеер) |
| 4 | `tools/sage_cli` линкует движок и не создаёт `Application` — не собралось бы |
| 5 | `scripts/check_engine_api.py` |
| 6 | `tests/test_ui.cpp` (предметных иконок в движке НЕТ) |

Добавили правило — добавьте и сторожа. Не получается написать сторожа — значит
правило сформулировано слишком расплывчато, чтобы его соблюдать.

## Откуда эти правила взялись (реальные случаи, не гипотезы)

**Проект жил в редакторе.** Класс `Project` лежал в `editor/src/` с
комментарием «проект это сущность редактора, движку о нём знать не нужно».
Плеер класса редактора не видит — и разбирал `project.sageproj` своим кодом,
своим json-парсером, со своим правилом поиска главной сцены. Правило успело
развестись в ТРЁХ местах, а игра без редактора проектом не могла
воспользоваться вовсе. Теперь это `sage::project::Project`, и второй
реализации завести негде (нарушены были правила 1, 2, 3, 4).

**Движок протекал в игровой код.** Игры брали коды клавиш у GLFW
(`InputBinding::Key(GLFW_KEY_W)`), захват курсора — у `glfwSetInputMode`,
время кадра — у `glfwGetTime`, математику — прямо у glm. То есть автор игры
был обязан знать, из чего движок собран, и связывать его библиотеки сам
(нарушено правило 5).

**Инвентарь одной игры лежал в движке.** Набор иконок `sage/ui/UIIcons.cpp` на
две трети состоял из предметов ОДНОЙ игры: доска, бревно, ящик, бочка, весло,
рыба, якорь, парус. Двадцать четыре предмета чужого мира ехали в каждую сборку
каждого проекта, а свои иконки игра добавить не могла — таблица была зашита
константой (нарушено правило 6).

**Обход бага движка жил в каждом потребителе.** `ResourceManager` освобождался
после гибели GL-контекста и ронял процесс на выходе. Обход — `Clear()` в своём
`OnDetach` — был записан в редакторе, плеере, sandbox и testgame: четыре
одинаковые строки, обязательные и никем не проверяемые. Первая игра,
написанная по документации, а не по памяти сопровождающего, о них не знала.
Правильное место оказалось одно — `~Application` (нарушено правило 1).

## Правила самого кода

- **Комментарии и весь текст интерфейса — по-русски.** Комментарий объясняет
  ПОЧЕМУ так, а не пересказывает код.
- **Каждая строка интерфейса — через `T("...")`**, перевод дописывается в
  `editor/lang/ru.json`, затем `python3 scripts/gen_lang.py`. Проверяет
  `scripts/check_localization.py`.
- **Вызовы `gl*` — только в `engine/src/rhi/`.** Проверяет
  `scripts/check_rhi_boundary.py`.
- **Новый файл в редакторе** дописывается в `editor/CMakeLists.txt`.
- Правка поведения — вместе с проверкой, которая на старом коде падает.
