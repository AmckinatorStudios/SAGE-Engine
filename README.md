# SAGE Engine — универсальный 3D-движок (C++ / OpenGL)

**SAGE Engine — универсальный движок общего назначения, не воксельный.**
Ядро (окно, рендер, камера, сцены, сериализация, скриптинг) не знает
и не должно ничего знать о вокселях — оно одинаково подходит для любой
3D-игры: шутера, платформера, симулятора, чего угодно. Воксельная система
(`src/voxel/`) — это МОДУЛЬ КОНКРЕТНОЙ ИГРЫ (The Boat), написанный поверх
ядра движка, точно так же как любой другой игровой код мог бы быть написан
поверх него. Если следующая игра не про воксели — просто не подключаешь
`src/voxel/`, и движок останется тем же самым.

Готовые пакеты игры The Boat собраны и лежат в `dist/` — Linux и Windows,
кросс-скомпилировано и проверено мной вручную (собрано, слинковано, запущено
headless для проверки).

## Быстрый старт (Windows, без сборки)
Готовый пакет игры лежит в `dist/windows/TheBoat-0.1.0-windows-x64.zip`.
Распакуй архив и запусти `TheBoat.exe` — всё нужное (ассеты) уже внутри,
ничего доустанавливать не надо.

### Движок ⇄ игра: где шов
Движок (`core/Engine.*`) владеет окном, главным циклом и таймингом и «крутит»
игру через интерфейс `core/Game.h` (хуки `OnStart`/`OnUpdate`/`OnRender`/
`OnShutdown`), но НИЧЕГО не знает о конкретной игре. `main.cpp` свёлся к паре
строк — создать `Engine`, создать `TheBoat`, вызвать `engine.Run(game)`.
Чтобы сделать другую игру, пишешь свой класс с интерфейсом `Game` вместо
`TheBoat` — код движка (`core`/`render`/`scene`/`scripting`/`ui`) не меняется:

```cpp
// весь main.cpp:
Engine engine(TheBoat::DefaultConfig()); // окно + GL-контекст
TheBoat game(engine);                    // игра грузит свои ресурсы
engine.Run(game);                        // OnStart -> цикл -> OnShutdown
```



## Управление в демо
- W/A/S/D — движение, мышь — поворот, Space/Shift — вверх/вниз, Esc — выход
- **F5** — сохранить текущую сцену в `assets/scenes/level1.sage`
- **F9** — загрузить сцену из `assets/scenes/level1.sage`

## Система сцен и сериализация
`Scene` — список объектов (`GameObject`): имя, `Transform` (позиция/
поворот/масштаб), ссылка на меш (`MeshRefComponent`: куб или путь к .obj),
цвет. `SceneManager` умеет держать несколько сцен одновременно и
переключать активную:

```cpp
SceneManager sceneManager;
Scene& level1 = sceneManager.CreateScene("Level1");
auto& obj = level1.CreateObject("MyCube");
obj.MeshRefComponent.type = MeshRef::Type::Cube;
obj.MeshComponent = ResourceManager::Instance().GetCube();

// Сохранить сцену на диск (человекочитаемый JSON, расширение .sage)
sceneManager.SaveScene("Level1", "assets/scenes/level1.sage");

// Загрузить сцену обратно (сам пересоздаст GPU-ресурсы мешей)
sceneManager.LoadScene("assets/scenes/level1.sage");
```

Файл `.sage` — обычный JSON, можно открыть и посмотреть/поправить руками:
```json
{
  "sage_scene_version": 1,
  "name": "Level1",
  "objects": [
    {
      "id": 1, "name": "Cube1",
      "position": {"x":0,"y":0,"z":0},
      "rotation": {"x":0,"y":0,"z":0},
      "scale":    {"x":1,"y":1,"z":1},
      "color":    {"x":0.8,"y":0.3,"z":0.3},
      "mesh": {"type":"cube","path":""}
    }
  ]
}
```

Для модели вместо куба: `"mesh": {"type":"model","path":"assets/models/dragon.obj"}`.

## Скриптинг (Lua)
Часть ЯДРА движка (`src/scripting/ScriptEngine.*`) — не зависит от вокселей
и вообще ни от какой конкретной игры. Позволяет управлять поведением
`GameObject` через `.lua` файлы без перекомпиляции движка: правишь скрипт,
перезапускаешь игру, видишь результат.

```cpp
ScriptEngine scriptEngine;
scriptEngine.AttachScript(myGameObject, "assets/scripts/spin.lua");

// каждый кадр:
scriptEngine.UpdateAll(deltaTime);
```

Скрипт получает объект как `entity` и может читать/писать его Transform и цвет:
```lua
-- assets/scripts/spin.lua
function OnStart(entity)          -- необязательно, вызывается один раз
    log("Скрипт запущен для: " .. entity.Name)
end

function OnUpdate(entity, dt)     -- обязательно, вызывается каждый кадр
    entity.Transform.Rotation.y = entity.Transform.Rotation.y + dt * 45.0
end
```

В демо (`main.cpp`) есть отдельный обычный (не воксельный!) `GameObject` —
жёлтый вращающийся куб рядом с водой — управляемый именно этим скриптом.
Он существует независимо от воксельного мира: это и есть доказательство,
что скриптинг (и вся ECS-сцена) — общая часть движка, а не что-то
специфичное для The Boat.

Что уже доступно скриптам из коробки: `entity.Name`, `entity.Transform`
(`.Position`/`.Rotation`/`.Scale`, каждое `Vec3` с полями `.x/.y/.z`),
`entity.Color`, функция `log(строка)`. Чтобы добавить свою API-функцию —
смотри `ScriptEngine::RegisterEngineApi()`, там пара строк на sol2 на каждую
привязку.

## Текстуры
Часть ЯДРА движка (`src/render/Texture.*`, через stb_image) — грузит PNG/JPG/BMP/TGA
в GPU-текстуру, не зависит от вокселей. Используется в двух местах, чтобы
показать это:

**1. Обычный (не воксельный) объект** — демо-куб красится текстурой
`assets/textures/checker_demo.png` (режим `Anisotropic`) через обычный
`basic.vert/frag` (обычные UV из `Mesh`/`ModelLoader`, ничего воксельного).

**2. Атлас текстур блоков** — `assets/textures/blocks_atlas.png` (сетка 4×2
тайла: grass/dirt/stone/wood/plank). `Chunk::RebuildMesh` считает для каждой
грани блока прямоугольник UV внутри атласа (`Block::GetBlockAtlasIndex`),
один тайл на все 6 граней блока (текстуры "верх отличается от боков" как в
Minecraft — пока нет, это в TODO).

```cpp
Texture myTexture("assets/textures/что-то.png", TextureFilter::Trilinear);
myTexture.Bind(0);
shader.SetInt("uTexture", 0);
shader.SetInt("uUseTexture", 1); // если 0 — рендер работает по-старому, только цветом
```

### Фильтрация текстур
`TextureFilter` — 4 режима, выбираются явно при загрузке:

| Режим | Когда использовать |
|---|---|
| `Nearest` | Пиксельная чёткость без сглаживания — voxel-атласы, pixel-art |
| `Bilinear` | Простое сглаживание без перехода между уровнями мипмапов |
| `Trilinear` | Сглаживание + плавный переход между мипмапами — стандартный выбор по умолчанию |
| `Anisotropic` | Как Trilinear, плюс убирает размытость на поверхностях под острым углом к камере (типично — земля/пол, если смотреть почти вдоль неё) |

```cpp
Texture ground("assets/textures/ground.png", TextureFilter::Anisotropic);
```

Anisotropic реализован через расширение `GL_EXT_texture_filter_anisotropic`
(в OpenGL до версии 4.6 это расширение, не core-функциональность — у нас
контекст 3.3 core, поэтому токены расширения объявлены в `Texture.cpp`
вручную, без загрузки функций — они и не нужны, только два enum-значения).
Уровень анизотропии запрашивается автоматически: движок узнаёт максимум,
который поддерживает видеокарта (`Texture::MaxSupportedAnisotropy()`), и
использует `min(4.0, максимум)` — разумный баланс качества и производительности.
Проверил на реальном GPU в этом окружении (Mesa) — драйвер поддерживает до
16x, движок корректно запросил и применил 4x.

`Anisotropic`/`Trilinear` требуют мипмапов и включают их автоматически.
Для атласов (см. ниже) это неприменимо — атласам нужен `Nearest` без мипмапов.

**Важная деталь про атласы**: для `blocks_atlas.png` мипмапы ОТКЛЮЧЕНЫ
(`generateMipmaps=false`, фильтр `Nearest`) — это принципиально для атласов. Я сначала собрал
атлас с мипмапами и обычным NEAREST-фильтром, запустил игру, посмотрел
скриншот — и увидел на дальних блоках едва заметный розовый оттенок (в
атласе были розовые "неиспользуемые" тайлы-заполнители, и мипмап на дальних
объектах усреднял их цвет с соседними настоящими текстурами — классическая
проблема "протекания" тайлов в атласе). Исправил два раза: заменил
неиспользуемые тайлы на нейтральную текстуру камня вместо розового, и
отключил мипмапы для атласа целиком. Если будешь делать свой атлас — либо
отключай мипмапы, либо добавляй отступы (padding) между тайлами (с отступами
можно будет включить мипмапы/анизотропию и для атласа тоже — пока не сделано).

## Загрузка 3D-моделей (OBJ+MTL / GLTF / GLB)
Часть ЯДРА движка (`src/render/Model.*`) — грузит модели трёх форматов,
с материалами и текстурами, без вокселей. Определяет формат по расширению
файла автоматически:

```cpp
auto model = Model::Load("assets/models/dragon.glb"); // или .obj, или .gltf
...
shader.Use();
shader.SetMat4("uModel", transformMatrix);
model->Draw(shader); // сама переключает текстуру/цвет между подмешами (submesh)
```

Одна модель может состоять из нескольких **подмешей** (`SubMesh`) — разные
части с разными материалами/текстурами. `Model::Draw()` сам проходит по всем
подмешам, для каждого включает нужную текстуру (или просто цвет, если
текстуры нет) и рисует.

**Проверено на реальных файлах** (не просто скомпилировано — я загрузил их
в реальном запуске движка и проверил вывод в консоли):

| Файл | Формат | Результат |
|---|---|---|
| `Monkey.obj` + `Monkey.mtl` | OBJ+MTL | Загружен, 1 подмеш (в .mtl не было материала — корректно упал на нейтральный серый цвет) |
| `trash_can_minecraft.glb` | GLB (бинарный glTF) | Загружен, 4 подмеша |
| `bench-minecraft` (`model.gltf`, текстуры встроены как base64) | GLTF (текстовый) | Загружен, 55 подмешей (из иерархии узлов — типично для экспорта из Sketchfab) |

Все три лежат в `assets/models/` и подгружаются прямо в демо (`main.cpp`) —
их видно в игре рядом с кораблём.

### Как это устроено технически
- **OBJ**: через tinyobjloader, с поддержкой `.mtl` (путь к материалам
  берётся из той же папки, где лежит `.obj`). Вершины группируются по
  `material_id` — каждая группа становится отдельным `SubMesh`, потому что
  у разных материалов могут быть разные текстуры. Если материала нет
  (как у Monkey.mtl) — используется нейтральный серый цвет.
- **GLTF/GLB**: через tinygltf, с полным обходом иерархии узлов сцены
  (`ProcessNode` рекурсивно применяет трансформацию узла — позицию/поворот/
  масштаб/матрицу — и запекает её прямо в вершины). Материалы читаются из
  `pbrMetallicRoughness` (базовый цвет + текстура). Для декодирования
  текстур (в том числе встроенных как base64, как у bench-minecraft)
  используется собственный image-loader на базе уже подключённого в
  движке stb_image — без дублирования кода/зависимостей.

### Известные ограничения (пока не поддержано)
- Только `pbrMetallicRoughness.baseColorTexture` — normal maps, metallic/
  roughness карты, emissive и т.п. пока не читаются (геометрия и базовый
  цвет/текстура — да, полноценный PBR-рендеринг — нет)
- Анимации/скелеты glTF не читаются (только статическая геометрия)
- OBJ без индексации вершин (каждая грань — свои вершины, без переиспользования) —
  чуть больше памяти на GPU, чем оптимально, но корректно и просто

## Воксельная система (модуль игры "The Boat", НЕ часть ядра движка)
Уже готово: несколько чанков, объединённых в открытый мир, генерация рельефа,
вода, текстуры блоков через общий атлас.

```
src/voxel/
  Block.h            — типы блоков (Air, Grass, Dirt, Stone, Wood, Plank),
                        индекс тайла в атласе для каждого типа
  Chunk.h/cpp         — чанк 16x16x16 блоков + генерация меша (face culling + UV)
  World.h/cpp          — СЕТКА чанков: GetBlock/SetBlock по мировым координатам,
                          процедурная генерация рельефа (остров), бесшовный мешинг
                          на стыках соседних чанков
  VoxelMesh.h/cpp       — GPU-меш с цветом (тонирование) и UV на вершину
  VoxelRaycast.h         — рейкаст по вокселям ОДНОГО чанка (для изолированных объектов)
  WorldRaycast.h          — рейкаст по вокселям ВСЕГО мира (пересекает границы чанков)
  WaterPlane.h             — простая полупрозрачная плоскость воды на уровне моря
```

В демо `main.cpp`: генерируется остров 7×7 чанков (112×112 блоков) с холмистым
рельефом и настоящими текстурами (трава/земля/камень), рядом стоит корабль
(тоже воксельный, из текстурированных блоков Wood/Plank), вокруг — полупрозрачная
вода. WASD+мышь — ходить, **ЛКМ — сломать блок**, **ПКМ — поставить блок**,
колесо мыши — выбрать тип блока. Ломать/строить можно и рельеф, и корабль —
это одна и та же воксельная система.

### Как это работает
- `World` хранит чанки в `unordered_map<ivec3, Chunk>` — по сути "бесконечная" сетка,
  чанки существуют только там, где реально что-то сгенерировано/построено
- При изменении блока на самой границе чанка (`World::SetBlock`) сосед тоже
  помечается "грязным" — иначе на стыке чанков были бы дыры или лишние грани
- `Chunk::RebuildMesh(World*)` при мешинге на границе чанка спрашивает соседний
  блок у `World`, а не считает всё за краем воздухом
- Рельеф генерируется суммой синусоид (`World::TerrainHeight`) — не настоящий
  шум Перлина, но даёт органичный холмистый ландшафт без сторонних библиотек
- Вода — не воксельная, а один большой полупрозрачный квад (дешевле и достаточно
  для ощущения открытого моря)

### Дальше для полноценной игры понадобится (скажи, с чего начать)
- **Разные текстуры на гранях одного блока** (верх/бок/низ — трава сверху
  зелёная, а сбоку с полоской земли, как в Minecraft)
- **Плавучесть/движение корабля** как единого твёрдого тела
- **Динамическая подгрузка чанков** вокруг игрока (сейчас мир генерируется
  весь сразу при старте, фиксированного размера)
- **Сохранение мира** — бинарный формат для чанков (JSON не подойдёт, будет тяжёлым)
- **Инвентарь и UI**
- **Коллизии игрока с блоками** (сейчас камера свободно летает сквозь блоки)

## Skybox
Часть ЯДРА движка (`src/render/Skybox.*`) — кубическая (cubemap) текстура,
создающая иллюзию бескрайнего неба вокруг сцены. Не зависит от вокселей.

```cpp
Skybox skybox({
    "assets/textures/skybox/px.png", "assets/textures/skybox/nx.png",
    "assets/textures/skybox/py.png", "assets/textures/skybox/ny.png",
    "assets/textures/skybox/pz.png", "assets/textures/skybox/nz.png"
});
// каждый кадр, ПЕРВЫМ (до остальной сцены):
skybox.Draw(skyboxShader, view, projection);
```

Как это устроено технически:
- Из view-матрицы перед отрисовкой skybox убирается позиция камеры
  (`glm::mat4(glm::mat3(view))`) — скайбокс реагирует на поворот камеры,
  но не двигается при перемещении, как и положено бесконечно далёкому небу
- В вершинном шейдере используется трюк `gl_Position = pos.xyww` — глубина
  после деления перспективы всегда получается 1.0 (максимально далеко),
  поэтому с `glDepthFunc(GL_LEQUAL)` skybox гарантированно оказывается
  позади любой другой геометрии независимо от порядка отрисовки
- На время отрисовки backface culling временно отключается (куб рисуется
  "изнутри", все грани отвёрнуты от камеры при обычном culling)

Текстуры неба (`assets/textures/skybox/*.png`) сгенерированы процедурно —
вертикальный градиент от зенита к горизонту на боковых гранях, согласованный
по цвету с остальной сценой.

### Исправленный баг: видимый шов на стыке верхней грани
Изначально при взгляде вверх был виден резкий скачок цвета ровно на границе
между верхней (+Y) гранью и боковыми гранями — выглядело как "видно край
скайбокса". Нашёл и исправил две причины:

1. **`GL_TEXTURE_CUBE_MAP_SEAMLESS` не был включён.** Без этого драйвер не
   интерполирует между соседними гранями cubemap на самой границе. Добавил
   `glEnable(GL_TEXTURE_CUBE_MAP_SEAMLESS)` в `Window.cpp` — это должно быть
   включено один раз при инициализации контекста, и полезно для любого
   cubemap в движке, не только skybox.
2. **Главная причина — неверный цвет на краю верхней грани.** Верхняя (+Y)
   грань физически стыкуется с *верхним* краем каждой боковой грани (не с
   нижним/горизонтом, как я изначально предположил). А цвет на этом крае у
   меня был HORIZON_COLOR вместо TOP_COLOR — то есть верх стыковался с
   "горизонтом" боковых граней вместо их "зенита", отсюда и резкий скачок
   яркости точно на границе. Проверял через headless-рендер под разными
   углами камеры (55°, 70°, 89° от горизонта) — строил вертикальный срез
   пикселей по кадру и автоматически искал резкие перепады яркости, чтобы
   локализовать баг именно на границе граней, а не гадать по скриншотам.
   Починил — сделал верхнюю грань сплошным зенитным цветом (гарантированно
   совпадает с краем боковых граней при любом угле обзора).

## Пост-процессинг (HDR + тон-маппинг)
Часть ЯДРА рендера (`src/render/Framebuffer.h`, `PostProcess.h`,
`assets/shaders/post.*`) — не зависит от вокселей/конкретной игры.

Вся 3D-сцена рисуется не в экран напрямую, а в offscreen HDR-буфер
(`GL_RGBA16F` — цвет может выходить за пределы [0,1], что нужно для честного
тон-маппинга). Затем полноэкранный проход выводит буфер на экран, применяя:
- **экспозицию** и плёночный **тон-маппинг ACES** (мягкий завал ярких участков
  вместо грубого клиппинга в белое);
- **гамма-коррекцию**;
- **насыщенность** и **контраст**;
- **виньетку** (затемнение к углам кадра).

UI рисуется ПОСЛЕ пост-процессинга, поэтому текст и полоски статов остаются
чёткими и не тон-мапятся вместе со сценой.

Все параметры — поля `PostProcessSettings`, заливаются каждый кадр (см.
`main.cpp`), так что игра может менять картинку без правки движка. Экспозицию
можно переопределить на запуске: `SAGE_EXPOSURE=1.3 ./TheBoat`. Весь проход
целиком отключается для сравнения "до/после": `SAGE_NO_POST=1 ./TheBoat`.

## Тени (shadow mapping от солнца)
Часть ЯДРА рендера (`src/render/ShadowMap.h`, `assets/shaders/shadow_depth.*`) —
не зависит от вокселей/конкретной игры.

Направленный свет ("солнце") отбрасывает тени через классический shadow
mapping в два прохода:
1. **Проход глубины** — сцена рисуется из точки зрения солнца (ортографическая
   проекция — параллельные лучи) в depth-текстуру. Ортобокс следует за
   кораблём, накрывая его и воду вокруг.
2. **Основной проход** — шейдеры-приёмники (`voxel`/`basic`/`water`) сэмплируют
   карту теней и решают, в тени ли фрагмент. Мягкие края даёт **PCF 3×3**,
   от самозатенения (shadow acne) защищает **slope-scaled bias** + отсечение
   лицевых граней в проходе глубины.

Тень гасит только вклад солнца — ambient и фонари не затеняются (ночью, когда
солнце выключено, фонари освещают палубу как обычно). Тень корабля ложится и
на палубу (самозатенение вокселей), и на воду вокруг. Отключается для
сравнения: `SAGE_NO_SHADOWS=1 ./TheBoat`. Статус обоих проходов виден в
debug-HUD (F3): строка `post: on  shadows: on`.

## Backface culling
Движок не рисует грани треугольников, обращённые от камеры (`glEnable(GL_CULL_FACE)`
в `Window.cpp`). Для воксельного мира это существенная экономия — у каждого
видимого блока обычно не все 6 граней смотрят на игрока. Все меши движка
(`Mesh`, `VoxelMesh`, `WaterPlane`) используют CCW-порядок вершин при взгляде
снаружи/сверху — если будешь добавлять свою геометрию руками, важно соблюдать
тот же порядок, иначе грани будут "невидимыми" с неправильной стороны.

## Сборка готового продукта под платформу
Есть скрипты, которые одной командой создают ГОТОВЫЙ К РАЗДАЧЕ архив —
бинарник + все assets, версионировано:

```
scripts/
  build_linux.sh      — собрать + упаковать под Linux (из Linux)
  build_windows.sh     — собрать + упаковать под Windows (кросс-компиляция из Linux)
  build_windows.bat      — собрать + упаковать под Windows (если собираешь прямо на Windows)
  build_all.sh             — собрать сразу под обе платформы
```

Использование:
```bash
./scripts/build_linux.sh              # соберёт "TheBoat" (имя по умолчанию)
./scripts/build_windows.sh            # кросс-компиляция в .exe
./scripts/build_all.sh                # обе платформы разом

./scripts/build_linux.sh MyNextGame   # для СЛЕДУЮЩЕЙ игры на этом же движке —
                                       # просто другое имя, весь код общий
```

Результат появляется в `dist/`:
```
dist/linux/TheBoat-0.1.0-linux-x64.tar.gz
dist/windows/TheBoat-0.1.0-windows-x64.zip
```

Версия игры берётся из файла `VERSION` в корне — подними её перед следующим
релизом. Каждый архив самодостаточен: распаковал — запустил, ничего доустанавливать
не нужно (Windows-сборка статически линкует рантайм MinGW, DLL не требуются).

## Как собрать вручную (без скриптов, для разработки)

### Windows
```
cd engine
cmake -B build -DGAME_NAME=TheBoat
cmake --build build --config Release
```
Или открой папку в Visual Studio через "Open Folder" — она сама подхватит CMake.

### Linux
```
sudo apt install cmake g++ libx11-dev libxrandr-dev libxinerama-dev \
                  libxcursor-dev libxi-dev libgl1-mesa-dev
cd engine
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGAME_NAME=TheBoat
cmake --build build -j$(nproc)
cd build && ./TheBoat
```

### Кросс-компиляция в .exe из Linux
```
sudo apt install g++-mingw-w64-x86-64
cd engine
cmake -B build-windows -DCMAKE_TOOLCHAIN_FILE=cmake/mingw-toolchain.cmake -DCMAKE_BUILD_TYPE=Release -DGAME_NAME=TheBoat
cmake --build build-windows -j$(nproc)
```
.exe линкуется статически — запускается на чистой Windows без установки рантайма MinGW.

Обрати внимание: имя выходного файла теперь `TheBoat` (или что укажешь в
`GAME_NAME`), а не `SAGEEngine` — движок называется SAGE Engine, но продукт,
который из него собирается, называется по имени игры.
