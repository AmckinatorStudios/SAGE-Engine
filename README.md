# SAGE Engine — универсальный модульный 3D-движок (C++ / OpenGL)

> **Статус: в активной разработке, версия `0.5.0`, до 1.0 ещё далеко.** Архитектура
> (ECS/RHI/редактор) на месте; боевое тестирование идёт через `games/testgame` —
> реальную игру-стресс-тест (комнаты-сцены, коллизии, подборы, враги, HUD,
> аудио, модели, тени, пост-процесс), которая гоняется в CI каждым коммитом и
> уже вскрыла и помогла починить реальные баги движка (конфликт GLFW-колбэков
> Window/InputSystem, неконструируемый из Lua `Vec3(...)`). До стабильного
> релиза — набрать больше такой практики и стабилизировать API редактора.

## Скачать и запустить редактор (Windows)

Посмотреть движок в деле можно без установки компилятора, CMake или чего бы то
ни было ещё.

1. Откройте раздел **[Releases](../../releases)** этого репозитория.
2. Скачайте **SageEditor-Windows.zip**.
3. Распакуйте папку целиком и запустите **SageEditor.exe**.

Внутри архива лежит `README.txt` с той же инструкцией на случай, если она
понадобится уже после скачивания.

Несколько заметок, которые экономят время:

* **Распаковывать нужно всю папку.** Рядом с программой лежат `assets`
  (шрифт интерфейса, шейдеры) и `plugins` (пример плагина). Один только
  `.exe` не заработает.
* **Windows покажет синее окно «Система Windows защитила ваш компьютер».**
  Это не поломка: так встречается любая программа без платной подписи
  разработчика. «Подробнее» → «Выполнить в любом случае», один раз.
* **Сам редактор ничего доустанавливать не требует.** `SageEditor.exe`
  собран со статической линковкой рантайма и требует только системные
  библиотеки Windows; сборка проверяет это автоматически и падает, если
  появилась посторонняя зависимость. Единственное исключение — идущий
  в комплекте `libstdc++-6.dll`: он нужен не самому редактору, а
  плагину-примеру (плагины линкуются на редактор как на хост и потому
  остаются на динамическом рантайме, см. `cmake/mingw-toolchain.cmake`).

Сборка обновляется автоматически при каждой правке — см.
`.github/workflows/windows.yml`. Это готовый `SageEditor` для знакомства с
инструментом; чтобы собрать и раздать СВОЮ игру на этом движке, см. раздел
«Сборка готового продукта под платформу» ниже — он про `scripts/build_*`,
отдельный сценарий для разработчиков игр.

**SAGE Engine — универсальный движок общего назначения с ECS, редактором на
ImGui и абстракцией графического бэкенда.** Ядро (окно, рендер, ECS-сцены,
сериализация, скриптинг, аудио) не знает ничего о конкретной игре — оно
одинаково подходит для любой 3D-игры. Проект строго разделён на три части:

- **`engine/`** — переиспользуемое ядро → статическая библиотека `sage::engine`.
  Публичный API отдаётся ТОЛЬКО под префиксом `<sage/...>` — игры и редактор
  физически не могут дотянуться до внутренностей мимо этой границы.
- **`editor/`** — редактор `SageEditor` на ImGui (линкует движок).
- **`games/<name>/`** — конкретные игры (линкуют движок, независимы друг от
  друга). Пример — `games/sandbox/`, минимальный showcase движка (см. ниже).

Добавить новую игру = создать `games/<name>/` и вызвать `sage_add_game()` в её
CMakeLists — движок общий, игровой код независим.

## Кэш ресурсов

Исходные форматы (glTF, PNG) сделаны для **обмена**: компактны, самоописательны,
читаются любой программой. Ровно поэтому они дороги при загрузке — JSON
разбирается посимвольно, PNG распаковывается попиксельно. Игра платила эту цену
при каждом запуске, хотя файл не менялся.

Замер на модели 48 тысяч вершин с текстурой 2048×2048:

| | время |
|---|---|
| разбор glTF | 4.6 мс |
| декодирование текстуры | 33.3 мс |
| **итого разбор** | **37.9 мс** |

87 % уходит на распаковку картинки — поэтому кэш хранит **распакованные
пиксели**, а не ссылку на исходный PNG.

Загрузка стала двухэтапной: `ParseGltf` разбирает файл в `ModelData` (чистые
данные, без OpenGL), `BuildFromData` загружает их на видеокарту. Между этими
этапами и встал кэш — раньше вставить его было некуда, потому что обе работы
делались одной функцией.

```
разбор исходника  93.7 мс
из кэша           58.0 мс   ( чтение кэша 24.7 мс + загрузка на GPU 33.3 мс )
```

Кэш обесценивается при правке исходника (сверяются размер и время), битый или
чужой версии — молча игнорируется: неверный кэш никогда не должен приводить к
неверной картинке, а его отсутствие — к отказу. Файлы лежат в `.sage-cache`
отдельным каталогом: каталог ассетов бывает только для чтения.

**Чего ещё нет и что говорят цифры.** Сжатия текстур (BC/ASTC) нет, поэтому
пиксели лежат сырыми и кэш крупной модели весит **20 МиБ против 4 МиБ
исходника**, а его чтение занимает те самые 24.7 мс. BC1 дал бы шестикратное
сжатие: чтение упало бы до ~4 мс, загрузка на видеокарту — вчетверо, и столько
же занимала бы видеопамять. Это следующий шаг, и теперь ему **есть куда
встать** — до появления этого пайплайна сжатие было некуда положить.

Тестовая модель генерируется `tools/make_test_model.py` (любого размера, без
внешних зависимостей); проверки сверяют, что модель из кэша совпадает с
разобранной до каждой кости и каждого ключа.

## Тени

Были «пиксельными» по двум независимым причинам, и большая — не та, на которую
думаешь.

**1. Коробка теней не подгонялась под сцену.** Стояло «центр в начале
координат, радиус 28 метров» — при карте 2048 это 2.7 см на тексель независимо
от того, что в сцене. Комнате из трёх предметов доставалась точность,
рассчитанная на стометровую площадку. Теперь радиус считается по фактическим
габаритам: сцена на 12 метров получает втрое более мелкий тексель на том же
разрешении. Это дало основную часть выигрыша.

**2. Сравнение глубины было жёстким.** `texture()` по карте глубины
интерполирует расстояния, а не тени, и сравнение с ним всё равно даёт ноль или
единицу — кромка выходила лесенкой в тексель. Теперь сравнение идёт в четырёх
соседних текселях, а смешиваются уже **результаты сравнения** (то же, что
делает аппаратный `sampler2DShadow`, но без смены формата текстуры), и таких
билинейных тапов берётся 3×3.

Плюс привязка коробки к сетке текселей — от неё тень перестаёт «кипеть» в
движении, — смещение выборки вдоль нормали вместо большого постоянного
смещения по глубине и отсечение по краям карты.

Измерено на демонстрационной сцене: резких ступеней на кромках стало на 22 %
меньше, плавных переходов на 39 % больше. Отдельная проверка
(`TestShadowSoftness`) меряет долю плавных переходов на нарочно грубой карте и
**падает на старом коде** — порог проверен с обеих сторон, а не подобран от
достигнутого.

### Каскады

Всё вышеперечисленное чинит качество на сцене, которая целиком помещается в
одну карту. Для улицы этого мало, и причина арифметическая: размер текселя в
метрах = `2·radius / resolution`. Комната (radius 10 м, карта 2048) — тексель
1 см, отлично. Улица (radius 200 м) — тот же тексель 20 см, и тень от столба
под ногами превращается в лесенку из квадратов. Фильтрацией это не лечится:
информации просто нет.

Каскады (`ShadowCascades` в настройках, 1..4) заводят несколько карт, каждая на
свой диапазон дальности. Ближняя маленькая и подробная, дальняя большая и
грубая — но она и видна издалека, где грубость незаметна.

```cpp
ShadowMap::CameraView v{camera.Position, camera.Front, camera.Up,
                        glm::radians(camera.Fov), aspect, camera.NearClip,
                        cfg.ShadowDistance};
shadows.SetCascades(sun.Direction, v);
for (int c = 0; c < shadows.CascadeCount(); ++c) {
    shadows.BeginRender(c);
    batch.RenderDepth(scene, shadows.LightMatrix(c));
}
shadows.EndRender(w, h);
// в цветном проходе — одним объектом, матрицы и текстуры вместе:
BindAndUploadShadows(shader, ShadowBinding(shadows, /*enabled=*/true));
```

Что стоит знать до включения:

* **Цена честная и линейная.** Проход глубины идёт по разу на каскад, то есть
  вся отбрасывающая тень геометрия рисуется N раз. Замерено профилировщиком на
  сцене Director 3D: 1.20 мс GPU на одной карте против 3.34 мс на трёх — ровно
  втрое, без сюрпризов. По умолчанию каскадов ТРИ: одна карта обязана
  растянуть свой тексель на всю `ShadowDistance`, и на улице это больше десяти
  сантиметров на тексель. Для помещения, где вся геометрия рядом, честный
  ответ по-прежнему 1 — три прохода дадут ту же картинку втрое дороже.
* **Границы считаются по описанной СФЕРЕ под-фрустума, а не по коробке.**
  Коробка меняет размер при повороте камеры, размер текселя скачет, и тени
  «кипят» просто от вращения мышью. Радиус сферы зависит только от дальностей и
  угла обзора.
* **Деление дальности — смесь логарифмического и равномерного** (λ ≈ 0.6).
  Чисто логарифмическое вырождает дальний каскад, чисто равномерное — ближний.
* **`ShadowDistance` — это не дальность камеры.** Тень у горизонта не видна, а
  разрешение на неё тратится.
* **В шейдере выбор каскада развёрнут вручную.** GLSL 330 запрещает
  индексировать массив сэмплеров переменной, а каскад выбирается на лету —
  цикл там физически невозможен.
* **На стыке каскадов тени смешиваются** в узкой полосе, иначе видна ступенька:
  слева тень подробная, справа грубая. Если следующего каскада в этой точке
  нет, остаётся значение своего: подмешать туда «нет тени» значило бы гасить
  тень полосой по всей границе каскада.
* **У предела дальности тень РАСТВОРЯЕТСЯ, а не обрывается.** Без этого граница
  карты видна как ровная линия поперёк земли — с одной стороны тени есть у
  всех, с другой ни у кого, и глаз читает это как ошибку рендера. Полоса
  растворения — последняя шестая часть `ShadowDistance`.
* **Ортобокс пускает в карту то, что стоит ВЫШЕ него по лучу** (`SetCasterRange`,
  по умолчанию 150 м). Мачта на восемнадцать метров выше накрытого куска земли
  всё равно бросает на него тень; без этого запаса её верхушка отсекается
  ближней плоскостью света, и тень обрывается посреди пола.
* **Карта едет за КАМЕРОЙ, а не стоит в начале мира.** `FitSingle` для одной
  карты, `SetCascades` для каскадов. Раньше вызывающие писали
  `SetLightMatrix(sun, {0,0,0}, 24)`, и всё, что игра успевала отойти от начала
  координат, оставалось без теней — молча, потому что это выглядит как «тени
  выключены», а не как ошибка.
* **В проходе глубины отсекаются ЗАДНИЕ грани, как везде.** Отсечение лицевых —
  известный приём против самозатенения, но платит за него картинка: тень
  отрывается от предмета на его толщину (куб стоит на полу, а тень лежит в
  метре от него), а односторонняя геометрия — плоскость, парус, лист — не
  попадает в карту вовсе и перестаёт отбрасывать тень. Самозатенение лечится
  при выборке: сдвигом вдоль нормали и наклонным bias'ом.

Проверка `TestShadowCascades` меряет две вещи, и обе нужны: что вдали тень
**есть** (это проверка выбора каскада) и что вблизи тексель мельче. Первая
версия проверяла только вторую половину — и проходила с намеренно сломанным
выбором каскада, то есть не проверяла главного. Нынешняя на той же поломке
показывает 29 пикселей дальней тени вместо 1283 и падает.


## Архитектура (ключевые решения)

| Слой | Что это | Где |
|---|---|---|
| **Application / Layer** | Движок владеет окном, главным циклом и таймингом; игра/редактор подключаются как слои (`OnAttach/OnUpdate/OnRender`). Точку входа даёт макрос `SAGE_MAIN`. | `sage/core/Application.h`, `Layer.h`, `GameModule.h` |
| **ECS (entt)** | Сцена — это `entt::registry`; сущности собираются из компонентов (`Name`, `Transform`, `MeshRenderer`, `Hierarchy` (родитель/дети), `Script`, ...). `GameObject` — дешёвый дескриптор поверх. Мировые матрицы — композицией по иерархии (`Scene::WorldMatrix`). Системы обходят сущности (`sage/ecs/RenderSystem.h`). | `sage/scene/Scene.h`, `Components.h`, `sage/ecs/` |
| **RHI (абстракция графики)** | Движок обращается не к OpenGL напрямую, а к интерфейсу `GraphicsDevice`. Реализация бэкенда (сейчас OpenGL) изолирована в `engine/src/rhi/opengl/`. Чтобы добавить Vulkan/D3D — реализуют интерфейс, код движка/игр не трогают. | `sage/rhi/GraphicsDevice.h`, `Resources.h`, `engine/src/rhi/opengl/` |
| **Скриптинг (Lua)** | Управление сущностями и логикой уровня из `.lua` без перекомпиляции. | `sage/scripting/ScriptEngine.*` |

Сборка даёт: библиотеку `sage::engine`, exe `Sandbox`, exe `TestGame` и exe
редактора `SageEditor`. Граница строгая и проверяемая: код движка нигде не включает
игровой код (см. `## Как разрабатывать движок и игру(ы) параллельно` ниже), а
`#include <glad/...>` на уровне устройства есть только в `engine/src/rhi/opengl/`.
Следующую игру можно собрать, слинковав ту же библиотеку и написав свой слой +
`CreateApplication`.

## Как сделать новую игру
```cmake
# games/mygame/CMakeLists.txt
sage_add_game(
    NAME MyGame
    SOURCES src/main.cpp src/MyGameLayer.cpp
    ASSETS  ${CMAKE_CURRENT_SOURCE_DIR}/assets
)
```
```cpp
// games/mygame/src/main.cpp
#include "sage/core/GameModule.h"
#include "MyGameLayer.h"
sage::Application* sage::CreateApplication(int, char**) {
    auto* app = new sage::Application({.Title = "My Game"});
    app->PushLayer(std::make_unique<MyGameLayer>());
    return app;
}
SAGE_MAIN()
```
Затем добавить `add_subdirectory(games/mygame)` в корневой CMakeLists. Игровой
слой наследует `sage::Layer` и работает с движковой `Scene` (ECS), рендером
через RHI-девайс и т.д. — именно так устроен `games/sandbox/src/SandboxLayer.*`,
самый простой рабочий пример, с которого можно скопировать структуру.

## games/sandbox — минимальный showcase движка
Это не игра, а нарочно упрощённый пример: плоскость-пол + три цветных куба
через ECS (`Scene::CreateObject`/`MeshRendererComponent`) + один куб со
`ScriptComponent` (крутится через `assets/scripts/spin.lua`, доказывая, что
скриптинг работает и вне редактора), авто-облёт камеры, один простой
шейдер с направленным светом (`assets/shaders/basic.*`). Никаких
теней/пост-процесса/аудио/UI — это подсистемы движка, которые игра включает
по мере необходимости (см. соответствующие разделы ниже), не обязательная
часть минимального примера.

`Sandbox` служит и референсом «как сделать игру», и запускаемой fixture для
headless smoke-тестов в CI (сама библиотека `sage_engine` не запускается —
нужен exe). Поддерживает те же env-хуки, что и `SageEditor`:
`SAGE_WINDOW_WIDTH`/`SAGE_WINDOW_HEIGHT`, `SAGE_SCREENSHOT_AT_FRAME`/
`SAGE_SCREENSHOT_PATH`.

## games/testgame — боевая игра-стресс-тест движка

Не игра ради игры, а полигон: маленький, но ПОЛНЫЙ игровой цикл, сознательно
нагружающий каждую подсистему движка (после удаления The Boat у многих из них
не оставалось ни одного реального потребителя — «компилируется» не значит
«работает»). Что внутри и что этим проверяется:

- **Игрок от первого лица** — `InputSystem` с именованными действиями
  (WASD/мышь/ESC) + **своя AABB-коллизия** со стенами в коде игры
  (`MovePlayer`): коллизии — забота игры, движок их не навязывает.
- **Две комнаты-сцены** (`SceneManager`) с переходом по пульсирующему
  порталу: реальная проверка мультисценового API и переноса состояния
  (здоровье игрока переезжает между комнатами).
- **Кастомные ECS-компоненты** (`src/GameComponents.h`: Health, Pickup,
  Patrol, StaticCollider, Portal) — навешиваются через
  `scene.Registry().emplace<T>()` и обходятся обычными entt-view в коде игры.
  Это ОФИЦИАЛЬНЫЙ паттерн расширения: движок не правится. (Ограничение:
  `SceneSerializer` кастомные компоненты не сохраняет — см. «Известные
  ограничения».)
- **Десятки Lua-скриптов одновременно** (монетки, маяки порталов) — стресс
  `ScriptEngine`; сериализация сцены проверяется round-trip-тестом на старте.
- **HUD движковым `UIRenderer`/`Widgets`** — health bar с динамическим
  источником значения, счёт, подсказки.
- **Аудио** (`AudioEngine`): эмбиент-луп + эффекты подбора/урона/портала; в
  headless CI тихо деградирует (нет устройства — no-op, не падает).
- **Модель `.obj` двумя путями**: ECS-энтити через `ResourceManager::GetModel`
  (комната 1) и прямой `Model::Load`+`Model::Draw` (монумент в комнате 2).
- **Тени** (`ShadowMap` + PCF) и **пост-процесс** (HDR `Framebuffer` +
  ACES-тон-маппинг) — первый реальный рендер-прогон обеих подсистем после
  RHI-миграции.

Env-хуки: общие `SAGE_SCREENSHOT_*`, плюс `SAGE_NO_SHADOWS`, `SAGE_NO_POST`,
`SAGE_TESTGAME_START_ROOM=room2` (старт в конкретной комнате для отладки) и
`SAGE_TESTGAME_AUTOPILOT=1` — бот сам собирает монеты и проходит портал; CI
гоняет его каждым коммитом и проверяет лог-маркеры `TESTGAME:` + отсутствие
ERROR-строк (см. `scripts/ci_smoke_test.sh`, тест 4/4).

Уже вскрытые этой игрой и починенные баги движка:
1. `Window` и `InputSystem` оба монопольно занимали GLFW user pointer окна —
   resize с активным вводом кастовал чужой указатель (UB). Теперь колбэками
   владеет `Window`, ввод подписывается через его хуки.
2. `Vec3(...)`/`Vec2(...)`/`Vec4(...)` нельзя было сконструировать из Lua
   (sol2 требует отдельной регистрации `call_constructor`) — ни один прежний
   скрипт векторы не создавал, поэтому баг жил незамеченным.

## The Boat — первая игра на движке (отдельный репозиторий)

[**The Boat**](https://github.com/AmckinatorStudios/The-Boat) — уютная воксельная
игра про жизнь на лодке посреди бесконечного океана. Живёт отдельно от движка и
лежит НЕ в `games/`, а в своём репозитории — как обычный проект редактора
(`project.sageproj` + `scenes/` + `assets/`). Это принципиально: `sandbox` и
`testgame` собираются вместе с движком и линкуют его как библиотеку, а The Boat
не содержит НИ СТРОЧКИ C++ — она открывается редактором, играется в Play и
собирается в exe кнопкой File → Build Game, как любая игра стороннего
разработчика.

Бесконечный океан с волнами, корабль как сетка блоков на качке, плавучий мусор
на настоящей физике движка, стройка, крафт, шкалы выживания и смена суток —
всё это Lua поверх обычной ECS: в движке нет ни одной строчки, знающей про воду,
лодки или блоки. Игра оказалась самой честной проверкой границы «движок / игра»
из всех — и первым потребителем, которому обычного скриптинга не хватило.

Что она заставила добавить в движок (подробности — в разделах «Скриптинг»,
«Физика» и «CI и smoke-тесты»):

- `require` и пути поиска модулей Lua — игра размером больше одного файла;
- `BindAction` из Lua — раскладка объявляется игрой, а не зашита в C++;
- `GetMouseDelta`/`SetMouseCaptured` и захват курсора в `Window` — вид от
  первого лица из скрипта;
- `LaunchArg`/`LaunchFlag` — зерно мира, время суток и автопрогон снаружи;
- привязку ввода, звука и модулей в рантайме И в Play-режиме редактора —
  раньше скрипты не получали ввод НИГДЕ, и игра на скриптах была невозможна;
- headless-сессию редактора над чужим проектом (`SAGE_EDITOR_OPEN_PROJECT`);
- **живой состав физического мира**: тела для сущностей, порождённых В РАНТАЙМЕ,
  и снятие тел за уничтоженными. Раньше `PhysicsScene` строил тела только в
  конструкторе — всё, что игра создавала после старта (плавучий мусор, обломки,
  брошенные предметы), физики не получало ВОВСЕ и молча: компонент на месте,
  тела нет. См. `PhysicsScene::SyncBodies` и `tests/test_physics.cpp`;
- **небо в API освещения** (`GetLighting().Skybox`) — без него цикл суток из
  скрипта выходил половинчатым: свет, туман и вода темнели к ночи, а купол неба
  оставался полуденно-синим.

И два бага, которые вскрылись только на ней:

1. **Мелкий текст терял штрихи букв.** Атлас шрифта печётся в 48px, а интерфейс
   рисует текст впятеро мельче; без мип-уровней прореживание выборки съедало
   тонкие вертикальные стойки — «П» выглядела как «Г», «К» теряла левую палку.
   Починено мип-уровнями атласа и разведением глифов (`render/Font.cpp`).
2. **Порог лога по умолчанию был `Trace`.** Игра, порождающая мир скриптом,
   писала по строке на каждый созданный блок — тысячи строк за загрузку, дороже
   самой загрузки. Умолчание поднято до `Debug`.

## Редактор SageEditor

### Что появилось в редакторе (и чего в нём не было)

Редактор был сырым в вещах, без которых им нельзя пользоваться каждый день.
Ниже — что именно чинилось и почему.

**Файловые диалоги.** КАЖДЫЙ путь вводился руками в текстовое поле: открыть
проект, сохранить сцену, собрать игру, выбрать модель, выбрать текстуру. Это не
неудобство, а неработоспособность — человек не помнит абсолютный путь к своей
модели, а ошибка в нём давала только строчку в консоли. Теперь рядом с каждым
путём есть «Обзор…», а сам диалог (`editor/src/FileBrowser.h`) умеет хлебные
крошки, быстрый доступ (домой/проект/диски), фильтр по расширению, поиск,
создание папки и режимы «открыть файл» / «сохранить как» / «выбрать папку».

Диалог свой, а не системный, намеренно: системный тянет по реализации на
платформу, на Linux ещё и зависимость от тулкита, а в headless-прогоне (CI,
автотесты редактора) не открывается вовсе.

**Свои модели наконец загружаются.** Сущность сцены держит один `Mesh`, и
грузился он через `LoadObj` — то есть поставить в сцену модель в glTF было
нельзя, а это формат, в который экспортирует Blender по умолчанию и в котором
лежит почти всё бесплатное. Класс `Model` формат понимал, но он не `Mesh` и в
ECS не подключён; выглядело это как «модели не грузятся вообще». Теперь
`ModelLoader::LoadMesh` понимает `.obj`, `.gltf` и `.glb`, у поля пути есть
«Обзор…» и «Из Assets», а три причины неудачи (нет файла / формат не
поддерживается / файл битый) звучат по-разному — человеку, у которого модель не
встала, нужна именно та, что случилась.

**Текстурные слоты.** Пять голых полей ввода, применявшихся по Enter, стали
слотами с превью: видно саму картинку, есть «Обзор…», «Из Assets» и «Очистить».
Пустой слот рисуется рамкой, а слот с путём, но без картинки — красным крестом:
«не назначено» и «назначено, но не загрузилось» — разные беды с разным лечением,
и раньше они выглядели одинаково.

**3D-превью материала.** Материал показывался квадратиком цвета albedo. По нему
нельзя понять ничего из того, ради чего материал и настраивают: металл или
диэлектрик, гладкий или матовый, как легла карта нормалей. Теперь это сфера под
фиксированным студийным светом, с окружением (без него металл в превью честно
чёрный — отражать ему нечего) и вращением мышью: блик читается только в
движении.

**Подтверждение опасных действий** — с галочкой «больше не спрашивать», и она
принципиальна. Диалог, который нельзя выключить, перестают читать: человек,
удаляющий двадцать объектов подряд, жмёт «Да» вслепую. Ответ запоминается ПО
ВИДУ действия, а не один на всё. В вопросе показывается, сколько сущностей
уйдёт ВМЕСТЕ С ПОТОМКАМИ — выделив одну строку в иерархии, редко помнишь,
сколько под ней. Кнопка подтверждения не является кнопкой по умолчанию: Enter
отменяет.

**Мультивьюпорт.** Раскладки «один вид», «два столбца» и «четыре вида»; виды —
перспектива, сверху, спереди, сбоку. Ортогональные виды нужны затем, что в
перспективе не проверить, ровно ли стоит объект: у неё нет прямых углов. У
каждого вида свой буфер (иначе виден был бы только последний), панорама средней
кнопкой и масштаб колесом. Активный вид обведён рамкой — в четырёх одинаковых
серых прямоугольниках иначе не понять, где что. Гизмо живёт только в активном
виде: два гизмо — это два разных ответа на вопрос «куда я тащу».

**Встроенный редактор кода** (`Window → Код`, или двойной клик по `.lua` /
`.vert` / `.frag` в Assets). Движок умеет перечитывать скрипты и шейдеры на
лету, и вся ценность этого терялась, потому что «на лету» упиралось в alt-tab.
Подсветка Lua и GLSL, номера строк, поиск, переход к строке, отмена, Ctrl+S,
автоотступ, UTF-8 при вводе. Позиция каждого куска текста считается измерением,
а не «номер символа × ширина буквы»: шрифт интерфейса пропорциональный, и
арифметика по индексу разъезжает строку тем сильнее, чем она длиннее.

Чего в редакторе кода нет и не будет: автодополнения по типам, рефакторингов,
отладчика — это работа языкового сервера, а не редактора сцены.

Полноценный редактор сцен на ImGui (docking + multi-viewport) + ImGuizmo.

**Архитектура (v3, модульная)**: ядро `EditorLayer` (сцена/проект/Play/undo/
рендер превью) реализует контракт `EditorHost` (`editor/src/EditorHost.h`), а
каждая панель — независимый класс в `editor/src/panels/` со СВОИМ
UI-состоянием, зависящий только от контракта: Hierarchy, Inspector, Viewport,
Game, Console, Assets, Launcher. Новая панель = новый файл + вызов `Draw()` в
кадре — в ядро врастать не нужно. Тема — `EditorTheme` (единая палитра/метрики).

- **Доккинг + отдельные окна**: раскладка по умолчанию строится автоматически
  (Hierarchy слева, Inspector/Lighting справа, Console/Assets табами снизу,
  Viewport+Game табами в центре); панели свободно перетаскиваются, стыкуются и
  **вытаскиваются в отдельные OS-окна** (multi-viewport), раскладка
  сохраняется между запусками (`sage_editor_imgui.ini`), Window > Reset Layout
  возвращает дефолт.
- **Тулбар** — полоса под меню-баром (не оверлей во вьюпорте): слева режим
  гизмо (Move/Rotate/Scale), snap, пространство (Local/World); по центру
  Play/Pause/Stop; справа режим рендера и сетка. Внизу — статус-бар: проект |
  сцена (+`*` при несохранённых правках — он же в заголовке OS-окна) |
  сущности | Play-статус | сообщения плагинов | FPS.
- **Иконки** (`editor/src/EditorIcons.h`) — рисуются, а не загружаются.
  У ImGui иконок нет вообще, и обычный путь — подмешать шрифт вроде Font
  Awesome, то есть добавить в репозиторий бинарник со своей лицензией и
  таблицей кодов, а потом расставлять по коду непечатаемые символы. Здесь
  вместо этого десяток примитивов в `ImDrawList`: ни файла, ни лицензии, ни
  магических констант, и иконка одинаково резка при любом масштабе интерфейса.
  Тулбар с тремя подписанными кнопками гизмо съедал треть полосы — форма
  стрелки, дуги и рамки читается быстрее слова, а горячая клавиша ушла в
  подсказку. В иерархии иконка отвечает на вопрос «что это»: в списке из
  полусотни `Object` глазу зацепиться не за что, а «свет / камера / зонд /
  модель» видно сразу.
- **Консоль**: фильтры по уровню, поиск по тексту и категории, счётчики,
  свёртка повторов, копирование (всего видимого — кнопкой, одной строки —
  правым кликом). Раньше это был список строк без фильтров, и в этом была
  практическая беда: единственное предупреждение о непрочитанном шейдере
  тонуло среди тысяч сообщений загрузки, а именно оно и объясняло, почему
  сцена выглядит не так. Один кадр умеет выдать одно и то же предупреждение
  тысячу раз (шейдер не собрался — и так на каждый объект), поэтому повторы
  сворачиваются в `(xN)`.
- **Ошибки видны, не открывая консоль**: счётчик в статус-баре подсвечен и
  кликабелен. Консоль легко держать свёрнутой, и тогда ошибка остаётся
  незамеченной, а сцена «просто выглядит не так».
- **Готовность к падению** (`sage/core/CrashHandler.h`). До этого падение
  выглядело так: окно исчезло. Ни файла, ни строки, ни намёка — и вместе с
  окном исчезала несохранённая сцена. Теперь при падении пишется отчёт
  (`sage-crash-*.txt`): причина, стек вызовов, версия, открытый проект и сцена,
  последние сорок строк лога. Ловятся оба вида отказа — сигнал (SIGSEGV и
  соседи) и необработанное исключение через `std::terminate`; поймать один и
  пропустить другой значит пропустить половину.

  Работать в этот момент можно почти ничем: куча могла быть повреждена, и любой
  `malloc` способен повиснуть навсегда вместо того, чтобы упасть. Поэтому
  буфер последних строк лога — кольцевой и выделен ЗАРАНЕЕ, запись идёт
  низкоуровневым `write`, а обработчик снимает себя первой же строкой, чтобы
  второй сигнал не закрутил рекурсию. Падение при этом остаётся падением:
  обработчик добивает процесс тем же сигналом — иначе его не увидят ни
  отладчик, ни системный сборщик отчётов, а код возврата соврал бы сборке.
- **Автосохранение и восстановление**: раз в минуту сцена с несохранёнными
  правками пишется в `sage-autosave.sage`, а при падении — в
  `sage-recovered.sage`. Оба — ОТДЕЛЬНЫЕ файлы, не поверх рабочей сцены:
  страховка, затирающая оригинал, страховкой не является, а записать поверх
  сцены данные из уже сломанного процесса — худший исход. При следующем
  запуске редактор предлагает открыть копию (модалкой, а не тихой загрузкой:
  восстановленная сцена может быть не той, над которой человек работал). Чистое
  завершение снимает файл автосохранения — это и есть доказательство, что
  падения не было.
- **Режимы рендера вьюпорта** (тулбар / env `SAGE_EDITOR_RENDER_MODE`):
  **Shaded** (полное освещение), **Wireframe** (каркас — движковый
  `PolygonMode::Line`), **Unlit** (плоский цвет), **Normals** (визуализация
  нормалей). Игровое окно (Game) всегда Shaded.
- **Гизмо и выделение**: выбранная сущность обведена **аутлайном**
  (масштабированная оболочка) + оси; **невидимые сущности видны и кликабельны**
  — у камеры рисуется каркас пирамиды видимости (frustum), у света — маркер и
  зона действия (сфера/конус). Клик по гизмо камеры/света выбирает сущность.
  Сетка вьюпорта — 3D-линии `DebugDraw` (заслоняются геометрией).
- **Иерархия родитель/ребёнок**: панель Hierarchy — ДЕРЕВО сущностей. Родитель
  задаётся **перетаскиванием** одной сущности на другую (drag-drop), открепление
  в корень — перетаскиванием в пустую зону внизу или ПКМ > Unparent; ПКМ >
  **Create Child** создаёт вложенную сущность. Мировая матрица ребёнка =
  `WorldMatrix(родитель) * локальная` (`sage::Scene::WorldMatrix`, композиция по
  цепочке) — двигаешь/поворачиваешь/масштабируешь родителя, дети следуют.
  Гизмо выбранной сущности работает в мировом пространстве и переводит результат
  обратно в локальную относительно родителя. Удаление узла удаляет всё поддерево;
  циклы (сделать родителем своего потомка) отклоняются. Связи сериализуются в
  `.sage` (поле `parent` по стабильному id, восстанавливается после загрузки всех).
- **Add/Remove компонентов**: у выбранной сущности показываются секции ТОЛЬКО
  присутствующих компонентов (каждая — с кнопкой Remove), а кнопка **Add
  Component** открывает попап со списком отсутствующих (Camera / Light / Script /
  Rigid Body / Collider / Animated Model / Particle Emitter). Каждое добавление/
  удаление пишется в undo. Transform и Mesh Renderer — базовые, не снимаются.
- **Игровое окно (Game)**: рендер сцены от ИГРОВОЙ камеры — первой сущности с
  `CameraComponent.Primary` (движковый компонент, сериализуется в `.sage`;
  Inspector > Camera — Add/Remove, FOV/Near/Far/Primary). При нажатии Play таб
  Game автоматически выходит на передний план — редактируешь в Viewport,
  играешь в Game. Демо-сцена сразу содержит Main Camera.
- **Стартовый Project Launcher**: пока проект не открыт — окно с недавними
  проектами (хранятся в `~/.config/sage/recent_projects.json`), формой
  создания нового и открытием по пути; открытие проекта автоматически грузит
  его первую сцену. File > Project Launcher... открывает hub повторно; File >
  Project Scenes — быстрый доступ ко всем сценам открытого проекта.
- **Полное освещение в редакторе (PBR)**: Viewport и Game рендерятся физически-
  корректным (metallic-roughness, Cook-Torrance GGX) forward-шейдером движка.
  Единый GLSL-блок освещения (`PbrShader.h`, `kPbrSharedGlsl`) встроен во ВСЕ
  пути — инстансный статический, текстурный (нормал-маппинг) и скиннинг — так
  статика, текстурированные и анимированные меши освещаются одинаково. Все
  стандартные типы света для forward-рендера:
  - **Ambient** (полусферический): SkyColor тонирует верхние грани, GroundColor
    — нижние (не плоская засветка). **Если включён скайбокс — засветка берётся
    ИЗ НЕГО** (верх тянется к цвету зенита/неба, низ — к приглушённому горизонту),
    так что освещение согласовано с видимым небом (см. `LightingEnvironment::
    ResolveAmbient`).
  - **Directional** («солнце»): один на сцену, отбрасывает **PCF-тени** (общий
    shadow-проход на кадр). Тени — только от солнца.
  - **Point** (точечный): лампа/факел, светит во все стороны, затухание из Range.
  - **Spot** (прожектор): конусный свет вдоль «вперёд» сущности (-Z её поворота),
    внутренний/внешний угол для мягкого края — фонарик, лампа-спот.

  Ambient и солнце — окружение сцены (панель **Lighting**, сериализуются, с undo).
  Точечные света и прожекторы — СУЩНОСТИ с движковым `LightComponent`
  (`Type` Point/Spot, Color/Intensity/Range + Inner/OuterCone у spot; позиция и
  направление из Transform — двигаются гизмо и скриптами): Entity > Create Light,
  секция Light в Inspector (переключение типа), у выбранного света рисуется зона
  действия (сфера радиуса — point, конус — spot). Итоговое освещение кадра
  собирает `sage::ecs::CollectLighting` (окружение + света-сущности, лимит
  шейдера — 8 точечных + 8 прожекторов).
- **Атмосфера сцены** (панель Lighting, сериализуется): **скайбокс** —
  процедурный градиент неба (`SkyRenderer`, зенит → горизонт, без ассетов) и
  **линейный туман** (цвет + start/end, применяется в Shaded). Оба поля —
  часть окружения сцены, работают и в редакторе, и в собранной игре.
- **Примитивы**: движок генерирует Cube/Sphere/Plane/Cylinder/Cone
  (`Mesh::Create*`, с нормалями и UV; кэш `ResourceManager::GetPrimitive`).
  Entity > Create Primitive, выбор в Inspector (Mesh), сериализация в `.sage`.
- **Сборка игры (File > Build Game...)**: упаковывает открытый проект в
  ЗАПУСКАЕМУЮ игру — папка `<out>/<Имя>/` с копией рантайма `SagePlayer`
  (переименован в имя проекта), его шейдерами и `project/` (сцены/ассеты).
  Собранная игра самодостаточна: запускается двойным кликом, без движка и
  редактора. Проверяется smoke-тестом 5/5 в CI — собранная self-test-игра
  реально запускается headless.
- **Гизмо** (ImGuizmo): перемещение/поворот/масштаб выбранной сущности прямо во
  вьюпорте. Горячие клавиши **W/E/R**, **T** — универсальное, **Y** — рамка
  (Rect). Рамка отвечает на другой вопрос, чем масштаб: масштаб тянет объект ОТ
  ЦЕНТРА и одинаково в обе стороны, рамка тянет ОДНУ ГРАНЬ, оставляя
  противоположную на месте (подогнать стену к проёму масштабом — это попасть
  сразу двумя краями, рамкой — одним). Ручки сидят на настоящих габаритах меша.
  Это ОДИН инструмент, а не два поверх друг друга: перемещение в нём оставлено
  ровно центральным кружком (перетаскивание в плоскости экрана), а стрелки и
  квадраты плоскостей погашены маской осей — иначе полный гизмо перемещения
  рисовался бы ровно там же, где рамка, и попасть по её углу, не задев стрелку,
  было делом везения. Растягивание рамкой отменяется через Ctrl+Z, как и всё
  остальное. Привязка к сетке — галка Snap. Выбранная
  сущность дополнительно подсвечивается каркасом и осями X/Y/Z, а сетка-
  ориентир рисуется движковым `DebugDraw` (3D-линии С ТЕСТОМ ГЛУБИНЫ — объекты
  сцены её заслоняют; раньше сетка была 2D-оверлеем и просвечивала сквозь всё).
- **Камера вьюпорта**: ПКМ — осмотреться, ПКМ+WASD (Q/E — вниз/вверх, Shift —
  быстрее) — полёт, колесо — наезд.
- **Пикинг**: клик ЛКМ по объекту выбирает его (луч в ECS-сцену), клик в пустоту
  снимает выбор.
- **Проекты**: File > New Project создаёт `<папка>/<имя>/` с `project.sageproj`,
  `scenes/` и `assets/`; Open Project открывает существующий. Сцены сохраняются
  в `scenes/` проекта (`.sage` JSON) и открываются двойным кликом в Assets.
- **Панели**: Hierarchy (создание/дублирование/удаление сущностей, контекстное
  меню), Inspector (имя, Transform, цвет, выбор меша Cube/Model, материал,
  скрипт), Console (живой лог движка с цветами уровней), Assets (сетка цветных
  тайлов по типу файла — папка/сцена/материал/скрипт/меш/текстура/аудио/шейдер —
  с breadcrumb, поиском по имени и rename/delete через ПКМ; двойной клик по
  `.sage` грузит сцену). ПКМ по пустому месту Assets создаёт ассеты: **New
  Folder / New Script (.lua с шаблоном OnStart/OnUpdate) / New Text File /
  New Material (.sagemat)**.
- **Материалы (PBR)**: `.sagemat` (JSON: albedo/emissive/**metallic/roughness**/
  **texture (albedo)**/**normalMap**/**metallicMap**/**roughnessMap**/**aoMap**/
  shininess-legacy) — переиспользуемое описание внешнего вида в metallic-roughness
  workflow. Скалярные факторы metallic/roughness применяются всегда; если задана
  карта — её значение (R-канал) умножается на фактор (glTF-семантика). Normal —
  tangent-space (OpenGL, зелёный вверх); AO множит непрямой (ambient) свет. Клик
  по `.sagemat` в Assets открывает его редактор в Inspector (слайдеры Metallic/
  Roughness, поля Albedo/Normal/Metallic/Roughness/AO Map; правки видны на всех
  сущностях с этим материалом сразу — экземпляр разделяемый, Save пишет на диск);
  у выбранной сущности секция Material — Assign/Clear. Материал с назначенными
  картами рисуется отдельным текстурным PBR-путём (TBN, нормал-маппинг + все
  карты); без карт — быстрым инстансным путём с metallic/roughness из материала.
  `games/testgame` умеет собрать материал из целого PBR-сета на диске (env
  `SAGE_TESTGAME_PBR_DIR` — карты ищутся по ключевым словам в именах файлов),
  чтобы протестить движок на реальном материале без коммита тяжёлых текстур.
  Путь материала сохраняется в `.sage` и восстанавливается при загрузке.
- **Свои ассеты вносятся в проект, а не подключаются «где лежат»**: кнопка
  **Импорт…** в панели Assets копирует выбранный файл в текущую папку проекта
  ВМЕСТЕ СО СПУТНИКАМИ — у `.obj` это `.mtl` и все его текстуры, у `.gltf` —
  `.bin` с геометрией и картинки; чего не нашлось, попадает в отчёт, а не
  теряется молча. Ссылки на ассеты пишутся в сцену ОТНОСИТЕЛЬНО корня проекта
  (`Project::AssetRef`): абсолютный путь работал в редакторе на этой машине и
  нигде больше — собранная игра делает `chdir` в свою папку и такого пути не
  находит. Инспектор помечает ссылку на файл вне проекта как непереносимую
  сразу, а не после сборки.
- **Модель приезжает со своим материалом.** `.gltf`/`.glb`/`.obj` несут PBR-
  материал рядом с геометрией, и до сих пор он выбрасывался — в сцену вставала
  белая болванка. Теперь при загрузке модели рядом с ней создаётся `.sagemat` с
  её факторами и картами и назначается сущности (уже существующий файл не
  перезаписывается — правки после импорта переживают повторное «Загрузить»).
  Упакованные каналы glTF раскладываются в отдельные карты: движок читает
  metallic и roughness из R-канала своих текстур, а glTF держит occlusion в R,
  roughness в G и metallic в B ОДНОЙ — отдать её как есть значило бы взять
  металличность оттуда, где лежит затенение. См. `sage/render/ModelMaterial.h`.
- **Mesh Renderer — одна секция, а не две.** Порядок повторяет структуру
  компонента: **Меш** (источник: примитив или файл модели) → **Материал**
  (слот с превью-шариком, назначение из Assets/диалогом/перетаскиванием) →
  **Поправки экземпляра** (тон, свечение, непрозрачность). Раньше материал был
  отдельным заголовком, будто это другой компонент, и противоречил соседу:
  сверху стоял Color, а назначенный материал молча его отменял. Теперь правило
  наложения ОДНО на все три поправки — они МОДУЛИРУЮТ материал (цвет и
  прозрачность множатся, свечение прибавляется), и нейтральные значения дают
  ровно то, что записано в материале. Старые сцены переводит миграция формата
  v3→v4: у сущности с материалом мёртвый цвет заменяется нейтральным, поэтому
  вид уже сделанной сцены не меняется.
- **Play-режим**: кнопка Play в тулбаре вьюпорта (или меню Play). При входе
  сцена снапшотится, к сущностям со Script-компонентом привязываются их `.lua`
  (`OnStart`/`OnUpdate` — тот же ScriptEngine, что в играх) и тикают каждый
  кадр; Pause замораживает, Stop откатывает сцену ровно к состоянию до Play.
  Скрипт назначается в Inspector (секция Script, пример: `assets/scripts/spin.lua`).
  Состав кадра на время Play регистрируется в том же `RegisterCoreSystems`, что
  и у собранной игры, — скрипты, физика, анимация, частицы, звук в одном
  порядке. Это не украшение: без регистрации `AttachScript` честно вызывал
  `OnStart` (и в консоли появлялось «spin.lua attached to: …»), а `OnUpdate` не
  звал никто и физика не считала ни шага — Play выглядел запущенным и не был им.
  Ловится это только прогоном НАСТОЯЩЕГО кадра, поэтому self-test редактора
  тикает Play через планировщик, а не вызовом `ScriptEngine::UpdateAll` напрямую.
- **Undo/Redo** (Ctrl+Z / Ctrl+Y, меню Edit): откатывает создание/удаление/
  дублирование сущностей, перетаскивания гизмо и правки в Inspector (одна
  запись на завершённое перетаскивание/правку). До 100 шагов истории.
- **Инструменты вьюпорта.** Всё это делалось правкой чисел в инспекторе —
  арифметика в уме и несколько попыток на каждую операцию:
  **F** — показать выделенное в кадре (камера подводится по настоящим
  габаритам); **End** — опустить выделенное на первую поверхность под ним
  (объект встаёт НИЗОМ габаритной коробки на точку попадания, а не центром, и
  не опирается на других выделенных); выравнивание нескольких выделенных по оси
  относительно первичного; **T** — универсальное гизмо (перенос + поворот +
  масштаб разом); переключатель показа габаритов выделенного — той самой
  коробки, по которой считается попадание мышью.
  **Шаг привязки** вынесен в тулбар и разделён по режимам (перенос / поворот /
  масштаб). Он был зашит константой 0.5, а движок строит примитивы размером в
  единицу: половина построек из блоков вставала со сдвигом на полблока. Шаг
  переноса по умолчанию — 1.0.
- **Inspector — вкладки «Объект» и «Ассет».** Панель складывала в одну простыню
  два РАЗНЫХ предмета правки: сверху материал, выбранный в Assets, снизу
  свойства выбранной сущности, между ними голая черта. Читалось как один список
  свойств одного объекта — при том что область действия у них разная: файл
  материала общий для всех, кто им покрашен, а Transform принадлежит одной
  сущности. Вкладка следует за последним выбором, а заголовок прямо называет,
  что правится и на кого подействует.
- Горячие клавиши: Ctrl+S — сохранить сцену, Ctrl+D — дублировать, Del — удалить,
  Ctrl+Z/Ctrl+Y (или Ctrl+Shift+Z) — undo/redo, W/E/R/T — режим гизмо,
  F — показать в кадре, End — опустить на поверхность.
- CI-хуки: `SAGE_SCREENSHOT_AT_FRAME`/`SAGE_SCREENSHOT_PATH` — авто-скриншот,
  `SAGE_EDITOR_SELFTEST=1` — headless-проверка «проект + сцена + undo/redo +
  Play» (пишет `SELFTEST: PASS/FAIL` в лог), `SAGE_EDITOR_AUTOPLAY=1` —
  авто-вход в Play при старте (для визуальных проверок).

## Производительность: отсечение по фрустуму + инстансный батчинг
Статические меши сцены рисуются через `sage::ecs::RenderBatch`
(`engine/src/sage/ecs/RenderBatch.*`) — так стоимость кадра зависит от ВИДИМЫХ
объектов и числа РАЗНЫХ мешей, а не от общего числа сущностей:

- **Отсечение по фрустуму.** Из матрицы `proj*view` извлекаются 6 плоскостей
  (`sage/render/Frustum.h`, метод Gribb–Hartmann); у каждого меша есть локальная
  ограничивающая сфера (`Mesh::BoundsCenter/BoundsRadius`, считается при
  создании), переводимая в мир по `Transform`. Сущности, чья сфера целиком вне
  фрустума, не рисуются. В depth-проходе теней отсечение идёт по фрустуму СВЕТА.
- **Инстансный батчинг.** Видимые сущности группируются по мешу и рисуются
  ОДНИМ инстансным вызовом на группу: `Mesh` несёт per-instance поток (модельная
  матрица + цвет + metallic/roughness, loc 4..10; per-vertex — position/normal/
  uv/**tangent**, loc 0..3), заливаемый раз в кадр, и `DrawInstances` →
  `glDrawElementsInstanced`. N одинаковых кубов = 1 draw call вместо N.

Освещение инстансного прохода — тот же общий PBR-блок (`kPbrSharedGlsl`,
Cook-Torrance), что и у текстурного/скиннинг-путей (ambient/солнце с тенями/
точечные/прожекторы/туман). Подключено в редакторе (Viewport и Game),
`SagePlayer` и `games/testgame`. Статистика (`RenderStats`: нарисовано/отсечено/
батчей) видна в статус-баре редактора; в testgame есть стресс-хук
`SAGE_TESTGAME_STRESS=N` (рассыпает N×N кубов — почти все отсекаются/батчатся).
Корректность отсечения и согласованность батч-статистики проверяются
editor self-test'ом.

### Сглаживание кромок

Два разных механизма, и путать их нельзя — они решают задачу на разных этапах.

**MSAA** (`RenderTargetDesc::Samples`, настройка `SceneMsaa`, по умолчанию 4) —
растеризатор считает ПОКРЫТИЕ пикселя геометрией по нескольким точкам и
смешивает по нему. Работает пока информация ещё есть, поэтому кромка любого
наклона получает честные промежуточные значения. Включается только у буферов
сцены: у промежуточных буферов пост-эффектов геометрии нет, а глубину карты
теней усреднять нельзя — среднее двух глубин не является глубиной ничего.

Рисование идёт в многосэмпловый буфер, а наружу отдаются обычные текстуры:
многосэмпловую `sampler2D` не берёт, а весь пост-процесс написан под него.
Перенос — явным вызовом `Framebuffer::Resolve()` после всей отрисовки в буфер,
а не внутри `ColorTexture()`: он стоит полного копирования кадра, и прятать его
в геттер значило бы платить за него по нескольку раз за проход.

**FXAA** — экранный фильтр ПОСЛЕ тон-маппинга: ищет перепад яркости в готовой
картинке и замывает его. Дешевле MSAA и ловит то, что тот не видит в принципе
(кромки, созданные шейдером, а не геометрией), но на пологой кромке — горизонт,
длинная грань пола — догадаться о геометрии не по чему, и лесенка остаётся.
Механизмы дополняют друг друга и включены оба.

**Накопительный сверхсэмплинг** (в экспорте Director 3D) — кадр снимается
несколько раз с микросдвигом проекции и усредняется. Дороже обоих во столько
раз, сколько выборок, зато убирает и мерцание тонких деталей, и шум шейдеров,
чего не умеет ни MSAA, ни FXAA.

## Стриминг текстур и бюджет видеопамяти

Что было **до** этой работы (и о чём стоит сказать прямо, потому что «стриминга
нет» — не совсем верно): асинхронная загрузка уже работала. `GetTextureAsync`
возвращает объект мгновенно (заглушка 1×1), файл декодируется в фоновом потоке,
`PumpAsyncUploads` подменяет пиксели на главном потоке. Плюс бюджет VRAM и
LRU-вытеснение.

**Чего не хватало.** Вытеснение бессильно, когда все текстуры кому-то нужны:
выгрузить их нельзя — это висячая ссылка у материала, — и бюджет просто молча
превышался. То есть настройка «бюджет видеопамяти» не работала ровно в том
случае, ради которого её заводили: в тяжёлой сцене.

**Стриминг мип-уровней** закрывает эту дыру. Когда вытеснять нечего, текстуры
понижаются в разрешении вдвое: объект `Texture` остаётся жив, у держателей
ничего не рвётся, меняется только картинка внутри. Слегка размытая текстура
лучше вылета по памяти.

* **Кого понижать — по давности обращения** (LRU), как и при вытеснении: то, на
  что смотрят сейчас, трогается последним.
* **Ниже 64 пикселей не опускаемся** — дальше экономия копеечная, а текстура
  превращается в кашу.
* **Уменьшение — усреднением 2×2**, а не выбрасыванием каждого второго пикселя.
  Прореживание вдвое дешевле и даёт алиасинг: тонкие линии то появляются, то
  исчезают при движении. Здесь это особенно важно, потому что понижение
  применяется к УЖЕ ВИДИМЫМ текстурам.
* **Пиксели читаются заново с диска.** Держать их копию в оперативной памяти
  ради возможного понижения значило бы экономить видеопамять за счёт обычной.

Политика памяти вынесена в чистые функции (`SelectDowngrades`, `DownscaleRGBA`)
и проверяется юнит-тестами без GL: за поведением памяти нельзя следить
наблюдением за игрой. Тест на выбор кандидатов падает, если убрать сортировку
по давности — проверено.

**Чего по-прежнему нет:** сжатия текстур (BC/ASTC) и стриминга самой геометрии.
Оба относятся к пайплайну ресурсов и делаются вместе с ним.

## Отсечение перекрытием (occlusion culling)

Фрустум отсекает то, что вне поля зрения. Он ничего не знает о том, что стена
закрывает собой полгорода: вся эта геометрия остаётся «видимой» и честно
рисуется в пиксели, которые тут же перезаписываются. В помещениях и плотной
застройке это самая большая потеря из всех.

**Как сделано.** После цветного прохода, когда буфер глубины кадра уже
заполнен, рисуются коробки-заменители кандидатов — только глубина, без цвета, —
каждая внутри запроса перекрытия (`GL_ANY_SAMPLES_PASSED`). Результат читается
**в следующем кадре**, и по нему решается, рисовать ли объект.

```cpp
batch.SetOcclusionCulling(cfg.OcclusionCulling);
batch.RenderColor(scene, view, proj, viewPos, env, shadows, 0);
batch.RenderOcclusionProbes(proj * view, viewPos); // результат — следующему кадру
```

**Почему не иерархия буфера глубины.** Она точнее и не требует запросов, но без
вычислительных шейдеров (их нет в GL 3.3) строить пирамиду пришлось бы
фрагментными проходами, а читать результат — на CPU, то есть с остановкой
конвейера. Запросы дают тот же ответ без остановки.

**Чем за это платим, и это надо знать заранее:**

* **Задержка в кадр.** При резком повороте камеры объект, который был закрыт, а
  стал видимым, появится кадром позже. На 60 кадрах это 16 мс.
* **Ответ консервативен в одну сторону.** Объект без готового результата
  считается видимым; коробка больше объекта, поэтому «коробка видна» не значит
  «объект виден». Ошибиться можно только в сторону «нарисовали лишнее».
* **Камера внутри объекта — особый случай, и он не мелкий.** Коробка, накрывшая
  камеру, обрезается ближней плоскостью, ни один пиксель не проходит, и объект
  объявляется закрытым. На стене — главном перекрывателе сцены — это означало
  катастрофу: стена исчезала, буфер глубины оставался пустым, и следующим кадром
  «видимым» становилось всё подряд. Картинка моргала целиком. Такие объекты
  считаются видимыми без запроса.
* **Закрытые перепроверяются раз в четыре кадра.** Иначе объект, однажды
  признанный закрытым, не вернулся бы никогда, а стена может уехать.

Выключено по умолчанию (`OcclusionCulling`): окупается в помещениях и плотной
застройке, а на открытой сцене только добавляет проход коробок.

Измерено (`TestOcclusionCulling`, стена + 40 объектов за ней + 3 перед ней):

| | без проверки | с проверкой |
|---|---|---|
| нарисовано объектов | 44 | **4** |
| признано закрытыми | 0 | 40 |
| изменение кадра | — | **0.000 %** |

Проверка «кадр не изменился» здесь не украшение, а вторая половина смысла:
«отсекает всё» — это не оптимизация, а пропавшая геометрия. Первая версия этой
проверки была слепой — единственным видимым объектом оставалась стена, а она
освобождена от запросов, и тест проходил, даже если объявить закрытым вообще
всё. Кубы перед стеной добавлены именно поэтому: с ними та же поломка даёт
14 % изменившихся пикселей и падение.

## Готовые проходы сцены (ScenePasses)

Проход глубины для карты теней существовал в **четырёх копиях**: рантайм-плеер,
игра-стресс-тест, редактор и Director 3D. Копии были почти одинаковы — «почти»
и есть проблема.

Это не эстетическая претензия, а описание уже случившегося. Когда в движок
добавили **каскадные тени**, цикл по каскадам пришлось вписывать в каждую копию
отдельно; три обновились, редактор остался с однокарточным вариантом. Когда
добавили **отсечение перекрытием**, вызов `RenderOcclusionProbes` попал ровно в
одного потребителя из четырёх — остальные три о нём не знали.

Теперь последовательность записана один раз:

```cpp
sage::render::RenderShadowDepth(shadows, scene, batch, w, h);       // все каскады
sage::render::SceneColorInput color;
color.View = view; color.Proj = proj; color.ViewPos = eye; color.Env = &env;
color.Shadows = ShadowBinding(shadows, true);
color.OcclusionCulling = cfg.OcclusionCulling;
sage::render::RenderSceneColor(scene, batch, color);
```

* То, что у потребителей действительно разное (у игры — своя ручная геометрия
  помимо ECS), передаётся **обработчиком**, а не копированием всего прохода
  ради одной строки.
* **Частицы намеренно не входят** в общий проход: система частиц у каждого
  своя (у редактора превью, у игры боевая), и владеть ею проход не может.
* Границы теней тоже остаются снаружи: откуда их брать — решение потребителя,
  оно зависит от камеры и сцены, и прятать его внутрь значило бы навязать одну
  политику всем.

Итог правки: −50 строк дублирования, число мест, которые нужно изменить, чтобы
добавить в проход сцены новую возможность, — **с четырёх до одного**. Поведение
не изменилось: 70 эталонных кадров сравниваются попиксельно и прошли без правок.

## Граф кадра

Порядок проходов раньше был зашит в тело функции в Director 3D. Это не граф:
порядок нельзя было изменить, не переписав функцию; зависимости между проходами
существовали только в голове у автора; выключенный проход всё равно приходилось
помнить и пропускать руками.

`sage/render/FrameGraph.h` делает проход **данными**: имя, что он читает, что
пишет, что делать с вложениями на входе и на выходе, и тело.

**Где он работает.** Кадр рантайма (`SagePlayer`) описан именно так: отражения
окружения, тени, зеркальный проход и главный проход сцены объявляются с их
чтениями и записями, после чего граф проверяет описание и выполняет его. Долгое
время граф существовал, был покрыт тестами и **не использовался ни одним
рендерером** — то есть был мёртвым кодом, что хуже отсутствия: тест зелёный, а в
продукте функция не участвует.

Что это даёт уже сегодня, а не в будущем на Vulkan:

* **Проход, результат которого никому не нужен, не выполняется.** Раньше это
  были ручные `if` перед каждым захватом; теперь условие живёт в описании кадра.
  Выключи отражения — и из четырёх проходов остаются два, без единой правки в
  коде.
* **Описание проверяется до отрисовки.** Прочитать то, во что никто не писал, —
  ошибка кадра, и находится она сообщением, а не чёрным экраном.
* **`Describe()` отвечает, что и почему было в кадре.** Рантайм печатает состав
  при каждой его смене:

```
Состав кадра: 2 из 4 проходов (отброшено 0, выключено 2)
  1. Тени: глубина от солнца (цвет: загрузить, глубина: загрузить)
       пишет  ShadowMap
  2. Сцена: освещение, тени, отражения (цвет: очистить, глубина: загрузить)
       читает ShadowMap
       пишет  Screen
```

```cpp
FrameGraph fg;
const auto hdr = fg.DeclareResource("HDR");
const auto out = fg.DeclareResource("Выход");

RenderPassDesc sky;
sky.Name = "Небо";
sky.Writes = {hdr};
sky.ColorLoad = LoadOp::Clear;
sky.Execute = [&] { DrawSky(); };
fg.AddPass(std::move(sky));
// ...
std::string err;
if (fg.Compile(out, err)) fg.Execute(); else LOG_ERROR("Кадр") << err;
```

**Версии ресурсов — суть модели, и без них ничего не работает.** Небо,
геометрия, сетка и служебная графика все читают HDR-буфер и все в него пишут.
Наивная модель «читатель зависит от всех писателей» объявляет их взаимно
зависимыми, и кадр не собирается вовсе — ровно это и произошло при первом
запуске. Правильно: каждая запись создаёт новую версию ресурса, а чтение
относится к версии, существовавшей на момент объявления прохода.

**Чего этот граф не делает — и это надо сказать прямо, потому что от слова
«граф» ждут большего.** Он **не переставляет проходы**. Из модели версий
следует, что зависимость всегда указывает на проход, объявленный раньше, то
есть порядок объявления уже топологический и сортировать нечего. Порядок кадра
задаёт человек; граф проверяет, что этот порядок осмыслен, и выбрасывает
лишнее. Он также не переиспользует память между ресурсами (aliasing) и не
расставляет барьеров: в OpenGL их нет, а проектировать вслепую под API,
которого в движке пока нет, — это угадывание, а не проектирование.

**Что он даёт уже сейчас:**

* Проход, результат которого никому не нужен, **не выполняется**. Такое
  возникает естественно: выключили эффект — остался проход, готовивший ему
  данные. Отбрасывается вся ветка, а не только её конец.
* Ошибки описания кадра ловятся **до отрисовки**, с именами прохода и ресурса.
  Прочитать то, во что ещё никто не писал, теперь нельзя.
* `Describe()` отвечает на вопрос «почему этого прохода нет в кадре» — раньше
  на него отвечало чтение тела функции с удержанием в голове всех условий.
  В Director 3D: `D3D_FRAME_GRAPH=1`.

**Почему форма именно такая, а не перенос прежнего кода.** Vulkan, D3D12 и
Metal требуют объявить проход заранее: какие вложения он трогает, что с ними
делать при входе и выходе, какие переходы состояний нужны между проходами. Эта
информация должна существовать ДО записи команд, и получить её из императивной
последовательности вызовов нельзя — её там просто нет. Теперь она есть и лежит
в одном месте. Это не доказывает переносимости; это снимает одно конкретное
препятствие.

## Уровни детализации (LOD)

Дальний объект стоит столько же, сколько ближний, а виден в десять раз хуже.
Уровни детализации убирают эту несправедливость: подробная геометрия остаётся
там, где на неё смотрят.

**Выбор — по проекционному размеру, а не по дальности.** Дальность — заманчиво
простая метрика и неверная: дом на ста метрах занимает пол-экрана, а болт на
десяти — два пикселя, и один порог «50 метров» означает для них
противоположное. Метрика (`sage/render/LodSelect.h`) — доля высоты кадра,
которую занимает ограничивающая сфера. Числа не зависят ни от разрешения, ни от
формата кадра, поэтому пороги задаются один раз.

**Уровни строятся сами.** LOD, который надо делать руками, не делает никто —
пока это отдельная работа художника на каждую модель, механизм выбора уровня
стоит в движке мёртвым грузом. `BuildAutoLods` строит грубые уровни из
подробного меша при загрузке.

```cpp
auto mesh = std::make_shared<Mesh>(Mesh::CreateSphere(48, 64, /*keepCpuData=*/true));
sage::render::LodComponent lod;
sage::render::BuildAutoLods(lod, *mesh, /*coarseLevels=*/2);
scene.Registry().emplace<sage::render::LodComponent>(entity, lod);
```

**Алгоритм упрощения — кластеризация вершин по сетке**, и это осознанный выбор
не в пользу лучшего. Схлопывание рёбер по квадрикам (Garland–Heckbert) даёт
аккуратнее силуэт, но ломается на незамкнутой и «грязной» геометрии — с дырами,
T-стыками, вывернутыми нормалями, — а именно такая приезжает из реальных
файлов. Кластеризация устойчива на любой, линейна по числу вершин и работает
мгновенно. Её место — дальние уровни; на ближних (сокращение меньше чем вдвое)
она гуляет по силуэту заметнее, чем экономит, и применять её там не нужно.

**Отсечение мелочи.** Объект мельче четверти процента высоты кадра (около трёх
пикселей на 1080p) не рисуется вовсе. Самая дешёвая экономия из всех.

Измерено (`TestLevelsOfDetail`, аллея из 14 сфер по 6144 треугольника):

| | без уровней | с уровнями |
|---|---|---|
| треугольников в кадре | 86 016 | 5 848 (**6.8 %**) |
| объектов отсечено по размеру | 0 | 5 из 14 |
| изменение кадра | — | **0.03 % пикселей** |

Обе половины проверки нужны. «Экономит» без «незаметно» доказывало бы только
то, что рисовать кубиками дешевле; проверка на подмену геометрии и ловит
перестаравшийся LOD. При отключённой подмене уровней тест показывает 64.3 %
вместо 6.8 % и падает.

**Чего пока нет:** уровни строятся из меша, который сохранил копию геометрии в
оперативной памяти (`keepCpuData`). Модели из файлов её не сохраняют, поэтому
автопостроение для них требует явного шага — это место связано с пайплайном
ресурсов и делается вместе с ним.

## Гизмо и отладочная графика (DebugDraw)

`sage/render/DebugDraw.h` — движковая система гизмо: батч 3D-линий, рисуемых
В МИРЕ с тестом глубины (не 2D-оверлей). Доступна и редактору, и играм:

```cpp
DebugDraw dbg; // шейдер встроен, внешних ассетов не требует
// каждый кадр, после отрисовки сцены в тот же буфер:
dbg.Grid({0,0,0}, 12.0f, 1.0f, {0.35f, 0.35f, 0.4f}); // сетка XZ, оси X/Z подсвечены
dbg.WireBox(transform.GetMatrix(), {1.0f, 0.6f, 0.1f}); // каркас (подсветка выбора/AABB)
dbg.WireSphere(center, radius, {0.2f, 0.8f, 0.3f});
dbg.Axes(transform.GetMatrix(), 1.5f);                  // оси: X-красная, Y-зелёная, Z-синяя
dbg.Line(from, to, color);
dbg.Flush(view, proj); // один draw call на весь батч
```

Линии проходят тест глубины (геометрия сцены их заслоняет), но глубину не
пишут. Редактор рисует этим подсветку выбранной сущности; играм это же API
годится для отладочных AABB/трасс/направлений.

### Сетка вьюпорта (GridRenderer)

`sage/render/GridRenderer.h` — сетка пола отдельным шейдером, а не набором
линий. `DebugDraw::Grid` умеет только конечный квадрат из отрезков, и у него два
неустранимых недостатка: у горизонта линии сжимаются в муар (толщина задана в
единицах мира, а не в пикселях), а «бесконечную» сетку пришлось бы набирать
десятками тысяч отрезков.

Здесь рисуется ОДИН полноэкранный треугольник, а в фрагментном шейдере луч из
камеры пересекается с горизонтальной плоскостью. Толщина линии считается через
`fwidth` — то есть в пикселях экрана: у горизонта клетка не рябит, а плавно
гаснет. Глубина пишется из ТОЧКИ ПЕРЕСЕЧЕНИЯ (`gl_FragDepth`), поэтому сетка
корректно уходит под геометрию, а не ложится поверх кадра.

```cpp
GridSettings grid;
grid.Mode = GridSettings::Extent::Infinite; // либо Radius + grid.Radius
grid.CellSize = 1.0f;      // шаг мелкой клетки, м
grid.MajorEvery = 10;      // каждая десятая линия — крупная
grid.ShowAxes = true;      // оси X (красная) и Z (синяя)
gridRenderer.Draw(view, proj, cameraPos, grid);
```

Два режима — не украшение, а два разных способа работы. **Infinite** тянется до
горизонта с автоматическим затуханием по высоте камеры: удобно, когда осваиваешь
пространство и не знаешь заранее его размер. **Radius** обрезает сетку мягкой
окружностью — так задают границу площадки: «моя сцена вот такая, за край
объекты не ставим». Затухание по расстоянию в этом режиме выключено намеренно:
оно существует ради горизонта, которого у конечной сетки нет, и гасило бы всю
площадку целиком, стоит отвести камеру.

Проверяется эталонными кадрами (`grid_infinite`, `grid_radius`) — у сетки нет ни
одного числа наружу, всё считает шейдер, и сравнить её можно только картинкой.

## Плагины редактора

> **По умолчанию ОТКЛЮЧЕНЫ** (экспериментальны — нестабильный ABI). Редактор не
> грузит плагины, пока не задана переменная окружения `SAGE_EDITOR_PLUGINS=1`.
> Без неё каталог `plugins/` игнорируется. Всё описанное ниже работает только
> при явном включении.

**v1: только редактор** (панели/инструменты) — плагины НЕ участвуют в рантайме
игр и не грузятся ни во что, кроме `SageEditor`. Без гарантий бинарной
совместимости между версиями движка/редактора: плагин пересобирается вместе с
редактором (собирается тем же CMake-проектом, тем же компилятором).

- Плагин — динамическая библиотека (`.so`/`.dll`), которую `PluginManager`
  грузит при старте редактора из каталога `plugins/` рядом с бинарником
  `SageEditor` (переопределяется переменной окружения `SAGE_PLUGINS_DIR`, тот
  же паттерн, что у `SAGE_SCREENSHOT_*`/`SAGE_EDITOR_SELFTEST`).
- Контракт — `editor/src/PluginAPI.h`: класс `SageEditorPlugin` с
  `Name()/OnLoad()/OnUnload()/OnUpdate(dt)/OnImGui()` (в `OnImGui()` плагин
  рисует свои `ImGui::Begin(...)` панели/пункты меню как обычный код
  редактора). `OnLoad` получает `EditorPluginContext&` — узкий facade
  (`Log`, `SelectedEntityName`, `SetStatusMessage`), **сознательно НЕ**
  пробрасывающий `Scene&`/`entt::registry&` через границу библиотеки (разные
  версии компилятора/STL у хоста и плагина делают это ABI-небезопасным);
  facade расширяется по мере появления реальных плагинов, не заранее.
- Плагин экспортирует две `extern "C"` функции:
  ```cpp
  extern "C" SageEditorPlugin* CreateSageEditorPlugin() { return new MyPlugin(); }
  extern "C" void DestroySageEditorPlugin(SageEditorPlugin* p) { delete p; }
  ```
- Сборка — `sage_add_editor_plugin(NAME <lib> SOURCES <files...>)` в
  `cmake/SageHelpers.cmake` (по образцу `editor/plugins/example_stats/`):
  собирает `MODULE`-библиотеку и копирует её в `plugins/` рядом с
  `SageEditor`. Плагин **не линкует** ни `sage::engine`, ни статическую
  `imgui` — только заголовки (ImGui хранит состояние `GImGui` в статической
  переменной; если плагин слинкует свою копию `libimgui.a`, он получит
  отдельный `GImGui` и упадёт на первом же `ImGui::Begin()`). Вместо этого
  вызовы `ImGui::` остаются неразрешёнными символами в библиотеке плагина и
  резолвятся в рантайме против уже загруженного ImGui хоста: на Linux/macOS —
  автоматически (dlopen против процесса, `SageEditor` собран с
  `ENABLE_EXPORTS`), на Windows — линковкой на сгенерированную
  import-библиотеку `SageEditor.exe` (`--export-all-symbols`).
- Пример: `editor/plugins/example_stats/` — панель с графиком времени кадра
  и именем выбранной сущности, показывающая полный цикл `OnLoad -> OnImGui`
  каждый кадр `-> OnUnload`.

## Как добавить графический бэкенд
Реализовать интерфейсы `sage::rhi::GraphicsDevice` (устройство: инициализация,
состояние конвейера, чтение пикселей) и ресурсы из `sage/rhi/Resources.h`
(`ShaderProgram`, `Geometry`, `Texture2D`, `TextureCube`, `RenderTarget`) в новом
каталоге `engine/src/rhi/<backend>/`, добавить ветку в фабрику
`GraphicsDevice::Create()`.

**Что здесь правда.** Движок, игры и редактор обращаются ТОЛЬКО к этим
интерфейсам: за пределами `engine/src/rhi/` во всём репозитории ноль вызовов
`gl*` (единственное исключение — `Window.cpp`, которому нужен контекст от
оконной системы). Это не заявление, а проверяемый факт: границу держит
`scripts/check_rhi_boundary.py`, он гоняется в CI отдельным шагом ДО сборки.

Второе доказательство — **Null-бэкенд** (`engine/src/rhi/null/`): полноценная
реализация того же интерфейса без единого графического вызова. Движок с ним
собирается и работает, что даёт тестам сцену без видеокарты и без xvfb.

Третье — **набор соответствия** (`sage/rhi/Conformance.h`): один исполняемый
контракт, который обязан пройти КАЖДЫЙ бэкенд. Пока реализация одна,
«интерфейс» и «то, что делает OpenGL» неразличимы, и отличить обязательство от
привычки невозможно — любое поведение выглядит правильным, потому что сравнивать
не с чем. Набор выносит контракт из комментариев в код: хендлы, дескрипторы,
безопасность вызова с невалидным аргументом, `Resolve()` на таргете без MSAA,
`nullptr` как легальный ответ на кубический таргет. Два уровня: структурный
проходят все, включая Null; пиксельный — только те, кто действительно
растеризует (Null честно пропускается, а не подделывает результат). Гоняется
из `sage_tests` по Null и из `sage_render_tests` по OpenGL.

Что он ловит на самом деле — видно, если сломать соглашение нарочно: перевёрнутое
начало отсчёта ножниц в GL-бэкенде роняет проверку «ножницы и чтение сходятся в
левом нижнем углу», хотя ни один из 97 эталонных кадров этого не замечает.

**Что здесь было неправдой.** Раньше в этом разделе стояло: «смена бэкенда не
затрагивает ни движок, ни игры, ни редактор». Для Vulkan, D3D12 и Metal это НЕ
так. Форма интерфейса — это машина состояний OpenGL (`SetBlend`, `SetDepthTest`,
`BindTexture2D`). Современные API устроены иначе: команды пишутся в буферы,
состояние собирается в объект конвейера заранее, ресурсы адресуются наборами
дескрипторов, синхронизация задаётся барьерами явно. `SetDepthTest` поверх
Vulkan реализуем, но это будет эмуляция состояния с пересборкой конвейеров на
лету — худшее из обоих миров.

**Что перестало течь.** Хендлы ресурсов были сырым `unsigned int` — то есть
именем объекта OpenGL, торчащим наружу через весь пост-процесс, тени и
отражения. Это была не стилистика: у Vulkan и Metal хендл — 64-битный указатель,
в 32 бита он не влезает, и второй бэкенд упёрся бы не в архитектуру, а в
арифметику. Хуже была вторая половина — число без типа путается с чем угодно, и
хендл текстуры, хендл запроса и номер юнита компилятор различить не мог. Теперь
это `rhi::TextureHandle` и `rhi::QueryHandle` без неявного приведения к числу.
Сырое число осталось ровно в одной, отдельно названной двери — `NativeHandle()`
для `ImGui::Image`: передача текстуры в стороннее API бэкенд-специфична по своей
природе, и делать вид, что это не так, было бы хуже протечки — тогда
бэкенд-зависимое место выглядело бы переносимым.

**Соглашения записаны.** Начало отсчёта прямоугольников (левый нижний угол),
порядок строк `ReadPixelsRGB` (снизу вверх), начало координат текстуры, диапазон
глубины NDC `[-1, 1]`, порядок матриц. Раньше интерфейс об этом молчал, а бэкенд
решал по привычкам OpenGL. Молчание здесь опаснее протечки типа: несовпадение
соглашений не ломает сборку, а даёт перевёрнутую картинку или маску интерфейса,
обрезающую не тот край, — и ищется это неделями, потому что «на OpenGL всё
работает».

**Честная оценка:** Vulkan-бэкенд потребует переписать МОДЕЛЬ интерфейса
(команды, проходы, дескрипторы) и места, где движок эту модель использует, —
прежде всего порядок проходов кадра. Null-бэкенд доказывает изоляцию, а не
переносимость: он выдержан в той же GL-подобной форме и потому не является
свидетельством, что форма годится для Vulkan. Пустышка соглашается с любой
формой — ей нечего возразить.

Два ограничения самого GL 3.3, о которых надо знать заранее:
* **нет вычислительных шейдеров** (появились в 4.3) — всё, что естественно
  ложится на compute (свёртки, отбор на GPU, частицы), делается через
  фрагментные проходы или на CPU;
* **macOS объявил OpenGL устаревшим** и остановился на 4.1 — порт на Apple
  означает Metal или MoltenVK, то есть тот же разговор про модель.

## Профилировщик кадра
`sage/core/Profiler.h` отвечает на вопрос, с которого начинается любая
оптимизация: **куда именно уходит время кадра**. Без него правки идут наугад, и
половина из них делает хуже.

```cpp
#include "sage/core/Profiler.h"

void MyLayer::OnRender() {
    { SAGE_PROFILE("Тени");  RenderShadows(); }
    { SAGE_PROFILE("Сцена"); RenderScene(); }   // участки вкладываются
}
```

`Application::Run` уже размечает кадр целиком (загрузка ресурсов, обновление,
отрисовка, обмен буферов), поэтому игре достаточно расставить свои метки внутри.

* **Две шкалы, и путать их нельзя.** CPU — сколько мы потратили, СОБИРАЯ
  команды. GPU — сколько видеокарта их выполняла. Они идут параллельно: процессор
  строит следующий кадр, пока видеокарта рисует прошлый. Узкое место — МАКСИМУМ
  из двух, а не сумма.
* **Метки, а не интервалы.** Внутри используется `glQueryCounter(GL_TIMESTAMP)`,
  потому что интервальный запрос `GL_TIME_ELAPSED` может быть активен только один
  за раз — вложенные проходы им не измерить.
* **Результат запаздывает на три кадра.** Спросить его сразу — значит дождаться
  видеокарты, то есть своим измерением создать ту самую задержку, которую
  измеряешь. У каждого кадра в полёте СВОЙ пул меток: с общим пулом следующий
  кадр перезаписывает метки, готовности которых ждёт профилировщик, и на
  медленной отрисовке они не созревают никогда.
* **Выключен по умолчанию.** Метки времени не бесплатны, и платить за них у
  игрока незачем: `sage::profile::SetEnabled(true)`.
* **Бэкенд без таймеров не мешает работать** — показывается только время CPU
  (`GpuTimersAvailable()` честно вернёт `false`). Если драйвер стабильно
  опаздывает с готовностью меток, профилировщик через десяток кадров сам
  отключает GPU-часть, а не молчит с пустой таблицей.

**Где смотреть.** В редакторе — **Window → Профилировщик**: таблица участков с
вложенностью, двумя колонками времени и полосой по доле от самого дорогого.
Панель включает профилирование, пока она открыта, и выключает при закрытии.

Там, где окна нет вовсе — headless-прогон, CI, машина игрока, — работают две
переменные окружения: `SAGE_PROFILE=1` включает замеры, `SAGE_PROFILE_LOG=<сек>`
дополнительно печатает таблицу в лог с этим периодом. Требовать ради разбора
просадки отладочную сборку значит не разобраться никогда: разбираться приходится
на чужой машине и на чужом драйвере.

**Что размечено.** Кадр целиком (загрузка ресурсов, обновление, отрисовка, обмен
буферов), каждая система планировщика по имени, отсечение, тени, геометрия,
скиннинг, зонды отражений, плоское отражение, куб окружения, проверка
перекрытия, интерфейс сцены и каждый проход пост-обработки по отдельности —
SSAO, глубина резкости, смаз, bloom, тон-маппинг, FXAA.

Разметка тут не формальность. Первый же прогон боевой игры показал, что
пост-обработка стоит больше геометрии, а внутри неё половину съедает SSAO — то
есть ответ на вопрос «где» оказался не там, где его искали бы по коду:

```
Отрисовка                 CPU 133.453 мс   GPU 148.728 мс
  Тени                    CPU   2.036 мс   GPU   6.795 мс
  Геометрия               CPU   7.927 мс   GPU  36.758 мс
  Пост-обработка          CPU 121.908 мс   GPU 102.295 мс
    SSAO                  CPU  66.160 мс   GPU  55.472 мс
    Bloom                 CPU  39.557 мс   GPU  18.600 мс
```

## Скелетная анимация
Движок умеет **скелетную анимацию** (skinning) — деформацию меша скелетом
костей. Данные независимы от GPU и живут в `sage/anim/`:

- `Skeleton` — кости (TRS + родитель + обратная bind-матрица);
- `AnimationClip` — каналы (перенос/поворот/масштаб кости) с ключами и
  интерполяцией (линейная со сферической для поворотов / STEP);
- `Animator` — проигрыватель: сэмплирует клип, считает глобальные матрицы
  костей и выдаёт **палитру** (`global · inverseBind`) для скиннинг-шейдера.
  Поддерживает **кросс-фейд между клипами** (`CrossFade(clip, fadeTime)`): во
  время перехода ОБА клипа проигрываются и позы смешиваются покостно (lerp T/S,
  slerp R) — плавные переходы без рывка, два клипа одновременно. Смена `Clip` в
  `AnimatedModelComponent` (редактор/скрипт) авто-запускает кросс-фейд на
  `BlendTime` секунд; в Lua — `PlayAnimation(entity, clip[, blend])`. Демо-
  щупалец несёт два клипа (Wave/Curl) для наглядного перехода.

**Ручная поза (переопределения костей).** Клипы — не единственный источник
позы: `Animator::SetPoseOverride` принимает вектор `JointPose` (локальные TRS с
раздельными флагами T/R/S) и накладывает их ПОСЛЕ сэмплирования и смешивания
клипов. Поэтому правка кости выигрывает у клипа даже во время кросс-фейда, а
покомпонентные флаги позволяют анимировать поворот руки, оставив перенос от
клипа. На этом стоит ручная анимация персонажа в Director 3D, и на этот же слой
ложится результат IK. Наружу отдаются и
**глобальные матрицы костей** (`GlobalMatrices()`, без `inverseBind`) — палитра
для этого непригодна, она переводит вершины из bind-позы, а не описывает
положение сустава.

**Блендшейпы (морф-цели).** Мимика и всё, что скелетом не выражается. Дельты
позиций и нормалей хранятся во **float-текстуре**, а не в дополнительных
вершинных атрибутах: атрибутов в GL 3.3 шестнадцать, пять уже заняты скиннингом,
и на каждую цель ушло бы по два — четыре-пять целей стали бы потолком, а лицу их
нужны десятки. Цена выборки платится только за АКТИВНЫЕ цели: в кадр уходят
индексы и веса тех, чей вес не ноль (до восьми, самые весомые). Морфинг
применяется ДО скиннинга — блендшейпы заданы в bind-позе, а кости двигают уже
итоговую форму. Веса живут в `AnimatedModelComponent::MorphWeights`, имена целей
читаются из glTF (`mesh.extras.targetNames`), стартовые веса — из `mesh.weights`.
Демо-щупалец несёт две процедурные цели (`Fatten`/`Bend`) — блендшейпы можно
посмотреть и проверить без лицевой модели.

**Ретаргет** (`sage/anim/Retarget.*`) — перенос клипа между скелетами.
Соответствие костей строится по именам с нормализацией (снимается префикс
экспортёра `mixamorig:`, разделители и регистр). Повороты переносятся
ОТНОСИТЕЛЬНО бинд-позы (`R_target = B_target · B_source⁻¹ · R_source`), поэтому
разная ориентация суставов у скелетов сокращается. Длины костей не переносятся —
они принадлежат целевому скелету; исключение — корень, его перемещение
масштабируется отношением роста. Это ретаргет на уровне поз: при сильно разных
пропорциях ступни проскальзывают — снимается прилипанием опорной ноги из IK
(`SetIKFootLock`), см. ниже.

**Обратная кинематика** (`sage/anim/IK.*`). Прямая кинематика отвечает на
вопрос «куда придёт кисть, если повернуть плечо и локоть», IK — на обратный:
«как повернуть плечо и локоть, чтобы кисть оказалась ЗДЕСЬ». Для анимации это
разница между «поставить ногу на ступеньку» и «подбирать два угла, пока не
совпадёт».

Четыре солвера, потому что задача распадается на разные случаи:

- `SolveTwoBone` — цепочка из трёх суставов (плечо-локоть-кисть,
  бедро-колено-ступня). Решается **аналитически** по теореме косинусов: угол
  сгиба однозначно выводится из длин костей и расстояния до цели, дальше корень
  доворачивается к цели. Итераций нет вовсе — ответ точный и одинаковый в каждом
  кадре, что для анимации важнее скорости: сходящийся по-разному солвер дал бы
  дрожание на соседних кадрах. `PoleTarget` задаёт, куда смотрит локоть или
  колено; без него плоскость сгиба берётся из текущей позы.
- `SolveChain` — **FABRIK** (Forward And Backward Reaching IK) для цепочек
  подлиннее: хвост, позвоночник, щупальце. Итеративно протягивает цепочку к цели
  и обратно к корню, сохраняя длины костей. Аналитики для N звеньев нет —
  решений бесконечно много.
- `SolveAim` — взгляд: ОДНА кость доворачивается так, чтобы её ось смотрела на
  цель. Двухзвенным это не решается — звено одно. Поворот ограничен **конусом**
  от текущего направления: цель за спиной не выворачивает шею, персонаж
  доворачивается до предела и останавливается. Предел УКОРАЧИВАЕТ поворот, а не
  отменяет его — отказ выглядел бы как «IK иногда не работает».
- `AimEnd` — доворот КОНЦА цепочки под заданную ориентацию. Ступне мало попасть
  в точку на склоне: не легла на него — значит воткнулась носком, и это заметнее
  ошибки в пару сантиметров по высоте.

Все возвращают ЛОКАЛЬНЫЕ повороты суставов (`IKResult`), а не готовую позу:
`ApplyIK` кладёт их в те же `JointPose`, что и ручная правка. Поэтому результат
IK можно заключить ключом, смешать с клипом весом и отменить как обычную правку
— отдельного «режима IK» в инструменте не появляется. `Reached` честно говорит,
дотянулись ли: цель дальше вытянутой конечности не ошибка, конечность просто
вытягивается в её сторону.

#### IK в игре: `IKComponent`

Солверы — это математика; чтобы ими пользовалась игра, нужен слой, который знает
про сцену. `IKComponent` держит список целей, а `SolveIKGoals` (второй проход
`UpdateAnimators`, после позы клипа и корневого движения) их решает.

```lua
local g = AddIKGoal(hero, "foot_l")          -- вернёт индекс цели
SetIKTarget(hero, g, Vec3(x, groundY, z))    -- МИРОВЫЕ координаты
SetIKPole(hero, g, Vec3(x, y, z + 2))        -- куда смотрит колено
SetIKAlign(hero, g, groundNormal)            -- ступня ложится на склон
SetIKFootLock(hero, g, true, 0.15)           -- прилипание опорной ноги
SetIKWeight(hero, g, w)                      -- плавное включение

local look = AddIKGoal(hero, "Head", 1)
SetIKAim(hero, look, Vec3(0, 0, 1), 70.0)    -- ось кости и предел конуса

BonePosition(hero, "foot_l")                 -- где сейчас кость (в мире)
BoneAxis(hero, "foot_l", Vec3(0, 1, 0))      -- куда смотрит её ось
IKLocked(hero, g)                            -- нога держится за землю? (шаги, пыль)
```

Три решения, каждое стоило отладки:

**Цели задаются в МИРЕ, кости — по ИМЕНИ.** Игра знает, где у неё пол и
предметы, а не где начало модели; переводом в пространство модели занимается
движок. Имя кости переживает переэкспорт, индекс — нет.

**Каждый кадр IK откатывается и считается заново от позы клипа.** Свои
переопределения он помнит (`Touched`/`Saved`) и перед новым решением возвращает
на место. Без отката ломались две вещи: доворот конца — величина
ОТНОСИТЕЛЬНАЯ, и, накладываясь сам на себя, он раскручивал ступню кадр за
кадром (в стенде это видно сразу: вектор подошвы прыгал между кадрами вместо
того, чтобы стоять); а выключенная цель оставляла бы свой последний поворот в
позе навсегда — снять IK было бы нечем.

**Доворот ступни не предполагает ничего про оси кости.** Соблазн взять локальный
`+Y` кости за «вверх» ступни живёт ровно до первой чужой модели: у рига
Universal Animation Library ось `Y` кости `foot_l` смотрит вперёд-вниз
`(0, −0.51, 0.86)`. Поэтому доворачиваем на РАЗНИЦУ между полом, под который
анимировали (ровный, нормаль `+Y`), и настоящим — это верно для любого рига.

**Прилипание опорной ноги (`Lock`)** — лекарство от скольжения: пока стопа ниже
`PlantHeight`, движок запоминает мировую точку касания и держит ногу в ней.
Отпускает не рывком, а за `ReleaseTime` секунд: мгновенный отпуск давал бы
щелчок — за кадр стопа прыгала бы из удержанной точки туда, где её к этому
времени поставил клип, а щелчок глазу заметнее плавного скольжения.

Цели сериализуются в `.sage` (без рантайм-состояния: индексы костей ищутся
заново, залипшая опора — это состояние текущего шага) и правятся в секции **IK**
инспектора, с выбором кости из списка реального скелета.

Ограничение, которое стоит знать: **опоры движок не ищет** — физического луча в
`sage/physics` нет, высоту и нормаль пола под ступнёй подаёт игра. Для лодки,
лестницы или тайловой карты это одна строка на своей же геометрии; для
произвольного ландшафта понадобится собственный запрос.

Геометрия и рендер — в `sage/render/SkinnedModel.*`: вершина несёт до 4 костей
с весами; скиннинг-шейдер считает позицию/нормаль как взвешенную сумму костей на
GPU. Его **фрагментная стадия использует тот же общий PBR-блок**
(`kPbrSharedGlsl`, Cook-Torrance metallic-roughness) — ambient (в т.ч. из
скайбокса) + солнце с PCF-тенями + точечные + прожекторы + туман, — так что
анимированные и статичные меши освещаются ФИЗИЧЕСКИ ОДИНАКОВО (metallic/roughness
берутся из glTF-материала submesh'а). Скелетные модели
также **отбрасывают тень**: у карты теней есть отдельный depth-проход со
скиннингом (`SkinnedModel::DrawDepth` / `DrawAnimatedModelsDepth`), поэтому
анимированный меш и получает, и отбрасывает тень в текущей позе. Модель —
разделяемый ассет (скелет/клипы), а покадровое состояние держит `Animator` у
каждой сущности.

**Загрузка.** `SkinnedModel::Load("hero.glb")` читает из glTF/GLB скин
(JOINTS_0/WEIGHTS_0, inverseBindMatrices) и анимации (каналы/сэмплеры) —
стандартный формат экспорта из Blender/Maya. Без внешнего ассета есть
процедурная демо-модель `SkinnedModel::CreateDemoTentacle()` (гибкий «щупалец»
с клипом Wave) — на ней держатся примеры и headless-тесты.

**В ECS/редакторе.** Повесь `AnimatedModelComponent` (поле `Path` — файл .glb,
пустое = процедурное демо; `Clip`/`Speed`/`Loop`/`Playing`). Система
`sage::anim::UpdateAnimators`/`DrawAnimatedModels` (`sage/anim/AnimationSystem.h`)
инициализирует, продвигает и рисует все такие сущности — вызывается редактором
(анимация видна в вьюпорте, секция **Animated Model** в Inspector, меню
**Entity → Create Animated Model**) и рантаймом `SagePlayer`. Описательные поля
сериализуются в `.sage`. Живой пример — «тотем» в `games/testgame` (комната 1).
Ограничение: до 128 костей на модель (`kMaxBones`).

### Библиотека анимаций: чужие клипы на своём скелете

Наборы движений продаются отдельно от персонажей — в этом их смысл: один набор
на любого героя. Чтобы им можно было ВОСПОЛЬЗОВАТЬСЯ, клипы надо переложить на
свой скелет:

```lua
local added = BorrowAnimations(entity, "assets/models/anim_library.glb")
PlayAnimationNamed(entity, "Walk_Loop", 0.25)   -- 0.25 с кросс-фейда
```

Клипы кладутся В МОДЕЛЬ, а не в сущность: результат зависит только от исходных
клипов и целевого скелета, оба принадлежат модели. Держи их сущность, две
тысячи NPC хранили бы две тысячи копий одних и тех же ключей.

Совпадение костей ищется сначала по точному имени, затем по КАНОНИЧЕСКОМУ
(`CanonicalBoneName`) — таблице синонимов трёх ходовых соглашений: Unreal зовёт
бедро `thigh_l`, Blender — `UpperLeg.L`, Mixamo — `LeftUpLeg`. Без неё
совпадают только руки, кисти и голова, и перенесённая анимация выходит БЕЗ НОГ
— выглядит как «ретаргет сломан», хотя просто никто не договаривался об именах.
На живой паре (библиотека из 65 костей → персонаж из 21) таблица подняла
совпадение с 9 костей до 15.

Ретаргет переносит ПОВОРОТЫ (как отклонение от бинд-позы источника, приложенное
к бинд-позе цели) и не переносит длины костей и масштаб: они принадлежат
целевому скелету. Перемещение переносится только у корня.

Отсюда и главная болячка ретаргета: пропорции у скелетов разные, длина шага в
клипе не совпадает с тем, как игра везёт тело, и опорная нога едет по полу.
Лечится это не ретаргетом, а IK поверх него — прилипанием опорной ноги. На
стенде (клип из библиотеки на 65 костей, перенесённый на скелет из 21, с
масштабом 1.5) за одни и те же кадры опоры нога без замка проехала **0.855 м**,
с замком — **0.001 м**. Второе ограничение — руки: они не сойдутся в точке сами
по себе, для этого цель кисти задаётся явно (`AddIKGoal(obj, "hand_r")`), и
тогда промах держится в пределах трёх сантиметров.

### Корневое движение (root motion)

Библиотеки поставляются в двух вариантах: с запечённым в клип перемещением и
без. С запечённым и БЕЗ извлечения меш уезжает от своей сущности — персонаж
идёт, а его коллайдер, камера и точка звука остаются на месте, и на стыке цикла
он телепортируется назад.

```lua
SetRootMotion(entity, true)   -- перемещение из клипа двигает СУЩНОСТЬ
```

Смещение считается по разности кадров, а не по абсолютной позиции: клип может
начинаться где угодно, а игре нужно «на сколько продвинулись». Откат на стыке
цикла отбрасывается по порогу — настоящий шаг за кадр это сантиметры, а откат
метры. К трансформу смещение прикладывается С ПОВОРОТОМ сущности: клип двигает
персонажа вперёд в СВОИХ координатах, а куда он смотрит, знает только трансформ.
Отдаётся оно один раз (`ConsumeRootDelta`) — иначе два читателя сдвинули бы
сущность дважды за кадр.

Переключателем, а не всегда: платформеру нужна своя скорость передвижения, а
катсцене — ровно та, что в клипе.

### Оснащённая модель без клипов

Наборы персонажей сплошь и рядом приходят ОСНАЩЁННЫМИ, но без единой анимации:
клипы продаются отдельно. Без возможности двигать кости из скрипта такой пакет —
набор неподвижных статуй, и проверить на нём скиннинг нечем.

```lua
AddAnimatedModel(entity, "assets/models/hero.glb")
local names = JointNames(entity)          -- имена костей как в файле
local head = JointIndex(entity, "Head")   -- индекс ищем ОДИН раз
SetJointRotation(entity, head, 0, yaw, 0) -- градусы, каждый кадр
ClearJointPoses(entity)
AnimationCount(entity)                    -- 0 — клипов в файле нет
```

Поворот ДОБАВЛЯЕТСЯ к позе покоя, а не заменяет её. Заменять нельзя: у скелета
кости уже развёрнуты как надо (руки вдоль тела, ступни по земле), и «повернуть
плечо на 30°» абсолютным кватернионом стирает эту ориентацию — персонаж встаёт в
раскоряку. Переопределения накладываются ПОСЛЕ клипа, поэтому «голова смотрит на
курсор» поверх ходьбы — это они же.

Две ловушки, найденные на живом наборе (low-poly people, 18 моделей):

* **Глобальный флаг переворота stb протекал между загрузчиками.** Обычные
  текстуры грузятся перевёрнутыми (у GL v=0 внизу), у glTF соглашение обратное.
  Унаследовав чужой флаг, модель получала палитру вверх ногами — и это не
  «зеркальная картинка», а совсем другие тексели: у палитровых моделей все цвета
  лежат в одном углу, и после переворота UV попадали в пустоту. Персонаж
  становился ЧЁРНЫМ, причём только если до него успели загрузить любую другую
  текстуру, то есть плавающе, в зависимости от порядка загрузки.
* **Кэш ассетов пережил исправление загрузчика.** Кэш хранит РЕЗУЛЬТАТ разбора,
  и после правки продолжал отдавать сломанные данные — молча, потому что файл-
  исходник не менялся. Поэтому версия кэша теперь версия ФОРМАТА И ЗАГРУЗЧИКА:
  поднимать её обязан всякий, кто чинит разбор.

Палитровые текстуры (≤128 px) грузятся `Nearest` без мип-уровней: мип-уровни
усредняют палитру целиком, а у палитровой модели 90 % текстуры пусто.

Анимированная модель кэшируется ПО ПУТИ (`ResourceManager::GetSkinnedModel`).
Раньше её грузила каждая сущность отдельно: дюжина одинаковых NPC означала
дюжину разборов файла, дюжину загрузок геометрии на видеокарту и дюжину копий
всех клипов — для библиотеки анимаций это десятки мегабайт ключей на ровном
месте.

## Физика
Физика построена по тому же принципу, что и графика (RHI): **подключаемая
абстракция** `sage::physics::PhysicsWorld` (заголовок `sage/physics/
PhysicsWorld.h`) — движок, редактор и игры создают тела и шагают симуляцию
через этот интерфейс, не завися от конкретной библиотеки. Конкретные бэкенды
живут в `engine/src/physics/<backend>/` и выбираются фабрикой
`PhysicsWorld::Create(Backend)`:

- **Jolt** (`Backend::Jolt`) — основной, «взрослый» бэкенд поверх
  [jrouwe/JoltPhysics](https://github.com/jrouwe/JoltPhysics): полная динамика
  твёрдых тел с вращением, честные контакты, формы Box/Sphere/Capsule.
  Подтягивается через FetchContent (тег `v5.3.0`), включён по умолчанию
  (`-DSAGE_PHYSICS_JOLT=ON`). Это бэкенд по умолчанию (`DefaultBackend()`),
  когда собран.
- **Simple** (`Backend::Simple`) — встроенный лёгкий интегратор без внешних
  зависимостей: гравитация + столкновение динамики со статикой как AABB,
  упругость/трение, без вращательной динамики. Доступен всегда — на нём
  движок собирается и работает даже с `-DSAGE_PHYSICS_JOLT=OFF` (быстрая
  сборка, окружения без сети). Fallback, если Jolt не скомпилирован.

### Состав физического мира живой

`PhysicsScene` — мост между ECS-сценой и физическим миром — сверяет состав
сцены КАЖДЫЙ КАДР, а не только при создании: сущность с `RigidBodyComponent`,
появившаяся после старта симуляции, получает тело на ближайшем шаге, а тело
уничтоженной сущности возвращается миру.

Это не удобство, а условие работоспособности. Игры порождают физические объекты
в рантайме постоянно — скрипт спавнит плавучий мусор, обломки, брошенные
предметы. Пока тела строились только в конструкторе, всё порождённое после
старта оставалось без физики МОЛЧА: компонент на сущности есть, тела нет,
объект висит в воздухе, и никакой ошибки. А удалённые сущности навсегда
оставляли тело в мире — игра, создающая и убирающая предметы каждую секунду, за
минуту набивала физический мир невидимым мусором, с которым продолжали
сталкиваться живые тела.

От игры при этом не требуется ничего: навесил `RigidBodyComponent` (хоть из
Lua — `entity:AddRigidBody()`) — получил физику. Покрыто тестами
(`tests/test_physics.cpp`): тело для сущности, созданной после старта; снятие
тела за уничтоженной и за снятым компонентом; повторный запуск симуляции на той
же сцене (Play → Stop → Play) строит тела заново, а не принимает протухшие
хэндлы первого прогона за живые.
- **Null** (`Backend::Null`) — заглушка (физика отключена, `IsAvailable()` =
  `false`).

**Как пользоваться в игре/редакторе.** Повесь на сущность два компонента:
`RigidBodyComponent` (тип тела Static/Dynamic/Kinematic + масса/трение/
упругость) и `ColliderComponent` (форма Box/Sphere/Capsule + размеры;
домножаются на `Transform.Scale`). Мост `PhysicsScene` (`sage/physics/
PhysicsScene.h`) строит физический мир по всем таким сущностям, а его `Step()`
каждый кадр синхронизирует: Dynamic — тело → `Transform`, Kinematic —
`Transform` → тело, Static — неподвижно. В редакторе это работает в Play-режиме
(секции Rigid Body / Collider в Inspector, каркас коллайдера в вьюпорте, пункт
меню **Entity → Create Physics Cube**); в собранной игре (`SagePlayer`) — сразу
при запуске; живой пример в `games/testgame` (комната 1 роняет башенку ящиков).
Компоненты сериализуются в `.sage`. Env-переопределения бэкенда не требуется —
`RigidBody`/`Collider` одинаковы для всех бэкендов.

**Как добавить свой бэкенд физики.** Реализуй интерфейс `PhysicsWorld` в новом
каталоге `engine/src/physics/<backend>/`, добавь значение в `enum class Backend`
и ветку в `PhysicsWorld::Create()`. Код игр/редактора не меняется — это и есть
требование «подключать разные библиотеки».

## Исправленные дефекты рендера и физики

Три дефекта, которые видно на экране, и у двух из них оказался общий корень.
(Дефекты редактора — выбор в иерархии и точность выбора мышью — описаны ниже,
отдельным разделом.)

**Коллизия не следовала за объектом.** Тело физики создавалось из ЛОКАЛЬНОГО
`Transform`. У корневой сущности локальное и мировое совпадают, поэтому ошибка
была невидима во всех сценах, где тела висят на корне, — и проявлялась ровно
тогда, когда объект прицепляли к другому: на экране всё правильно (рендер
мировую матрицу учитывает), а сталкивается объект в стороне. Обратная запись
страдала тем же с другого конца: физика отвечает в мировых координатах, а
`Transform` хранит локальные, и ребёнок каждый кадр уезжал на смещение
родителя. Теперь тело создаётся, толкается и читается через мировую матрицу, а
результат переводится обратно в локальные координаты через матрицу родителя.

Гизмо коллайдера врало отдельно: рисовало осевой ящик по локальной позиции, без
поворота вообще. Врущее гизмо хуже отсутствующего — по нему принимают решения.
Теперь каркас строится по мировой матрице, капсула рисуется капсулой (а не
ящиком по габаритам, у которого есть углы, которых у капсулы нет), и составная
форма показывает КАЖДУЮ свою часть в её смещении и повороте.

**Кривой угол скайбокса.** Вершинный шейдер неба нормализовал направление луча
ДО интерполяции. Луч восстанавливается из точки на дальней плоскости, а
растеризатор интерполирует линейно — линейно интерполировать можно только сами
точки плоскости, они на ней и остаются. Нормаль делит каждую вершину на СВОЮ
длину, а у полноэкранного треугольника длины отличаются в разы (NDC идёт от -1
до 3). После такого деления промежуточные значения не соответствуют ни одному
лучу камеры: градиент сжимается, горизонт уезжает и перекашивается — тем
сильнее, чем шире кадр. Нормализация переехала во фрагментный шейдер, где она
поточечная.

**Ступенька на отражающей сфере** оказалась тем же небом с другой стороны.
`pow(t, 0.5)` даёт нужный вид — почти всё небо цвета зенита, у горизонта узкая
светлая полоса, — но у корня БЕСКОНЕЧНАЯ производная в нуле, а ниже горизонта
лежала плоская плита ровно одного цвета. Стык плиты с бесконечно крутым
подъёмом — разрыв по производной; на самом небе он читается полосой, а в
отражении на шаре — жёсткой ступенькой поперёк, которая выглядит как дефект
рендера. Окно `smoothstep` гасит подъём в первых ~15° над горизонтом: у него
нулевая производная в нуле, стык становится гладким, а выше окна картина
остаётся ровно той, ради которой брали корень.

Все три закреплены тестами, и два из них — численными, а не эталонными
картинками: направление луча неба сверяется с АНАЛИТИЧЕСКИМ ответом (отклонение
0.6 из 255), а тело дочерней сущности проверяется лучом в точку, где оно обязано
оказаться после поворота родителя. Такой тест не зависит ни от драйвера, ни от
того, что кто-то однажды перезапишет эталон.

Побочно вскрылась мера в тесте отражений: «резкость перехода» считалась
абсолютным перепадом яркости, а он с шероховатостью РАСТЁТ (чем шероховатее
металл, тем больше окружения собирает env-BRDF). Мера считала две вещи сразу и
держалась только потому, что кривое небо смазывало горизонт в кубе. Теперь она
делится на полный размах яркости шара и отвечает ровно на нужный вопрос: за
какую долю всего перепада отвечает один пиксель.

## Исправленные дефекты редактора

**В иерархии не выбирались объекты.** Строка дерева рисовалась через
`TreeNodeEx`, а сразу после неё — иконка типа сущности через `EditorIcons::Inline`.
Inline резервирует место под рисунок с помощью `ImGui::Dummy`, то есть ПОДАЁТ
СВОЙ ЭЛЕМЕНТ, и с этого момента всё «Item»-семейство ImGui — `IsItemClicked`,
`BeginDragDropSource`, `BeginDragDropTarget`, `BeginPopupContextItem` — отвечает
про квадратик размером с букву вместо строки дерева. Клик проверялся у иконки,
попасть в которую можно было лишь случайно; заодно молча не работали
перетаскивание и контекстное меню. Появился `EditorIcons::Overlay` — рисунок в
списке отрисовки окна БЕЗ подачи элемента, поэтому «последним элементом»
остаётся строка.

**Клик мимо объекта засчитывался как попадание** («кликаю прямо по объекту, а
точка как будто ниже»). Выбор мышью проверял куб со стороной радиуса
ограничивающей СФЕРЫ меша. Сфера считается для отсечения по фрустуму, где она и
уместна: инвариантна к повороту, проверка дешёвая, а ошибка в большую сторону
безобидна — лишний объект просто нарисуется. Для попадания мышью та же ошибка
становится главной: у куба такая коробка больше него на 73% по каждой оси, у
пола 20x20 — это квадрат 28x28, внутри которого оказывается вся сцена, и пол
выигрывал клик у всего, что на нём стоит.

Что изменилось:

- `Mesh` хранит настоящий AABB (`BoundsMin`/`BoundsMax`) — он и раньше
  вычислялся при построении меша, но выбрасывался;
- `sage::render::RayMesh` / `RayGeometry` (`engine/src/sage/render/MeshRaycast.h`)
  — сначала коробка, а при наличии копии геометрии на стороне процессора
  перебор треугольников (Мёллер—Трумбор): клик в просвет между деталями модели
  больше не выбирает модель. Без копии точность честно деградирует до коробки, и
  вызывающий узнаёт об этом по полю `RayHit::Exact`;
- точное попадание бьёт приблизительное ДАЖЕ ЕСЛИ ОНО ДАЛЬШЕ — иначе объект без
  копии геометрии перехватывал бы выбор у соседа просто потому, что его коробка
  начинается раньше;
- `ResourceManager::SetKeepMeshCpuData` — копии геометрии включает редактор,
  собранная игра за них не платит (копия большой модели весит мегабайты).

Проверки: `tests/test_picking.cpp` (луч против коробки и против треугольников,
включая случай, в котором сфера и коробка расходятся) и шаг self-test'а
редактора, который кликает по спроецированным мировым точкам. Оба падают, если
вернуть старые габариты.

## Система сцен и сериализация
`Scene` — это ECS-сцена на `entt::registry`. Сущности собираются из компонентов
(`NameComponent`, `Transform`, `MeshRendererComponent`, `ScriptComponent`,
`CameraComponent`, ...);
`GameObject` — дешёвый дескриптор `{registry, entity}` с аксессорами к
компонентам. `SceneManager` держит несколько сцен и переключает активную:

```cpp
SceneManager sceneManager;
Scene& level1 = sceneManager.CreateScene("Level1");
GameObject obj = level1.CreateObject("MyCube");
obj.GetTransform().Position = {0.0f, 1.0f, 0.0f};
obj.Renderer().Ref = MeshRef{MeshRef::Type::Cube, ""};
obj.Renderer().MeshPtr = ResourceManager::Instance().GetCube();

// Сохранить сцену на диск (человекочитаемый JSON, расширение .sage)
sceneManager.SaveScene("Level1", "assets/scenes/level1.sage");

// Загрузить сцену обратно (сам пересоздаст GPU-ресурсы мешей)
sceneManager.LoadScene("assets/scenes/level1.sage");
```

Обход сущностей — через ECS-view (`scene.Registry().view<...>()`) или готовую
систему `sage::ecs::ForEachRenderable(scene, ...)`. Для снапшотов в памяти
(undo/redo, Play-режим) есть строковые варианты — `SceneSerializer::SaveToString`/
`LoadFromString`, тот же JSON, без обращения к диску.

Файл `.sage` — обычный JSON, можно открыть и посмотреть/поправить руками:
```json
{
  "sage_scene_version": 1,
  "name": "Level1",
  "objects": [
    {
      "id": 1, "name": "Cube1",
      "position": {"x":0,"y":0,"z":0},
      "rotation": {"x":0,"y":0,"z":0},
      "scale":    {"x":1,"y":1,"z":1},
      "color":    {"x":0.8,"y":0.3,"z":0.3},
      "mesh": {"type":"cube","path":""}
    }
  ]
}
```

Для модели вместо куба: `"mesh": {"type":"model","path":"assets/models/dragon.obj"}`.
Сущность со скриптом добавляет поле `"script": "assets/scripts/spin.lua"`.

## Скриптинг (Lua)
Часть ЯДРА движка (`engine/src/sage/scripting/ScriptEngine.*`) — не зависит ни
от какой конкретной игры. Позволяет управлять поведением сущностей через
`.lua` файлы без перекомпиляции движка: правишь скрипт, перезапускаешь игру,
видишь результат.

```cpp
ScriptEngine scriptEngine;
scriptEngine.BindScene(scene);
scriptEngine.AttachScript(myGameObject, "assets/scripts/spin.lua");

// каждый кадр:
scriptEngine.UpdateAll(deltaTime);
```

Скрипт получает объект как `entity` и может читать/писать его Transform и цвет:
```lua
-- assets/scripts/spin.lua
function OnStart(entity)          -- необязательно, вызывается один раз
    log("Скрипт запущен для: " .. entity.Name)
end

function OnUpdate(entity, dt)     -- обязательно, вызывается каждый кадр
    entity.Transform.Rotation.y = entity.Transform.Rotation.y + dt * 45.0
end
```

`games/sandbox` показывает это на практике: один куб со `ScriptComponent`
крутится через `spin.lua`, привязанный напрямую через `ScriptEngine` (без
редактора) — доказательство, что скриптинг (и вся ECS-сцена) общая часть
движка, а не что-то специфичное для конкретной игры или для `SageEditor`.

### Пространства имён: `sage.<область>.<Функция>`

API был **плоской кучей**: 126 глобальных имён, где `SetIKFootLock`,
`SetWaterReflection` и `BorrowAnimations` лежали рядом и ничем не отличались от
функций самой игры. Плохо в этом не то, что некрасиво:

* подсказка редактора бесполезна — список из 126 несвязанных имён;
* узнать «что вообще есть про анимацию» можно только чтением исходника движка;
* игра, объявившая свою `Raycast`, **молча затирает движковую**.

Теперь каждая функция живёт в модуле:

```lua
sage.physics.Raycast(from, dir, 50.0)
sage.ik.SetFootLock(hero, 0, true)
sage.anim.PlayNamed(hero, "Walk", 0.2)
sage.reflect.SetWater(0.9)
sage.tween.Move(box, Vec3.new(0, 3, 0), 0.5)
```

Восемнадцать модулей: `scene`, `render`, `reflect`, `light`, `camera`, `input`,
`physics`, `anim`, `ik`, `ui`, `tween`, `fx`, `audio`, `time`, `msg`, `math`,
`app`, `core`.

**Старые имена продолжают работать и удалять их не планируется.** Все
существующие игры написаны на них, и ломать работающие скрипты ради порядка в
пространстве имён — цена без выгоды. Псевдоним ссылается на **ту же** функцию, а
не регистрируется вторым вызовом: две регистрации одного поведения — та же
болезнь, от которой уходим, только в новой форме. Тест проверяет это буквально —
`sage.ik.SetFootLock == SetIKFootLock`.

Определения разъехались по файлам `ScriptApi_*.cpp` — по файлу на область,
вместо одного `ScriptEngine.cpp` на 1800 строк, где, чтобы дописать строчку про
анимацию, приходилось листать интерфейс, физику и таймеры. Порядок регистрации
по-прежнему записан в ОДНОМ месте (`RegisterEngineApi`) и не зависит от того, в
каком файле лежит тело.

Что уже доступно скриптам из коробки: `entity.Name`, `entity.Transform`
(`.Position`/`.Rotation`/`.Scale`, каждое `Vec3` с полями `.x/.y/.z`),
`entity.Color`, функции `SpawnObject`/`FindObject`/`DestroyObject`,
`Schedule`/`Repeat`/`StartCoroutine`, доступ к камере/частицам/билбордам/аудио
(после соответствующих `Bind*`), функция `log(строка)`. Чтобы добавить свою
API-функцию — смотри `ScriptEngine::RegisterEngineApi()`, там пара строк на
sol2 на каждую привязку.

### Полный доступ к движку из скрипта

API не ограничен `Transform`/`Color` — скрипт общается со всеми системами
движка через ECS и с другими скриптами через сообщения:

- **Компоненты любой сущности** (в т.ч. чужой) — единый набор `Has*/Get*/Add*/
  Remove*` на каждый тип: `entity:AddLight()`, `entity:GetRigidBody()`,
  `entity:HasCollider()`, `entity:GetEmitter()`, `entity:GetCamera()`,
  `entity:GetRenderer()`, `entity:GetScript()`. `Get*` отдаёт компонент (или
  `nil`, если его нет), `Add*` создаёт и отдаёт ссылкой — правки идут прямо в
  состояние системы. Enum-значения именованы: `LightType.Spot`,
  `BodyType.Dynamic`, `ColliderShape.Capsule`.
- **Иерархия** прямо на объекте: `child:SetParent(parent)` / `child:Unparent()` /
  `entity:Parent()` / `entity:Children()` (таблица) / `entity:WorldPosition()` /
  `entity:Destroy()`.
- **Сообщения между скриптами** (событийная модель — компоненты общаются, не
  завязываясь на глобальные переменные): скрипт объявляет хук
  `OnMessage(entity, name, data)`, другой шлёт ему `SendMessage(target, name,
  data)` (target — объект или его `Id`) либо всем сразу `Broadcast(name, data)`.
  `data` — любое значение Lua (число/строка/таблица) или отсутствует.
- **Математика**: `Cross`/`Lerp`(число и `Vec3`)/`Clamp`/`Radians`/`Degrees`
  сверх арифметики `Vec*` (`+ - * /`, `Length`/`Normalized`/`Dot`).
- **Меш-примитивы**: `SetMeshCube`/`SetMeshSphere`/`SetMeshPlane`/
  `SetMeshCylinder`/`SetMeshCone`/`SetMeshNone` и `SetMeshModel(path)`.
- **Освещение сцены**: `GetLighting()` — солнце/ambient/туман
  (`GetLighting().Sun.Intensity = 0.2`, `GetLighting().Fog.Enabled = true`)
  для цикла дня и программной атмосферы.
- **Физика времени выполнения** (после `BindPhysics`, привязан в Play-режиме
  редактора и в рантайме игры): `SetVelocity(entity, v)` / `GetVelocity(entity)`
  для тела с `RigidBodyComponent` и `SetGravity(v)` для всего мира.

Пример «компоненты общаются» — дверь открывается по сообщению от кнопки:
```lua
-- door.lua
function OnMessage(entity, name, data)
    if name == "open" then entity.Transform.Position.y = 3.0 end
end
-- button.lua
function OnUpdate(entity, dt)
    if WasActionPressed("Use") then
        SendMessage(FindObject("Door"), "open")   -- адресно
        -- или Broadcast("open") — всем слушателям сразу
    end
end
```

### Игра ЦЕЛИКОМ на скриптах: модули, раскладка, мышь, параметры запуска

Всё выше позволяет написать поведение отдельной сущности. Чтобы на скриптах
можно было написать саму ИГРУ — а не украшение к игре на C++, — движок отдаёт
скриптам ещё четыре вещи. Каждая появилась из конкретной нехватки: без них
воксельная игра от первого лица [The Boat](https://github.com/AmckinatorStudios/The-Boat)
не писалась в принципе.

- **Модули**: `require "voxel"` подтягивает соседний `.lua` из папок, которые
  хост добавил через `ScriptEngine::AddScriptSearchPath` (рантайм и Play-режим
  редактора добавляют `assets/scripts` открытого проекта). Модуль загружается
  ОДИН раз на `ScriptEngine`, поэтому общий код и общее состояние мира
  действительно общие для всех скриптов. Загрузка нативных модулей отключена
  намеренно (`package.cpath` пуст), `io`/`os` скриптам по-прежнему закрыты.
- **Раскладка из игры**: `BindAction("Jump", "SPACE")`,
  `BindAction("Move Forward", {"W", "UP"})`, `BindAction("Break", "MOUSE_LEFT")`
  заводят именованные действия прямо из Lua — дальше их читает тот же
  `IsActionDown`/`WasActionPressed`, что и код на C++. Имена клавиш — из
  `core/KeyNames.h`. Раньше объявить действие мог только хост, и игра на
  скриптах не могла завести ни одной своей клавиши.
- **«Сырой» ввод**: `GetMouseDelta()`, `GetMousePosition()`, `GetScrollDelta()`,
  `SetMouseCaptured(true)`, `IsMouseCaptured()` — обзор от первого лица пишется
  скриптом. Именованные действия дискретны и обзора не дают; см.
  `core/RawInput.h` и `ScriptEngine::BindRawInput`.
- **Параметры запуска**: `LaunchArg("seed")` и `LaunchFlag("autopilot")`. Хост
  наполняет их из командной строки (`SagePlayer <проект> --seed=42`) и
  переменной `SAGE_GAME_ARGS`. Без них игра на скриптах не могла узнать НИЧЕГО
  о том, как её запустили: `os` ей закрыт, а зерно мира, режим отладки и
  автопрогон для CI задаются снаружи.

```lua
-- Вид от первого лица целиком на скрипте: ни строчки C++.
function OnStart(entity)
    BindAction("Move Forward", {"W", "UP"})
    SetMouseCaptured(true)
end

function OnUpdate(entity, dt)
    local look = GetMouseDelta()
    yaw = yaw - look.x * 0.11
    pitch = math.max(-89, math.min(89, pitch + look.y * 0.11))
    if IsActionDown("Move Forward") then --[[ ... ]] end
end
```

Ввод, звук и пути модулей одинаково привязаны и в собранной игре
(`runtime/PlayerLayer`), и в Play-режиме редактора — превью играется ровно как
игра. В редакторе ввод уходит игре только при фокусе панели **Game**
(см. `editor/src/EditorPlayInput.h`): иначе `WASD` уезжал бы в игрока прямо
во время переименования сущности, а захваченный курсор не давал бы нажать ни
одной кнопки редактора. `Esc` возвращает курсор, не выходя из Play.

Всё это покрыто модульными тестами (`tests/test_scripting.cpp`): компоненты,
иерархия, сообщения (адресные/широковещательные/с полезной нагрузкой),
математика, доступ к освещению, модули `require` (в том числе общее состояние
между скриптами), параметры запуска, `BindAction` и «сырой» ввод.

## Твины (интерполяция значений)
`sage/core/Tween.h` — система inbetweening: плавно ведёт значение из A в B за
`duration` секунд по кривой сглаживания, без ручного лерпа в каждом `OnUpdate`.

- **Кривые** (`sage::Easing`): Linear, Quad/Cubic/Sine In/Out/InOut, ExpoOut,
  **BackOut** и **ElasticOut** (пружинят с перелётом за цель), **BounceOut**.
  `Ease(e, t)` — чистая функция, покрыта юнит-тестами.
- **`TweenManager`**: `To<T>(from, to, dur, ease, setter, onComplete, delay,
  loop)` — интерполирует float/vec2/vec3/vec4 (glm::mix) и кватернионы (slerp);
  `TweenLoop` None/Restart/**PingPong**; `Cancel`/`CancelAll`. Твины,
  добавленные из коллбека, безопасно копятся в pending (без порчи вектора).
  Движком твинов владеет `ScriptEngine` — они тикают со скриптами (`UpdateAll`),
  замирают на паузе и умирают на Stop.
- **Из Lua**: `TweenMove(entity, target, dur[, Ease.X])`, `TweenScale`,
  `TweenRotate`, `TweenColor`, `TweenUIValue` (полоса/значение UI); сеттеры
  проверяют `Valid()` — уничтоженная в полёте сущность безопасно пропускается.
  `TweenCancel(id)`/`TweenCancelAll()`/`ActiveTweens()`. Пример — пружинистое
  появление монеток в `games/testgame` (`pickup_bob.lua`, `Ease.BackOut`).
- Покрытие: `tests/test_tween.cpp` (кривые, интерполяция, delay, ping-pong,
  cancel, добавление из коллбека) + Lua-интеграция в `tests/test_scripting.cpp`.

## Текстуры и модели
Часть ЯДРА движка (`engine/src/sage/render/Texture.*`, через stb_image) —
грузит PNG/JPG/BMP/TGA в GPU-текстуру через текущий RHI-бэкенд:

```cpp
Texture myTexture("assets/textures/что-то.png", TextureFilter::Trilinear);
myTexture.Bind(0);
shader.SetInt("uTexture", 0);
shader.SetInt("uUseTexture", 1); // если 0 — рендер работает по-старому, только цветом
```

`TextureFilter` — 4 режима, выбираются явно при загрузке:

| Режим | Когда использовать |
|---|---|
| `Nearest` | Пиксельная чёткость без сглаживания — текстурные атласы, pixel-art |
| `Bilinear` | Простое сглаживание без перехода между уровнями мипмапов |
| `Trilinear` | Сглаживание + плавный переход между мипмапами — стандартный выбор по умолчанию |
| `Anisotropic` | Как Trilinear, плюс убирает размытость на поверхностях под острым углом к камере (типично — земля/пол, если смотреть почти вдоль неё) |

Уровень анизотропии запрашивается автоматически: движок узнаёт максимум,
который поддерживает видеокарта (`Texture::MaxSupportedAnisotropy()`), и
использует `min(4.0, максимум)`. `Anisotropic`/`Trilinear` требуют мипмапов и
включают их автоматически. Для атласов (несколько текстур в одном файле,
разные UV-прямоугольники на разные части меша) мипмапы нужно отключать
(`generateMipmaps=false`) вместе с `Nearest` — иначе на дальних объектах
мипмапы «усредняют» цвет с соседними тайлами атласа (протекание цвета на
границах).

**Загрузка 3D-моделей** (`engine/src/sage/render/Model.*`) — форматы OBJ+MTL
(через tinyobjloader) и GLTF/GLB (через tinygltf, включая встроенные как
base64 текстуры), автоопределение по расширению файла:

```cpp
auto model = Model::Load("assets/models/dragon.glb"); // или .obj, или .gltf
shader.Use();
shader.SetMat4("uModel", transformMatrix);
model->Draw(shader); // сама переключает текстуру/цвет между подмешами (submesh)
```

Известные ограничения: только `pbrMetallicRoughness.baseColorTexture` (normal
maps/metallic-roughness/emissive пока не читаются), OBJ без переиспользования
вершин. Это путь для СТАТИЧЕСКОЙ геометрии (`Model`); скелетные меши с анимацией
из glTF грузит отдельный путь `SkinnedModel::Load` — см. `## Скелетная анимация`.

## Наборы интерфейса: спрайты из листа, девятина, пиксель-арт
Готовый UI-набор с itch.io — это один PNG на всё: рамки, кнопки, слоты, иконки
и шкалы лежат в общем листе. Чтобы такой набор можно было ВЗЯТЬ И
ИСПОЛЬЗОВАТЬ, движку нужны три вещи; без любой из них набор приходится резать
на сотню файлов вручную и всё равно получать мыло.

* **Спрайт — кусок листа в ПИКСЕЛЯХ исходника.** `Sprite = {x, y, w, h}` у
  `UI Element` (в Lua — `SetUISprite`). Именно в пикселях, а не в UV: в
  документации набора написано «26x26 начиная с (52,0)», и переводить это в
  доли текстуры должен движок.
* **Девятина (9-slice).** Панель нарисована как 26x28 с уголками по 8 пикселей.
  Растянуть её на 372x240 обычным квадом нельзя — углы размажутся вместе с
  серединой. `SliceBorder = {лево, верх, право, низ}` режет спрайт на девять
  кусков: углы рисуются как есть, края тянутся по одной оси, середина по обеим.
  `PixelScale` — во сколько раз пиксель исходника крупнее экранного (для
  пиксель-арта целое, иначе рамка идёт волнами).
* **Пиксель-арт.** `PixelArt` грузит текстуру как `Nearest` без мипмапов.
  Сглаживание превращает такой набор в кашу, а мипмапы ЛИСТА ещё и подмешивают
  в края соседний спрайт. Фильтрация запоминается вместе с текстурой, и запрос
  той же картинки с другими настройками пересоздаёт её на месте.

```lua
SetUIImage(panel, "assets/ui/basic.png", true) -- true = пиксель-арт
SetUISprite(panel, 11, 11, 26, 28)             -- кусок листа
SetUISlice(panel, 8, 8, 8, 9, 3)               -- углы + масштаб пикселя
local w, h = ImageSize("assets/ui/basic.png")  -- размер листа для нарезки
```

Всё это настраивается и в инспекторе редактора (секция Image у `UI Element`),
и рисуется одинаково в редакторе и в собранной игре.

**Шрифт интерфейса** задаётся в настройках (`ui.font`, `ui.fontPixelHeight`,
`ui.fontPixelArt` в `sage.cfg`), потому что `UIRenderer` создаёт движок и у игры
нет места, где вклиниться до первого кадра.

* `fontPixelArt` — шрифт нарисован по пикселям: атлас берётся `Nearest`, без
  мип-уровней, а масштаб на отрисовке округляется до ЦЕЛОГО. Полупиксельное
  увеличение растягивает одни штрихи буквы на два экранных пикселя, а соседние
  на один — «M» выходит с ножками разной толщины, и весь текст идёт волнами.
* Символы, которых в шрифте НЕТ, в атлас не попадают: иначе stb запекает для
  них `.notdef` (рамка или «?»), глиф выглядит настоящим, и «шрифт не знает
  кириллицы» становится неотличимо от «знает». При загрузке шрифта без
  кириллицы движок предупреждает в лог — иначе русские надписи молча
  превращаются в ряд вопросительных знаков, и ошибку ищут в движке.
* Межстрочный интервал берётся у ШРИФТА (`UIRenderer::LineHeight`), а не из
  номинальной высоты строки: на пиксельном шрифте с целым масштабом глиф вдвое
  выше номинала, и абзац, разложенный по номиналу, налезает сам на себя.

## Интерактивный интерфейс: поля ввода, галки, ползунки
Рисовать интерфейс мало — в него надо тыкать. `sage::ui::UpdateSceneUI(scene,
input, w, h)` за кадр разбирает подсветку, нажатия, фокус, набор текста и
перетаскивание, и возвращает, что интерфейс СЪЕЛ:

```cpp
sage::ui::UIInputState in;   // мышь + символы от оконной системы
in.Mouse = {mx, my}; in.MousePressed = pressed; in.TypedText = typed;
sage::ui::UIInputResult r = sage::ui::UpdateSceneUI(scene, in, w, h);
if (r.WantsMouse) { /* игре этот щелчок не отдаём */ }
```

Виды элементов: `Input` (поле ввода — подсказка, предел длины, режим пароля,
мигающий курсор), `Checkbox`, `Slider` — плюс прежние `Panel/Label/Image/Bar/
Icon`. Любому из них флаг `Interactive` включает подсветку и нажатие, `Enabled`
— выключает; `SpriteHover`/`SpritePressed` подменяют спрайт под состояние (в
наборах кнопка нарисована трижды, и подменить картинку правильнее, чем
осветлить основную). Скрипт читает `Clicked`/`Changed` — флаги на ОДИН кадр.

Три решения, без которых это не работает:

* **Ввод приходит СТРУКТУРОЙ, а не опросом устройств внутри UI.** Интерфейс
  живёт и в игре, и в панели Game редактора (там мышь пересчитана в панель), и
  в тестах без окна. Опрашивай он устройства сам — он был бы привязан к GLFW, а
  редактор не смог бы отдать ему свои координаты. Заодно весь интерактив
  тестируется без единого окна (см. `tests/test_ui.cpp`).
* **Текст приходит СИМВОЛАМИ, а не клавишами.** Раскладка, Shift, мёртвые
  клавиши и композиция превращают нажатия в символы по правилам системы;
  повторять их в движке — значит получить ввод, работающий только на английской
  раскладке. Курсор при этом ходит по СИМВОЛАМ UTF-8, а не по байтам: шаг в
  байт разрезал бы кириллическую букву пополам.
* **Щелчок — это нажать И отпустить НА элементе.** Увести курсор с кнопки и
  отпустить — общепринятый способ передумать, и ломать его нельзя.

`WrapText` переносит длинный текст по ширине элемента (по словам, слишком
длинное слово — по символам) и обрезает его своим прямоугольником, если он не
влез по высоте: абзац, вылезший из панели на фон, выглядит хуже обрезанного и
читается как ошибка вёрстки.

**Сглаживание краёв** считается по производной SDF (`fwidth`), а не по
константе: константа верна ровно при одном масштабе интерфейса, на другом край
получается либо зубчатым, либо мыльным.

## Прозрачность и свои шейдеры материала
Две вещи, без которых нельзя нарисовать воду, стекло или листву, — и обе
устроены так, чтобы НЕ отменять инстансный батчинг: тысяча полупрозрачных
плиток и тысяча объектов со своим шейдером остаются одним draw call'ом каждая.
Без этого и то и другое было бы неприменимо ровно там, где нужно чаще всего.

**Альфа.** `opacity` материала и `MeshRenderer.Opacity` сущности перемножаются
(`EffectiveOpacity`); меньше 1 — объект уходит в полупрозрачный проход:

- рисуется ПОСЛЕ всей непрозрачной геометрии, отсортированный от дальних к
  ближним (смешивание не коммутативно: стекло, нарисованное раньше того, что за
  ним, просто закрасит его собой);
- глубина ЧИТАЕТСЯ, но не пишется — прозрачное прячется за стеной, но не
  закрывает собой другое прозрачное;
- подряд идущие объекты одного меша и материала всё равно рисуются пачкой:
  непрозрачность едет в инстансе (`iAlpha`, локация 12), а не в юниформе;
- `doubleSided` материала (по умолчанию `true`) решает, рисовать ли задние
  грани. Листве и «плоскому» стеклу они нужны; у ЗАМКНУТОГО тела (плитка воды,
  стеклянный ящик) двусторонность означает два слоя смешивания на объект — цвет
  темнеет вдвое, а по стыкам идёт сетка;
- тень полупрозрачный объект отбрасывает только при непрозрачности ≥ 0.5: карта
  теней бинарна и «половину тени» не умеет.

Из скрипта: `SetOpacity(entity, 0.6)` / `GetOpacity(entity)`; в редакторе —
ползунок **Opacity** в Mesh Renderer и в редакторе материала.

**Свой шейдер.** Материал может нести пару `.vert`/`.frag` — и остаётся
полноценным объектом сцены: освещение, тени, GI, туман, отсечение по фрустуму,
инстансинг. Прозрачность своим шейдером не отменяется: полупрозрачная группа
идёт в тот же проход и сортируется ВНУТРИ СЕБЯ, инстанс за инстансом, оставаясь
одним draw call'ом.

```json
{ "opacity": 0.82, "doubleSided": false,
  "vertexShader": "assets/shaders/water.vert",
  "fragmentShader": "assets/shaders/water.frag",
  "params": { "uWaveHeight": 0.53, "uFoamColor": [0.92, 0.98, 1.0] } }
```

```lua
SetMaterial(entity, "assets/materials/water.sagemat")
SetMaterialParam("assets/materials/water.sagemat", "uFocus", Vec3(x, 0, z)) -- общая
SetShaderParam(entity, "uWaveHeight", 0.6)                                 -- штучная
```

Готовое PBR-освещение подключается строкой `#include <sage_pbr>` — движок
подставляет тот же блок, которым рисует всё остальное, так что свой шейдер не
расходится со сценой по свету. Правка `.vert`/`.frag` подхватывается редактором
на лету (сверка mtime раз в кадр); шейдер с ошибкой компиляции НЕ заменяет
рабочий — в сцене остаётся прежняя версия, ошибка уходит в лог. Полный контракт
(локации атрибутов, стандартные юниформы, ограничения) — `docs/custom_shaders.md`.
Обкатано на воде «The Boat»: 2809 плиток, волна и пена в шейдере, один draw call.

## Skybox
Часть ЯДРА движка (`engine/src/sage/render/Skybox.*`) — кубическая (cubemap)
текстура, создающая иллюзию бескрайнего неба вокруг сцены:

```cpp
Skybox skybox({
    "assets/textures/skybox/px.png", "assets/textures/skybox/nx.png",
    "assets/textures/skybox/py.png", "assets/textures/skybox/ny.png",
    "assets/textures/skybox/pz.png", "assets/textures/skybox/nz.png"
});
// каждый кадр, ПЕРВЫМ (до остальной сцены):
skybox.Draw(skyboxShader, view, projection);
```

Технически: из view-матрицы перед отрисовкой убирается позиция камеры
(скайбокс реагирует на поворот, но не двигается при перемещении); вершинный
шейдер даёт глубину 1.0 через `pos.xyww`, что вместе с `DepthFunc::LessEqual`
гарантирует, что скайбокс всегда позади сцены независимо от порядка отрисовки;
backface culling на время отрисовки выключается (куб рисуется изнутри).
`GL_TEXTURE_CUBE_MAP_SEAMLESS` включается один раз при инициализации RHI-девайса
— без этого на стыках граней cubemap виден шов.

## Частицы (billboard-эффекты)
Система частиц (`engine/src/sage/render/ParticleSystem.*`) — инстансные
billboard-частицы (всегда развёрнуты к камере) для огня/дыма/искр/всплесков.
Один draw call на все живые частицы; встроенный шейдер (мягкий круг/квад) —
частицы рисует кто угодно без ассетных шейдеров:

```cpp
particles.Update(dt);
particles.DrawFromView(view, proj); // camRight/Up берутся из матрицы вида
```

**В ECS/редакторе.** Повесь `ParticleEmitterComponent` (см. `## ECS`): готовый
пресет (`ParticlePresets::Registry` — Fire/Smoke/Sparks/Water Splash/Embers/
Block Break) плюс тонкая настройка (скорость/гравитация/время жизни/размер/цвет/
разлёт/эмиссия). `Continuous` — непрерывная струя (частиц/сек), иначе —
периодические залпы. Система `sage::fx::UpdateEmitters` (`ParticleECS.h`) рождает
частицы в позиции `Transform` каждого эмиттера в общий пул, которым владеет слой
(редактор/рантайм/игра) и рисует одним вызовом. Параметры сериализуются в
`.sage`. В редакторе: секция **Particle Emitter** в Inspector, меню **Entity →
Create Particle Emitter**, гизмо-маркер эмиттера, живое превью в вьюпорте. Живой
пример — факел в `games/testgame` (комната 1).

## Пост-процессинг (HDR: SSAO + Bloom + тон-маппинг)
Часть ЯДРА рендера. Сцена рисуется не в экран напрямую, а в offscreen HDR-буфер
(`Framebuffer` — float-цвет + **depth-текстура**, значения могут выходить за
[0,1]). Затем `PostFX` (`engine/src/sage/render/PostFX.h`, встроенные шейдеры)
прогоняет полную цепочку эффектов:
- **SSAO** (screen-space ambient occlusion) — из depth-текстуры сцены
  реконструирует вид-позиции и нормали (по производным), полусферическая
  выборка 16 сэмплов + размытие; затемняет щели/контакты. Радиус/сила настраиваются.
- **Bloom** — bright-pass (выделение ярких участков выше порога) + separable
  Gaussian-размытие на половинном разрешении, добавляется к кадру (свечение).
- **Финальный composite** — экспозиция + ACES тон-маппинг + AO + bloom +
  насыщенность/контраст + **виньетка** + гамма.

Параметры — `PostFXSettings` (мапятся из `EngineConfig`: `bloom`/`bloomThreshold`/
`bloomIntensity`/`ao`/`aoStrength`/`aoRadius`/`vignette`/`exposure`/…,
сериализуются в `sage.cfg`, правятся в панели редактора **Config → Post-Process**).
`PostFX` реюзабелен (один экземпляр на вьюпорт), пишет либо в экран (игры), либо
в `Framebuffer` (вьюпорт/Game-панель редактора). UI рисуется ПОСЛЕ прохода,
чтобы не тон-мапиться со сценой. Подключено в редакторе (Viewport и Game) и
`games/testgame`; старый `PostProcess` (только тон-маппинг) оставлен для простых
игр.

## Порядок кадра (планировщик систем)

`engine/src/sage/core/SystemScheduler.h`. Порядок «скрипты → физика → анимация
→ частицы → звук» был записан РУКАМИ в каждом потребителе: рантайм, редактор,
игры. Копии разошлись — и не гипотетически: в `games/testgame` скрипты
вызывались ПОСЛЕ шага физики, то есть заданная скриптом скорость применялась на
кадр позже, чем в рантайме. Такую разницу невозможно заметить в редакторе и
мучительно ловить в игре, потому что «иногда управление немного залипает» — это
не сообщение об ошибке.

Ровно та же болезнь уже была у проходов рендера, и там её вылечил
`ScenePasses`. Здесь то же лекарство для логики кадра:

```cpp
sage::SystemScheduler sched;
sage::RegisterCoreSystems(sched, {.Scripts = &scripts, .Physics = &physics});
sched.Add(sage::Stage::Update, "мойИИ", [](Scene& s, float dt) { ... });
sched.Run(scene, dt);                       // каждый кадр
```

**Стадии фиксированы, порядок внутри стадии — числом.** Свободный список «систем
с приоритетами» выглядит гибче, но означает, что порядок зависит от того, кто в
каком порядке зарегистрировался, — а именно этого мы и избегаем. Стадия
отвечает на вопрос «до или после физики», и ответ не должен зависеть от порядка
вызовов `Add`.

Что это дало сразу, помимо единого порядка:

* **Игра и плагин могут добавить свою систему в кадр.** Раньше вписать её было
  некуда — только руками в тело каждого слоя.
* **Упавшая система не уносит кадр.** Исключение ловится, остальные системы
  отрабатывают, сообщение уходит в лог: одна опечатка в Lua обязана стоить
  строки в консоли, а не чёрного экрана.
* **Время каждой системы за кадр.** Профайлер движка знает только «Обновление»
  целиком; здесь видно, КАКАЯ система съела кадр, — первый вопрос при просадке.
* **Повторная регистрация заменяет, а не дублирует.** Перезапуск Play
  переподключает скрипты и физику; без замены каждый заход удваивал бы шаг
  физики, и мир пошёл бы вдвое быстрее.

Редактор пользуется этим же планировщиком, и разница режимов выражена явно: в
правке зарегистрированы только анимация и частицы (превью — художник должен
видеть движение модели, не запуская игру), а скрипты с физикой добавляются на
входе в Play и снимаются на выходе.

## Отражения

`engine/src/sage/render/Reflection.h`. До этого непрямой свет в движке был
только диффузным: `ambient` умножал albedo и на этом заканчивался. Металл в
такой модели невозможен физически — у металла нет диффузной составляющей
вообще, весь его вид и есть отражение окружения. Хромовый шар выходил ровным
серым пятном, мокрый асфальт — сухим, вода — крашеной плоскостью, и настройками
света это не лечилось: отражать было нечего, потому что окружение нигде не
хранилось.

Источников два, и они складываются по убыванию точности.

**Карта окружения (cubemap)** — фундамент. Знает всё вокруг, включая то, что за
камерой, но снята из ОДНОЙ точки. Мипы здесь не «уменьшенные копии для
экономии», а шкала размытия: зеркало берёт нулевой, матовая краска — дальний,
мип выбирается шероховатостью. Снимается двумя способами:

```cpp
sage::render::ReflectionSystem reflections;
reflections.UpdateSky(sky, env);            // только небо: шесть заливок градиентом
reflections.CaptureScene(pos, 0.1f, 60.0f,  // вся сцена: шесть проходов геометрии
                         [&](const glm::mat4& v, const glm::mat4& p) { /* рисуем */ });
reflections.SetBox(min, max);               // коробка влияния (параллакс-коррекция)
```

Пересъёмка — по ИЗМЕНЕНИЮ, а не по расписанию: небо переснимается, когда
поменялись его цвета, зонд — по явной просьбе. Шесть проходов сцены на кадр не
потянет никто, а «снять один раз» — это неверное отражение сразу после первого
заката.

Параллакс-коррекция нужна потому, что куб снят из одной точки, а смотрят на него
из разных: без поправки отражение «плывёт» при движении камеры, как будто
окружение приклеено к объекту. Поправка ищет пересечение отражённого луча с
коробкой влияния зонда и берёт направление уже к точке пересечения.

**Зонды отражений** (`ReflectionProbeComponent`) — компонент, а не настройка
сцены, ровно потому, что зондов нужно несколько: в трюме отражается трюм, на
палубе — палуба и небо, и снять это одной картой из одной точки нельзя. Какой
зонд действует, решается по положению камеры: сначала тот, в чьей коробке она
стоит (из нескольких — самый тесный, он подробнее), иначе ближайший.

Один зонд на кадр — не от лени: активная карта уходит в шейдер одним
`samplerCube`, а смешивать два пришлось бы либо вторым сэмплером (юниты в GL 3.3
на пересчёт), либо вторым проходом. Резкого переключения при этом не видно
именно потому, что выбирается зонд, В КОРОБКЕ которого камера, — переход
происходит на границе комнаты, где отражение и так меняется.

Снятая карта НЕ сериализуется: она пересобирается из той же геометрии и того же
неба, а шесть картинок на зонд в проекте устаревали бы от любой правки уровня.
За кадр снимается не больше одного зонда — съёмка это шесть проходов сцены, и
снять десяток разом означало бы застывший на секунду редактор ровно в тот
момент, когда художник двинул свет.

В редакторе зонд рисуется маркером и КОРОБКОЙ ВЛИЯНИЯ (коробка важнее маркера:
именно она отвечает на вопрос «какой зонд подхватит камера здесь», а по числам
в инспекторе на него не ответить). Не снятый зонд — тускло-красный: «здесь
будет отражение, но его ещё нет».

**Кубическая карта неба** как источник отражений: если у сцены задан
`Skybox.CubemapDir`, в карту отражений уходит ОН, а не процедурный градиент.
Иначе сцена с настоящим небом отражала бы совсем другое небо, и расхождение
было бы заметнее всего на воде и хроме — там, где отражение и смотрят.

**Плоское отражение** — сцена, отрисованная зеркально относительно плоскости.
Точное и полное, ценой второго прохода геометрии, но ровно для одной плоскости:
вода, зеркало, мокрый пол.

```lua
SetWaterReflection(0.55)          -- плоскость y = 0.55
SetPlanarReflection(n, point)     -- произвольная плоскость
SetPlanarReflectionScale(0.5)     -- доля разрешения кадра
```

Читается оно по ЭКРАННОЙ позиции пикселя — не для простоты: проекция у
отражённого вида та же, поэтому точка на плоскости попадает в тот же пиксель,
что и её отражение, и совпадение получается точное, а не подогнанное. Три
места, где это ломается, если не позаботиться, и все три пришлось чинить:

* **Обход треугольников.** Отражение выворачивает пространство наизнанку, и
  лицевые грани становятся изнаночными — без смены отсечения в зеркале видны
  внутренности моделей.
* **Геометрия под плоскостью.** В отражении она не участвует, но честно
  рисуется и перекрывает нужное. Отсекается косой ближней плоскостью (oblique
  near plane): проекция правится так, что ближней плоскостью отсечения
  становится сама плоскость отражения.
* **Зеркало в собственном отражении.** Вода рисуется внутри своего же
  отражения и застилает его: в зеркале оказывается слой воды, сквозь который
  сцена едва просвечивает. Поверхности с `Material::PlanarReflectivity > 0`
  выбрасываются из зеркального прохода. Дефект нашёлся не глазами, а выводом
  буфера отражения на экран — в обычном кадре он читается как «отражение
  какое-то мутное».

**Специфика BRDF.** Зеркальная составляющая считается по «split-sum»
приближению Karis. Второй множитель обычно берут из запечённой LUT-текстуры;
здесь вместо неё аналитическая аппроксимация Lazarov — она укладывается в
несколько операций, не занимает текстурный юнит (их в GL 3.3 шестнадцать, и
четыре уже съедены каскадами теней) и не требует шага запекания, без которого
движок был бы неработоспособен «из коробки». Диффузный непрямой свет теперь
берёт только ту долю, что не ушла в отражение, и у металла её нет вовсе — это
вторая половина того же исправления.

**Чего здесь нет и почему.** Экранных отражений (SSR). В отложенном рендере они
почти бесплатны: нормаль и шероховатость уже лежат в G-буфере, а отражение
подмешивается после сцены. У движка рендер прямой, и оба доступных варианта
платят ровно теми артефактами, ради борьбы с которыми SSR и берут: считать SSR
ДО сцены можно только по цвету ПРОШЛОГО кадра — отражение отстаёт от движения
на кадр и «плавает»; считать ПОСЛЕ — не по чему, шейдер уже не знает, где какая
шероховатость. SSR — это решение, которое принимают вместе со сменой типа
рендера, а не галочка.

**Проверяется** шестью рендер-тестами: цвета неба на зеркальном шаре против их
отсутствия без карты, монотонность размытия по шероховатости, Френель
(диэлектрик отражает слабее металла), ориентация граней куба (красная стена
обязана отразиться с той стороны, где стоит), отсутствие шва на стыках граней и
геометрия зеркального пола — предмет над зеркалом в нём есть, предмет под
зеркалом в нём отсутствует, отражение стоит под предметом, а не сбоку.

## Версия формата сцены и миграции

`sage_scene_version` писался в файл с самого начала и **никогда не читался**.
Это худший из вариантов: он создаёт впечатление, что о совместимости
позаботились, а на деле первое же ломающее изменение формата тихо испортило бы
все старые сцены — без ошибки, без предупреждения, просто «объекты почему-то не
там».

Теперь файл несёт номер, а загрузчик прогоняет его через цепочку миграций до
текущей. Каждая миграция — маленькая функция «из N в N+1», которая правит
**JSON, а не сцену**: правка на уровне JSON не зависит от того, как сегодня
выглядят компоненты, и потому не устаревает вместе с ними. Иначе миграцию
пришлось бы переписывать каждый раз, когда меняется структура, ради которой она
и была написана.

Три правила, каждое проверено тестом:

* **Нет номера — значит версия 1.** Сцены, сохранённые до появления проверки,
  не за что винить, и загружаться они обязаны.
* **Файл новее движка — отказ, а не половинчатое чтение.** Половина полей
  такому движку незнакома, и молча потерять их хуже, чем честно отказаться.
* **Миграция идемпотентна.** Повторный прогон актуального файла не меняет
  ничего: иначе сохранение-загрузка по кругу дрейфовали бы, а это самый
  неприятный вид порчи данных — медленный и незаметный.

Версия растёт при ЛОМАЮЩЕМ изменении. Добавление необязательного поля её не
двигает: старые файлы читаются без него как раньше.

## Префабы и сохранения игры

### Префабы: сущность как шаблон

Префаб — сущность с потомками, сохранённая в `.sageprefab`. Формат тот же, что
у сцены: префаб — это мини-сцена с одним корнем, и потому у него бесплатно
появляются и загрузчик, и миграция версий. Отдельный формат означал бы второй
сериализатор, который надо держать в согласии с первым, и первое же новое поле
компонента разошлось бы между ними.

В редакторе: `Save as Prefab` в контекстном меню иерархии, двойной клик по
файлу в панели Assets ставит копию в сцену.

У префаба есть **3D-обложка** — такая же, как у материала, и по той же причине.
Материал показывался квадратиком цвета, префаб — синим прямоугольником с
надписью PREFAB, одинаковым у всех: чем «Ящик_02» отличается от «Ящик_03»,
можно было узнать, только поставив оба в сцену. Обложка снимается тем же
проходом, что и вьюпорт, с фиксированным студийным светом; префаб для неё
разбирается тем же `InstantiatePrefab`, что и для настоящей сцены (отдельный
«облегчённый разбор для картинки» означал бы второй загрузчик префабов, и
обложка расходилась бы с тем, что человек получит в мире). В инспекторе она
крупная и вращается мышью. Модели (`.obj`/`.gltf`/`.glb`/`.sagemesh`) получают
обложку там же и так же.

У каждой обложки СВОЙ буфер (см. `key` в `editor/src/AssetPreview.h`). Это не
мелочь: обложки снимаются по одной за кадр и запоминаются, а показываются все
сразу, и с общим буфером все запомненные хендлы указывали бы на одну текстуру —
вся папка показывала бы то, что нарисовали последним. Пока обложка была только
у материала и в папке он лежал один, это было незаметно.

**Чего не было и что чинилось.** Код префабов жил внутри `EditorLayer.cpp`, в
безымянном пространстве имён, и потому был недоступен никому, кроме редактора.
Для игры про постройку из блоков это значит, что главной её операции — поставить
заготовленный объект в мир — из скрипта не существовало: игра либо собирала
объект по компонентам вручную при каждом спавне, либо не собирала вовсе.
Реализация переехала в `sage/scene/Prefab.h`, а редактор стал ещё одним её
потребителем, наравне с Lua:

```lua
local id = sage.scene.SpawnPrefab("assets/turret.sageprefab", Vec3.new(3, 0, 4))
sage.scene.SavePrefab(id, "assets/turret_v2.sageprefab")
```

Разобранный префаб **кэшируется** по пути: игра, которая ставит тысячу блоков,
иначе тысячу раз разбирала бы один и тот же JSON — а это самая частая операция
такой игры.

Рантайм-поля копии сбрасываются: тело физики, сустав, поза анимации, снятая
карта отражений и накопитель частиц принадлежат ЭКЗЕМПЛЯРУ, а не шаблону.
Скопируй их как есть — и две сущности делили бы один дескриптор тела, а удаление
одной уносило бы физику другой.

### Сохранения: прогресс игрока, а не сцена

Сериализовалась только сцена — **редакторный формат**. Прогресс игрока сохранять
было нечем, и игре оставалось либо писать файлы в обход движка, либо не
сохраняться вовсе.

Разница принципиальна. Сцена — исходник: какие объекты в уровне, где стоят,
какие компоненты. Она одинакова у всех игроков и лежит рядом с игрой. Прогресс —
противоположное: принадлежит одному человеку, меняется каждую минуту и не имеет
отношения к расстановке объектов в редакторе. Сохранять прогресс сериализацией
сцены значит записывать в файл игрока всю геометрию уровня и при загрузке
подменять ему уровень на тот, что был при сохранении: **любая правка игры
перестаёт доходить до тех, кто уже начал играть**.

```lua
sage.save.Write("main", {
    day = 12, hp = 80, name = "Робинзон",
    inventory = {"доска", "верёвка"},
    base = { x = 3, y = 0, z = -7 },
}, 1)                                  -- последний аргумент — версия формата

local s = sage.save.Read("main")       -- таблица или nil
for _, slot in ipairs(sage.save.Slots()) do   -- для меню «Продолжить»
    print(slot.name, slot.savedAt, slot.version)
end
```

* **Где лежит.** В пользовательском каталоге (`$XDG_DATA_HOME` / `~/.local/share`,
  на Windows `%APPDATA%`), а не рядом с игрой: папка установки бывает доступна
  только на чтение (Program Files, каталог Steam), и запись туда либо молча не
  проходит, либо требует прав, которых у игры нет.
* **Как пишется.** Во временный файл, затем переименование поверх старого.
  Переименование в пределах тома атомарно, и это единственный способ пережить
  падение посреди записи: иначе игрок теряет не текущее сохранение, а ВСЁ —
  файл остаётся обрезанным, а прошлого уже нет.
* **Версия формата** у каждого слота — та же дисциплина, что у сцен. Игра меняет
  структуру прогресса чаще, чем формат уровней.
* **Нет слота — `nil`, а не пустая таблица.** «Сохранения нет» и «сохранение
  пустое» — разные вещи; спутав их, новый игрок попадает в конец игры с нулями.
* **Имя слота обеззараживается.** Оно приходит из поля ввода или имени
  персонажа, и `../../.bashrc` означал бы запись за пределы папки сохранений.
* **Циклы в таблицах не роняют игру.** `t.self = t` ловится по факту повторной
  встречи, а не глубиной рекурсии: каждый уровень держит открытый обход таблицы,
  и три десятка вложенных обходов переполняют стек Lua — причём падает игра не
  на сохранении, а позже, при закрытии состояния.

The Boat пользуется этим по-настоящему: построенная лодка (168 блоков в
проверочном прогоне), инвентарь, голод/жажда/тепло, время суток и пройденный
путь пишутся автосохранением раз в полминуты и восстанавливаются при следующем
запуске. Автосохранение по таймеру, а не по событию «поставил блок»: блоки
ставят пачками, и запись на каждый означала бы сотни записей в минуту.

## Свои форматы ассетов и импорт из чужих

### Зачем свой формат

Чужие форматы — `.obj`, `.gltf`, `.blend`, `.bbmodel`, `.png` — это форматы
ОБМЕНА. Они описывают то, что удобно программе-источнику, и платят за
универсальность. `.obj` — текст, где каждое число разбирается из строки;
`.gltf` — JSON плюс отдельный бинарник; `.blend` — дамп памяти Blender'а;
`.png` разжимается в полный RGBA-буфер, который целиком уезжает в видеопамять.

Ни один из них не описывает то, что нужно движку В МОМЕНТ ЗАГРУЗКИ: готовый к
заливке в видеопамять буфер. Поэтому загрузка модели — это всегда разбор,
пересборка и пересчёт, заново при каждом запуске игры, хотя результат каждый
раз один и тот же.

### Контейнер (`sage/assets/format/Blob.h`)

Один контейнер на все свои типы: заголовок, таблица кусков, данные.

- **Куски адресуются по имени** (четыре байта, видны в hex-редакторе), а не по
  порядку. Новый кусок в новой версии движка не ломает чтение старых файлов, а
  незнакомый кусок — не ошибка, а «его нет». Это решение RIFF/PNG и по той же
  причине: формат живёт дольше, чем код, который его придумал.
- **Числа пишутся побайтно little-endian**, а не `memcpy` структуры: раскладка
  структуры зависит от компилятора, а ассеты переезжают между машинами всегда.
- **У каждого куска контрольная сумма.** Битый ассет обязан обнаружиться при
  загрузке, а не проявиться дырой в кадре.
- **Сжатие покусочное** (deflate, miniz) и только если реально выиграло: на уже
  плотных данных deflate добавляет байты, и платить за это распаковкой при
  каждой загрузке незачем.

### `.sagemesh` — геометрия

Формат перестаёт хранить точность, которой в данных нет:

| величина | было | стало |
|---|---|---|
| позиция | float32 x3 = 12 Б | uint16 x3 = 6 Б (в габаритах меша) |
| нормаль | float32 x3 = 12 Б | int16 x2 = 4 Б (октаэдр) |
| касательная | float32 x4 = 16 Б | int16 x2 + знак = 5 Б |
| UV | float32 x2 = 8 Б | uint16 x2 = 4 Б (в габаритах UV) |

Индексы пишутся дельтами переменной длины: соседние треугольники ссылаются на
близкие вершины, и дельта почти всегда влезает в один байт вместо четырёх.
Поверх — deflate, но он добирает последнее: основную работу делает то, что
данные вообще перестали хранить лишние биты.

На сфере 24x32 выходит **5.1x** при максимальной ошибке позиции **8 микрон**.

**Про «без потери качества».** Квантование — сжатие С ПОТЕРЯМИ, и называть его
иначе нечестно. Потеря измерима и задаётся явно: при 16 битах на координату
ошибка не превышает габарита меша, делённого на 65535 (для модели в 10 метров —
0.15 мм). Где это неприемлемо, есть режим `Lossless`: те же куски, те же
индексы, но координаты float32 и побайтное воспроизведение входа.

### `.sagetex` — текстуры

Хранит текстуру так, как её принимает видеокарта: блочное сжатие **BC1/BC3**
(4 и 8 бит на пиксель вместо 32, распаковка в железе — бесплатная) и
**мип-уровни, посчитанные заранее**. На градиенте 128x128 BC1 даёт 65536 → 8192
байт в видеопамяти при средней ошибке канала 2.35/255.

Блочное сжатие применяется **не везде**, и это главное решение формата:

- **карты нормалей и карты данных** (roughness/metallic/AO) остаются побайтно
  точными — по ним считается свет, и «почти тот же цвет» означает «не тот
  рельеф»;
- **пиксель-арт** остаётся без мипов и без блочного сжатия: мипы на листе
  спрайтов подмешивают соседний спрайт по краям.

Выбор делается по назначению текстуры и переопределяется явно.

### Реестр импортёров (`sage/assets/import/Importer.h`)

Раньше форматы жили цепочкой сравнений расширения внутри загрузчика: добавить
четвёртый мог ТОЛЬКО тот, кто правит движок. Теперь движок объявляет, что такое
импортёр, а регистрирует кто угодно — движок, игра, плагин редактора:

```cpp
sage::assets::ImporterRegistry::Instance().Register(
    ".myformat", "Мой формат",
    [](const std::string& path, sage::assets::ImportedScene& out, std::string& err) {
        // ... разобрать файл, положить узлы в out.Nodes
        return true;
    });
```

Встроенные форматы регистрируются ровно тем же вызовом: будь у них
привилегированный путь, интерфейс никто бы не проверял. Загрузчик моделей
спрашивает реестр для всего, чего не разбирает сам, поэтому новый формат сразу
становится загружаемым везде, где движок грузит модели — и в сцене, и в
редакторе, и в собранной игре.

Поддерживается: `.obj`, `.gltf`, `.glb`, `.bbmodel`, `.blend`, `.sagemesh`.

### Blockbench (`.bbmodel`)

Для игры про постройку из блоков это самый прямой источник контента: в
Blockbench рисуют ровно то, из чего такие игры и состоят. Гонять модели через
Blender ради `.obj` значит терять привязку к сетке и попутно ломать UV.

16 «пикселей» Blockbench = один блок движка (импорт делит на 16, и модель
приходит в масштабе, где блок есть блок). Поворот вокруг своей точки отсчёта,
обе схемы UV (пофейсовая и `box_uv`), грани без текстуры не рисуются — на этом
держится экономия внутренних граней.

### Blender (`.blend`)

`.blend` — не формат обмена, а дамп памяти Blender'а: блоки кучи вместе с их
адресами на момент сохранения, ссылки — указатели тех времён, схема структур
лежит в самом файле (блок `DNA1`). Разобрать контейнер и схему можно надёжно, и
это сделано. Но смысл полей меняется от версии к версии: в Blender 3.x позиции
вершин переехали из `MVert.co` в обобщённые атрибуты, в 4.0 `MVert` исчез.
Обещать поддержку «любого .blend» значит обещать сопровождать чужую внутреннюю
схему вечно.

Поэтому два пути, в таком порядке:

1. **Прямое чтение** — для несжатых файлов с классической раскладкой
   (`MVert`/`MPoly`/`MLoop`). Не требует ничего, кроме файла.
2. **Мост через Blender** — если он есть на машине, движок просит его выгрузить
   сцену в `.glb` и читает уже её. Так делают промышленные пайплайны, и это
   единственный способ, который переживает смену внутренней схемы: конвертирует
   её тот, кто её и придумал. Путь к Blender задаётся `SAGE_BLENDER`.

Не сработало ничего — сообщение говорит, ЧТО сделать (пересохранить без сжатия,
поставить Blender, экспортировать в glTF), а не «не удалось загрузить».

### Конвертация

Отдельный слой (`sage/assets/import/Convert.h`), потому что импорт и упаковка —
разные вопросы: импорт отвечает «что в этом файле», упаковка — «как это хранить».
Между ними лежит выбор, который может сделать только автор игры.

В редакторе: ПКМ по файлу в Assets → «Конвертировать в .sagemesh/.sagetex», ПКМ
по пустому месту → «Конвертировать всю папку». Отчёт уходит в статусную строку.

Конвертацию запускают на всю папку сразу, поэтому она не падает на одном плохом
файле (отчёт пофайловый), не теряет данные молча (предупреждения импортёра
доезжают до отчёта) и без явного разрешения не перезаписывает существующий файл —
по папке ассетов могли пройтись руками. Назначение текстуры угадывается по имени
(`_normal`, `_rough`, `_ao`) — соглашение всех библиотек PBR-материалов.

**Известное ограничение.** Блочно сжатые уровни `.sagetex` пока разжимаются на
процессоре и заливаются как RGBA: экономия видеопамяти появится вместе с
поддержкой сжатых форматов в RHI. Выигрыш в размере файла и в отсутствии
декодирования PNG есть уже сейчас.

## База ассетов: GUID вместо пути

Ассет опознавался **путём**. Путь — не личность, а адрес: он меняется от
переименования, от переноса в другую папку, от наведения порядка в проекте.
Каждое такое движение ломало сцены, и ломало молча в буквальном смысле: сцена
загружалась, объект оставался на месте, просто без модели и без материала, а в
логе не было ни строчки. Причину можно было найти только вспомнив, что вчера
переименовал файл.

Теперь у каждого ассета есть **GUID** — 128-битный номер, выданный один раз и
живущий рядом с файлом в сайдкаре `<имя>.meta`:

```
sage_meta=1
guid=3f9c1a04b7e25d8811ae6f0c94d3720b
type=model
```

Формат нарочно строчный и без библиотеки: сайдкар должен читаться глазами в
diff'е и не зависеть от парсера, который однажды поменяется.

**Почему сайдкар, а не один общий файл-реестр.** Реестр надо держать в согласии
с содержимым папок, и рассогласовать его проще всего именно тем действием, ради
которого всё затевалось: файл переименовали мимо редактора — в проводнике, в
git, скриптом. Сайдкар переезжает вместе с файлом сам, потому что лежит рядом и
называется так же.

Сцена сохраняет **и GUID, и путь**: `pathGuid` рядом с `path`, `materialGuid`
рядом с `material`, `scriptGuid` рядом с `script`. Путь остаётся — но как
подсказка для человека, а не как личность. Разрешение ссылки идёт по убыванию
доверия, и порядок здесь — суть всего механизма:

1. **GUID найден** — берём его путь. Файл могли переименовать, и это
   единственный способ узнать новое имя.
2. **GUID не найден, но путь существует** — берём путь и заводим GUID. Так
   открываются проекты, сделанные до появления базы; отказ здесь означал бы,
   что старые проекты просто не открываются.
3. **Ничего** — пусто и запись в список сломанных ссылок. Молчать нельзя:
   молчание и было исходной болезнью.

Сломанные ссылки видны в панели «Ассеты» красным заголовком «Битых ссылок: N» —
с последним известным путём, чтобы было что искать, и кнопкой пересканирования.

**Побочно вылечилось ещё одно.** Пути в проекте относительны его корню
(`assets/materials/water.sagemat`), и это верно ровно до тех пор, пока процесс
запущен ИЗ корня проекта. Собранная игра так и работает — а редактор живёт в
своём каталоге и открывает чужие проекты. Разница выглядела безобидно («в игре
всё на месте»), а стоила того, что в редакторе вода теряла свой материал и
рисовалась серой: ошибка была в логе, но правку сцены никто не прерывал, и в
глаза это не бросалось. Теперь загрузчики спрашивают у базы `LocatePath`, и она
достраивает путь до корня проекта, когда файл не открывается как есть. Ключи
кэша при этом остаются исходными — иначе один ассет лежал бы в кэше дважды.

Заодно база отвечает на второй вопрос — **кто на кого ссылается**. Граф
зависимостей нужен затем, что «удалить ассет» и «переименовать ассет» — операции
с последствиями, и показывать их надо ДО, а не после.

**`.meta` обязаны быть в git.** Это единственные файлы в проекте, которые
выглядят служебными, но коммитить их необходимо: без них на каждой машине
сгенерируются свои номера, и ссылки в сценах разойдутся ровно там, где должны
были держаться.

Чего здесь **нет**: это не система импорта. База не превращает `.png` в текстуру
и не печёт бандлы. Она отвечает ровно на два вопроса выше — оба нужны прямо
сейчас, а импорт и бандлы решают другие задачи и должны появляться отдельно.

## Тени (shadow mapping от направленного света)
Часть ЯДРА рендера (`engine/src/sage/render/ShadowMap.h`,
`assets/shaders/shadow_depth.*`). Классический shadow mapping в два прохода:
депт-проход из точки зрения солнца (ортографическая проекция) в depth-текстуру,
затем основной проход сэмплирует её с PCF-фильтрацией мягких краёв и
slope-scaled bias против самозатенения (плюс отсечение лицевых, а не задних,
граней в депт-проходе — тот же классический приём). Ортобокс света задаётся
центром и радиусом, которые игра передаёт каждый кадр под свою сцену.

## Глобальное освещение (запечённое GI: лайтмапы + световые пробы)

Двухуровневая схема запечённого непрямого света, как в современных движках
(модуль `engine/src/sage/gi/`):

- **Лайтмапы для статики.** Сущности с компонентом `GIStaticComponent`
  запекаются CPU path tracer'ом: BVH по треугольникам всей статики
  (`gi/BVH.*`), многоотскоковый непрямой свет (солнце/точечные/прожекторы с
  теневыми лучами + небо, согласованное с полусферическим ambient),
  цветовой bleeding от albedo поверхностей. Развёртка — чарты по доминантной
  оси нормали + shelf-упаковка в HDR-атласы (`gi/LightmapUV.*`); каждая
  запечённая сущность получает персональную копию меша со вторым UV-каналом
  (`Vertex::TexCoords2`, атрибут loc 11). Запекается ТОЛЬКО непрямой свет:
  прямой остаётся realtime — динамические тени и спекуляр не ломаются, двойного
  счёта нет (лайтмапа заменяет прежний однотонный ambient).
- **GI-объём (сетка световых проб) для динамики.** Те же лучи проецируются в
  L1 сферические гармоники по узлам равномерной сетки; три RGBA16F 3D-текстуры
  (по одной на цветовой канал) семплятся в шейдере per-pixel с аппаратной
  трилинейной интерполяцией (`EvalGIVolume` в `PbrShader.h`). Любой объект без
  лайтмапы — движущиеся ящики, игрок, подобранные предметы — автоматически
  освещается окружением сцены. Пробы внутри геометрии отбраковываются и
  заполняются соседями.

Как пользоваться (редактор): панель **Lighting → Global Illumination** —
кнопка «Mark static geometry» вешает `GIStaticComponent` на сущности с мешем
без динамического тела (или вручную через Inspector → Add Component → GI
Static, там же `TexelScale` — локальная плотность), затем «Bake GI». Бейк идёт
в фоновом потоке с прогресс-баром (вход собирается на главном потоке — сцена
из фона не читается); недетерминизма нет: сэмплинг фиксирован сидом. Undo/Play
переносят бейк без повторного запекания (`gi::Transplant` сверяет отпечаток
геометрии). При сохранении сцены страницы атласа пишутся рядом с ней
(`<сцена>_gi_page<N>.hdr`), настройки/пробы — в сам `.sage`; при загрузке
развёртка детерминированно пересчитывается и страницы подхватываются, а если
геометрия менялась после бейка — лайтмапы честно помечаются устаревшими
(нужен ре-бейк, статус виден в панели).

Из кода: `sage::gi::CollectBakeInput(scene, settings)` → `sage::gi::Bake(input)`
→ `scene.GI = state` — весь бейк чистый CPU (без GL, параллелится на своих
потоках), поэтому гоняется в headless-тестах (`tests/test_gi.cpp`: BVH, SH,
упаковка без пересечений, свет/тень/окклюзия, детерминизм, раундтрип страниц).
GPU-ресурсы (HDR-атлас, 3D-текстуры объёма, меши с UV2) создаются лениво при
первом кадре в `RenderBatch`; рендер-путь общий для редактора, `SagePlayer` и
игр. Модели в бейке — `.obj` (CPU-стадия `ModelLoader::LoadObjData`); `.gltf`
статика участвует как получатель объёма проб, но пока не как окклюдер.
Скиннинг-модели остаются на полусферическом ambient (осознанное ограничение,
см. roadmap). Self-test редактора запекает и рендерит GI на реальном GPU в CI.

## Конфигурация и настройки (EngineConfig)
Единый гибкий конфиг движка — `sage::EngineConfig` (`engine/src/sage/core/Config.h`)
— заменяет разрозненное чтение env-переменных одним источником правды. Приоритет
применения (от слабого к сильному):

    значения по умолчанию  →  файл sage.cfg (JSON)  →  env-переменные

Каждое приложение на движке в точке входа делает `cfg.LoadFile("sage.cfg");
cfg.ApplyEnvOverrides(); EngineConfig::Set(cfg);`, после чего окно строится из
конфига, а слои читают `EngineConfig::Get()`.

Что настраивается:

- **Окно**: размер (`width`/`height`), режим (`windowed`/`borderless`/
  `fullscreen`), `vsync`, `resizable`, ограничение кадров `frameCap`,
  сглаживание `msaa` (0/2/4/8).
- **Дисплей**: соотношение сторон `aspect` (`free`/`16:9`/`16:10`/`4:3`/`21:9`
  — фиксированное даёт letterbox/pillarbox чёрными полосами) и масштаб
  внутреннего разрешения `renderScale` (0.25..2.0 — быстрее/чётче).
- **Графика**: `shadows` (+`shadowResolution` 512..4096), `postProcessing`,
  `fog`, `skybox` — любой тяжёлый проход отключается одним флагом.
- **Пост-эффекты**: `exposure`/`gamma`/`saturation`/`contrast`/`vignette`.

**Файл** (`sage.cfg` рядом с игрой). Пример:

```json
{
  "window":  { "width": 1920, "height": 1080, "mode": "borderless", "vsync": true },
  "display": { "aspect": "16:9", "renderScale": 1.0 },
  "graphics":{ "shadows": true, "shadowResolution": 2048, "postProcessing": true }
}
```

**env-переопределения** (поверх файла — для отладки/CI): `SAGE_WINDOW_WIDTH/
HEIGHT`, `SAGE_WINDOW_MODE`, `SAGE_VSYNC`, `SAGE_FRAME_CAP`, `SAGE_MSAA`,
`SAGE_ASPECT`, `SAGE_RENDER_SCALE`, `SAGE_SHADOWS`(+`SAGE_SHADOW_RES`),
`SAGE_POST`, `SAGE_FOG`, `SAGE_SKYBOX` (плюс обратно-совместимые
`SAGE_NO_SHADOWS`/`SAGE_NO_POST`, чьё наличие выключает проход).

**Редактор**: окно **Window → Settings** правит настройки визуально и сохраняет
их в `<проект>/sage.cfg`; **File → Build Game** кладёт файл рядом с собранной
игрой, так что игрок правит настройки, не залезая внутрь. Оконные параметры
(размер/режим/vsync) применяются при следующем запуске игры.

## Текст и шрифты (TrueType)
Текст в игровом интерфейсе рисует `UIRenderer` (`engine/src/sage/ui/`)
настоящим **TrueType-шрифтом** через класс `Font`
(`engine/src/sage/render/Font.*`, на базе
[stb_truetype](https://github.com/nothings/stb)). При создании `UIRenderer`
запекает глифы в атлас-текстуру (R8) и печатает текстурными квадами:

- **Unicode/UTF-8** — строки в `Text/TextCentered` декодируются как UTF-8, из
  коробки запечены латиница (Basic Latin + Latin-1), **кириллица** и типографская
  пунктуация (тире, кавычки, «…»). Игровые надписи можно писать по-русски —
  `games/testgame` так и делает (нижняя подсказка HUD).
- **Шрифт по умолчанию** — `engine/assets/fonts/sage-default.ttf` (DejaVu Sans,
  свободная лицензия Bitstream Vera). `sage_add_game()` копирует его рядом с
  каждой игрой автоматически, так что текст работает без ассетов в самой игре;
  если файл не найден, `UIRenderer` пробует системные шрифты, а в последнюю
  очередь откатывается на встроенный векторный `stb_easy_font` (ASCII-only) —
  движок рисует текст в любом случае.
- **Свой шрифт** — `ui.SetFont("assets/fonts/my.ttf", pixelHeight)`; метрики
  масштабируются от базовой высоты запекания, `MeasureText` учитывает
  пропорциональную ширину глифов (для вёрстки/центрирования).

Редактор `SageEditor` рисует свой UI через ImGui (у него собственная загрузка
шрифта с кириллицей — `EditorTheme::LoadFont`), поэтому `Font`/`UIRenderer` —
это именно текст ВНУТРИ игры, не редактора.

## Аудио (2D/3D-звук, эмбиент, музыка)
Звуковая подсистема ядра (`engine/src/sage/audio/AudioEngine.*`) — часть
движка наравне с рендером и скриптингом. Бэкенд —
[miniaudio](https://github.com/mackron/miniaudio) (single-header, public
domain): сам выбирает системный аудио-API (ALSA/PulseAudio на Linux, WASAPI на
Windows, CoreAudio на macOS) и грузит его через `dlopen` в рантайме.

Что умеет: 2D-эффекты (`PlaySound2D`, непозиционные, для UI), 3D-эффекты
(`PlaySound3D`, микшируются относительно слушателя — обычно камера,
`SetListener` каждый кадр), зацикленный эмбиент (`PlayLoop`), потоковая музыка
(`PlayMusic`, декодируется на лету), микс-группы категорий (SFX/Music/Ambient)
с раздельной регулировкой громкости.

```cpp
AudioEngine audio;
audio.SetListener(cam.Position, cam.Front, cam.Up);      // каждый кадр
audio.PlaySound3D("assets/audio/splash.wav", worldPos);  // звук в точке мира
audio.PlayLoop("assets/audio/ocean.wav", 0.7f);          // эмбиент
audio.PlayMusic("assets/audio/music.wav", 0.5f);         // фоновая музыка
```

**Graceful degradation:** если аудио-устройство недоступно (headless-сервер,
CI, нет звуковой карты), конструктор не падает — движок переходит в «немой»
режим, и все `Play*` становятся no-op (проверка — `IsAvailable()`). Тот же
бинарник работает и со звуком, и без него. Из Lua доступны `PlaySound`/
`PlaySound3D`/`PlayMusic`/`StopMusic`/`SetMasterVolume` после
`ScriptEngine::BindAudio()`.

**Декодирование без воспроизведения.** `AudioEngine::DecodeToMono` (статический,
работает и в «немом» режиме, и без единого созданного движка) читает файл или
кусок памяти и отдаёт сэмплы моно вместе с частотой дискретизации. Форматы —
все, что понимает miniaudio: **WAV, MP3, FLAC**. Нужно это тем, кому звук надо
не услышать, а ПОСМОТРЕТЬ: осциллограмма на монтажной дорожке, поиск пиков для
синхронизации анимации по удару, детект тишины. Director 3D рисует этим
звуковую дорожку таймлайна — до этого он разбирал заголовок WAV вручную и
спотыкался на любом другом формате.

## Стабильность API к 1.0
Текущая версия — ДО 1.0, API ещё может меняться без предупреждения. Номер
версии живёт в ОДНОМ месте — файле `VERSION` в корне; CMake запекает его в
`sage/core/Version.h`, и редактор показывает именно его. Дублировать номер в
тексте не стоит: он расходится первым же релизом, что уже и произошло — README
говорил `0.3.0`, когда в `VERSION` стояло `0.4.0`.
С версии `1.0.0` (когда движок пройдёт боевое тестирование — см. статус в
начале файла) публичный API движка (всё, что включается как `<sage/...>` из
`engine/src/sage/**`) не будет ломаться без повышения мажорной версии. НЕ входит в
этот контракт: внутренности `engine/src/rhi/opengl/` (детали конкретного
бэкенда), внутренности самого `SageEditor` (не библиотека, а приложение) и
`games/sandbox` (пример, может меняться свободно). Версия читается из файла
`VERSION` в корне и запекается в бинарник (`sage::core::Version.h`, константа
`kSageEngineVersion`).

## Как разрабатывать движок и игру(ы) параллельно без переписывания архитектуры
Модульная граница `engine/` ↔ `editor/` ↔ `games/<name>/` уже поддерживает это
— вот как ей пользоваться:

1. **Разрабатывай игру прямо в этом репозитории**, как `games/<name>/`, рядом
   с `games/sandbox/`, пока движок и игра меняются вместе — быстрый цикл без
   версионирования/пиннинга, именно для этого спроектирован `sage_add_game()`.
   Несколько игр могут существовать в `games/` одновременно уже сейчас (сегодня
   это `games/sandbox`, но структура одинаково подходит и для второй, третьей
   игры) — не нужно ничего перестраивать, чтобы добавить ещё одну.
2. **Жёсткое правило границы**, которое нельзя нарушать: код `engine/` и
   `editor/` никогда не включает файлы из `games/*`. Проверяется командой
   (гоняй её перед коммитом, если тронул `engine/`):
   ```bash
   grep -rnE '#include "(\.\./)*games/' engine/ editor/
   ```
   должно быть пусто. Обратное направление — `games/<name>/` включает
   `<sage/...>` из движка — это и есть нормальный, ожидаемый способ
   использования библиотеки.
3. Когда/если конкретная игра станет самостоятельным продуктом и понадобится
   отделить её исходники от движка (например, чтобы поставлять движок другим
   разработчикам без вашей игры внутри) — её `games/<name>/` можно механически
   вынести в отдельный репозиторий, подключив движок как git submodule или
   через `FetchContent` на тегнутую версию (`v1.0.0` и выше). Контракт
   `sage_add_game()`/`CreateApplication`/`SAGE_MAIN` при этом не меняется —
   это перенос файлов, а не переписывание архитектуры.

## Модель многопоточности
Движок использует все ядра там, где это **безопасно и выгодно**, и остаётся
последовательным там, где параллелизм был бы гонкой или не даёт выигрыша —
это осознанная граница, а не недоделка.

- **`JobSystem`** (`sage/core/JobSystem.h`) — единый на процесс пул задач:
  постоянные фоновые воркеры + вызывающий поток разбирают работу. Базовый
  примитив `ParallelFor(count, body)` режет диапазон `[0, count)` на
  непересекающиеся подотрезки; каждый поток пишет только в свой — гонок нет.
  Число воркеров — `EngineConfig.WorkerThreads` (0 = авто, аппаратные потоки − 1),
  общий тумблер — `MultithreadedRender`. Поднимается в `Application` на старте,
  корректно останавливается (join) до разрушения GL/окна. При одном ядре или
  выключенном MT — честный последовательный фолбэк.
- **Рендер — параллельная подготовка кадра, последовательная выдача GL.**
  `RenderBatch::CollectVisible` делает отсечение по фрустуму (матрица·вектор,
  длины столбцов мировой матрицы, 6 плоскостей на сущность) через `ParallelFor`
  — это горячая математика кадра, и она масштабируется по ядрам. Сбор из ECS
  (итерация реестра) и слияние в бакеты — последовательны и в исходном порядке,
  поэтому **результат кадра детерминирован и побайтово совпадает с
  однопоточным**. Сами GL-команды выдаёт только главный поток — контекст один
  (это фундаментальное ограничение OpenGL, а не движка).
- **Физика — уже параллельна.** Бэкенд **Jolt** молотит солвер/бродфазу на
  собственном `JobSystemThreadPool` (аппаратные потоки − 1) — это включено с
  момента интеграции Jolt, шаг физики использует все ядра.
- **Скрипты — последовательны by design, и это правильно.** Игровые Lua-скрипты
  идут через одну `sol::state` и свободно делают структурные правки ECS
  (`SpawnCube`/`DestroyObject`) прямо из тела `OnUpdate`. Параллельный заход в
  один `lua_State` — краш, а одновременные структурные изменения `entt`-реестра
  из нескольких потоков — UB. Поэтому апдейт скриптов исполняется на главном
  потоке — ровно как gameplay-логика в Unity/Unreal/Godot. Это не техдолг:
  безопасная альтернатива потребовала бы N отдельных Lua-VM, запрета spawn/
  destroy в параллельной фазе и командного буфера отложенных правок — что
  сломало бы простой контракт скриптинга ради выигрыша, которого у gameplay-кода
  обычно и нет (узкое место — рендер и физика, они и распараллелены).

## Известные ограничения / roadmap после 1.0
Сознательно не входит в 1.0 (см. `## Стабильность API` выше — это не забытое,
а осознанное решение по масштабу релиза):

- **Физика — полноценная (Jolt), с выбором бэкенда.** Основной — **Jolt**,
  плюс встроенный `Simple` (без зависимостей) и `Null` (выкл). Твёрдые тела
  (Box/Sphere/Capsule, Static/Dynamic/Kinematic) с гравитацией, контактами и
  вращением. Есть **составные (compound) тела** — один твёрдый объект из
  нескольких примитивов с локальными смещениями (`ColliderComponent.Parts` —
  «молоток», «гантель», кластер-аппроксимация модели); **соединения (joints/
  constraints)** — `JointComponent`: Fixed (сварка), Point (шарнир), Hinge
  (петля с пределами угла), Slider (призма с пределами хода), Distance (трос),
  Cone (конус) — все проброшены через абстракцию `PhysicsWorld`; и **ragdoll** —
  сборщик `sage::physics::BuildRagdoll` собирает тряпичную куклу из капсульных
  костей на суставах Cone/Hinge (в Lua — `SpawnRagdoll(pos)`). Мгновенные
  импульсы — `AddImpulse` (в Lua тоже). Всё редактируется в Inspector
  (compound-части, Joint-компонент) и сериализуется в `.sage`. На `Simple`-
  бэкенде соединения не решаются (составное тело сводится к объемлющему AABB) —
  для суставов/ragdoll нужен Jolt. НЕ входит пока: персонажный контроллер,
  триггеры/сенсоры, рейкасты из API движка — есть в Jolt, но ещё не проброшены.
  Игра со своей узкой потребностью (как AABB-игрок в `games/testgame`)
  по-прежнему вольна считать коллизии сама — физика не навязывается.
- **UI-тулкит: рендер и вёрстка — полноценные, интерактив — на игре.**
  `UIRenderer` v3 умеет скруглённые углы и рамки (SDF, гладкий край), картинки
  с тонированием, клип-маски (стек ножниц) и слои, **вертикальный градиент**
  заливки (один квад — не полосы: полупрозрачные полосы клали бы внахлёст и
  давали тёмные линии на каждой границе), **мягкую тень** под элементом и
  **~36 векторных иконок** (`sage::ui::IconNames` — сердце, капля, пламя, доска,
  верёвка, фонарь, компас, лодка…), нарисованных теми же SDF-примитивами: ни
  одного файла-картинки, любой размер и цвет. Текст — TrueType с
  Unicode/кириллицей. Интерфейс собирается прямо В РЕДАКТОРЕ: сущность с
  компонентом `UI Element` (Panel/Label/Image/Bar/Icon; якоря, вложенность через
  иерархию — контейнеры, `Clip Children` — маски, `Layer` — порядок, `Icon` —
  выбор иконки списком, `Auto Width` — ширина по содержимому для «таблеток»)
  видна в панели Game (WYSIWYG), сериализуется в `.sage` и рисуется в собранной
  игре. Иконка, заданная НЕ у `Kind::Icon`, встаёт у левого края элемента, а
  текст начинается за ней — «иконка + подпись + шкала» это один элемент, а не
  три сущности, которые надо держать выровненными вручную. Готовые НАБОРЫ
  интерфейса поддержаны напрямую — см. следующий раздел.
  Скрипты правят UI через `entity:GetUI()` (текст/значение/видимость), клики
  игра обрабатывает сама через `GetUIElementAt(x, y, w, h)` — готовой системы
  фокуса/полей ввода нет (для инструментов это ImGui в редакторе). Тулкит
  обкатан на СЛОЖНОМ реальном экране, не на демо: `sage::ui::BuildShowcase`
  (в Lua — `SpawnUIShowcase()`) собирает **инвентарь** (сетка слотов с иконками/
  счётчиками во вложенном контейнере под клип-маской — нижние ряды реально
  обрезаются как прокручиваемый список, выделенный слот, полоса веса) и
  **дерево навыков** (узлы, соединённые «проводами» под слоем узлов, состояния
  locked/unlocked) — десятки элементов; рендерится в `games/testgame` тем же
  `DrawSceneUI`, что и собранная игра. Плотная вёрстка/маски/слои/hit-тест
  покрыты юнит-тестами (`UI_showcase_*` в `tests/test_ui.cpp`).
- **`ResourceManager` — кэш + управление памятью.** Кэширует меши, модели,
  материалы и текстуры (повторный запрос того же пути не грузит файл заново;
  битый файл кэшируется как «нет» и не перечитывается). Для больших проектов
  есть управление памятью текстур: **бюджет VRAM с LRU-вытеснением**
  (`SetTextureBudgetBytes`; при превышении выгружаются наименее недавно
  использованные текстуры, на которые больше никто не ссылается —
  `use_count()==1`; ссылаемые не трогаются, чтобы не было висячих ссылок),
  **сборка мусора** неиспользуемых текстур/моделей/материалов при смене сцены
  (`GarbageCollectUnused()`) и **асинхронный стриминг**: `GetTextureAsync(path)`
  возвращает объект мгновенно (плейсхолдер 1×1), фоновый поток декодирует файл
  в CPU-буфер, а `Application` раз в кадр заливает готовые пиксели в VRAM
  (`PumpAsyncUploads()` — только на главном потоке, у него единственного
  GL-контекст) прямо в тот же объект `Texture`, так что держатели `shared_ptr`
  видят картинку без повторного запроса и кадр не встаёт на диске/декодировании.
  По умолчанию синхронный `GetTexture` (материалы грузятся сразу, без
  «всплывания»); бюджет по умолчанию не ограничен — включается игрой явно.
- **Материалы v1 — данные, не шейдеры.** Движок/редактор гарантированно
  применяют только `Albedo` (базовый цвет вместо Color сущности);
  Emissive/Shininess/Texture сериализуются и доступны игре, но их поддержка —
  дело шейдеров конкретной игры. Путь материала хранится как записан при
  назначении (для переносимости проекта используй относительные пути).
- **Освещение — forward, тени только от солнца.** Полный набор типов света
  (ambient/directional/point/spot) есть, но тени отбрасывает лишь направленное
  «солнце» (одна shadow-карта); точечные и прожекторы не затеняются
  (для этого нужны cube-shadow'ы/доп. карты). Площадных (area) источников нет —
  они требуют другой модели затенения (LTC), это за рамками forward-рендера.
  Лимит шейдера — 8 точечных + 8 прожекторов одновременно.
- **GI — запечённое (лайтмапы + пробы), рамки первой версии.** См.
  `## Глобальное освещение`. Не входит пока: лайтмапы/окклюдеры из `.gltf`
  (только `.obj` и примитивы), GI для скиннинг-моделей (они на полусферическом
  ambient), запечённый directional-компонент (лайтмапа хранит только цвет),
  автоматический ре-бейк при правке сцены (устаревание честно показывается в
  панели Lighting, бейк — по кнопке). Realtime-GI (SSGI/DDGI) — отдельная
  тема после 1.0.
- **Редактор**: есть **мультивыделение** (Ctrl-клик в Hierarchy/Viewport; гизмо
  двигает весь набор относительно первичной, Delete/Duplicate — по всем, аутлайн
  подсвечивает все), **префабы** (`Save as Prefab` в Hierarchy -> `.sageprefab`
  в assets/; двойной клик по префабу инстанцирует поддерево в сцену), **полное
  undo** всех мутаций (снапшот-модель) и **ассет-импорт-пайплайн для моделей**
  (выбери `.obj`/`.gltf` в Assets -> Inspector правит масштаб/центрирование/
  нормализацию, `Reimport` пишет сайдкар `.sageimport` и перечитывает меш во
  все сущности; настройки пекутся в вершины при загрузке — действуют и в
  собранной игре). Пока НЕТ: универсального добавления произвольных компонентов
  (Inspector понимает Transform/MeshRenderer/Material/Camera/Light/Script/
  RigidBody/Collider/Joint/Particle/UI/AnimatedModel).
- **`SceneSerializer` не сохраняет кастомные компоненты игр** — в `.sage`
  попадают только встроенные (Name/Id/Transform/MeshRenderer/Material-путь/
Script/Camera + свет + RigidBody/Collider).
  Игра с собственными компонентами (как `games/testgame`) либо строит мир
  кодом, либо сериализует своё сама поверх движкового файла. Подтверждено
  боевым тестом; кандидат на «пользовательские сериализаторы компонентов»
  после 1.0.
- **Тестовое покрытие** — три уровня в CI. **Модульные тесты** (`tests/`,
  цель `sage_tests`, гоняются через `ctest`): быстрые проверки БЕЗ GL —
  математика (фрустум-отсечение, матрица трансформа, вычисления конфигурации),
  сериализация (round-trip `EngineConfig`/`Material`/`Scene`) и анимация
  (сэмплирование каналов, иерархия костей Animator). **Headless smoke-тесты**
  (`scripts/ci_smoke_test.sh`): движок реально запускается и рисует кадр,
  self-test редактора проходит, `TestGame` в автопилоте проходит игровой цикл
  (подбор/портал/рендер без ERROR). **Эталонные кадры** (`tests/render`, цель
  `sage_render_tests`): сцена рисуется в offscreen-буфер и сравнивается с
  закоммиченными PNG. Это единственный тест, который проверяет КАРТИНКУ —
  ошибку в шейдере (перепутанный канал, потерянный множитель, съехавшая гамма)
  не видит больше ничто: код собирается, значения считаются, кадр выглядит
  иначе. Сравнение с допуском (разные драйверы дают разные последние биты),
  эталоны сгенерированы программным рендерером — тем же, что на CI-раннере;
  на другой видеокарте расхождение в пределах точности не является регрессией.
  Покрытие пока точечное, не сплошное.
- Второй графический бэкенд (Vulkan/D3D) — RHI к этому готов (`glad` изолирован
  в `engine/src/rhi/opengl/`), но никто пока не реализован.
- Хот-релоад скриптов; каскадные тени (CSM) + мягкие тени (PCSS);
  IBL (image-based lighting) поверх уже сделанного metallic-roughness PBR;
  буфер скоростей (motion vectors) для честного смаза от объектов и для TAA.
- **IK без ограничений суставов.** Солверы (`SolveTwoBone`, FABRIK) дотягивают
  цепочку до цели, но не знают, что колено не гнётся назад: пределы углов на
  сустав пока не заданы, и вывернуть конечность вручную возможно.

## CI и smoke-тесты
`.github/workflows/ci.yml` на каждый push/PR:
- **Linux**: собирает движок + `Sandbox` + `TestGame` + `SageEditor`, затем
  гоняет headless (`xvfb-run`) `scripts/ci_smoke_test.sh` — тот же скрипт можно
  запустить локально, чтобы воспроизвести падение CI:
  ```bash
  cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j$(nproc)
  ./scripts/ci_smoke_test.sh build
  ```
  Четыре проверки: `Sandbox` реально рисует кадр (скриншот на заданном кадре,
  файл непустой); `SageEditor` проходит собственный self-test
  (`SAGE_EDITOR_SELFTEST=1` — создание проекта, сохранение/загрузка сцены,
  undo/redo, Play-режим); плагин-пример `example_stats` грузится и выгружается
  без падения (см. «Плагины редактора»); `TestGame` в автопилоте проходит
  реальный игровой цикл — сериализация сцены, подбор предметов, портал между
  комнатами, рендер с тенями/пост-процессом/HUD — без единой ERROR-строки.
- **Windows (build-only)**: кросс-компиляция через `mingw-w64` тем же
  `cmake/mingw-toolchain.cmake`, что и `scripts/build_windows.sh` — ловит
  поломки Windows-сборки без необходимости реально запускать .exe в CI.

### Headless-сессия над ЧУЖИМ проектом

Проверки выше гоняют редактор на играх, которые редактор сам же и сочинил у
себя в коде. Настоящая игра лежит в отдельном репозитории, её сцены и скрипты
пишет человек — и чтобы CI ТАКОЙ игры мог проверить себя настоящим редактором,
`SageEditor` умеет отработать сессию над любым проектом без единого клика:

```bash
SAGE_EDITOR_OPEN_PROJECT=/путь/к/проекту \
SAGE_EDITOR_OPEN_SCENE=main.sage \
SAGE_EDITOR_PLAY_SECONDS=60 \
SAGE_EDITOR_PLAY_STEP=0.0166 \
SAGE_GAME_ARGS="autopilot=1 seed=42" \
SAGE_EDITOR_BUILD_TO=dist \
  ./build/editor/SageEditor
```

Делается ровно то, что человек делает мышью: **Open Project → выбрать сцену →
Play → Stop → File > Build Game**. Время в Play идёт ФИКСИРОВАННЫМ шагом, а не
настоящим: прогон должен быть воспроизводимым, иначе «успела ли игра дойти до
события» зависело бы от загрузки машины. Итог — строка `SESSION: PASS` (или
`FAIL`) в логе, по которой CI игры и решает, жива ли она. Так [The
Boat](https://github.com/AmckinatorStudios/The-Boat) на каждый push проходится
автопилотом внутри редактора, собирается в exe и проходится ещё раз уже
собранным бинарником.

## Сборка готового продукта под платформу
Есть скрипты, которые одной командой создают ГОТОВЫЙ К РАЗДАЧЕ архив —
бинарник + все assets, версионировано:

```
scripts/
  build_linux.sh      — собрать + упаковать под Linux (из Linux)
  build_windows.sh     — собрать + упаковать под Windows (кросс-компиляция из Linux)
  build_windows.bat      — собрать + упаковать под Windows (если собираешь прямо на Windows)
  build_all.sh             — собрать сразу под обе платформы
  ci_smoke_test.sh          — headless smoke-тест (см. "CI и smoke-тесты" выше)
```

Использование:
```bash
./scripts/build_linux.sh              # соберёт "Sandbox" (имя по умолчанию)
./scripts/build_windows.sh            # кросс-компиляция в .exe
./scripts/build_all.sh                # обе платформы разом

./scripts/build_linux.sh MyGame       # для СВОЕЙ игры на этом же движке —
                                       # просто другое имя (см. games/<name>/), весь код общий
```

Результат появляется в `dist/`:
```
dist/linux/Sandbox-0.3.0-linux-x64.tar.gz
dist/windows/Sandbox-0.3.0-windows-x64.zip
```

Версия берётся из файла `VERSION` в корне — подними её перед следующим
релизом. Каждый архив самодостаточен: распаковал — запустил, ничего
доустанавливать не нужно (Windows-сборка статически линкует рантайм MinGW,
DLL не требуются).

## Как собрать вручную (без скриптов, для разработки)

Имена таргетов фиксированы (задаются через `sage_add_game`): `Sandbox` (пример
игры), `SageEditor` (редактор), `sage_engine` (библиотека). `-DGAME_NAME`
не нужен — таргет каждой игры называется так, как указано в её CMakeLists.

### Linux
```bash
sudo apt install cmake g++ libx11-dev libxrandr-dev libxinerama-dev \
                  libxcursor-dev libxi-dev libgl1-mesa-dev
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)
./build/games/sandbox/Sandbox      # запуск примера
./build/editor/SageEditor          # запуск редактора
```
Собрать только один таргет: `cmake --build build --target Sandbox` (или `SageEditor`).

### Windows
```
cmake -B build
cmake --build build --config Release
```
Или открой папку в Visual Studio через "Open Folder" — она сама подхватит CMake.

### Кросс-компиляция в .exe из Linux
```bash
sudo apt install g++-mingw-w64-x86-64
cmake -B build-windows -DCMAKE_TOOLCHAIN_FILE=cmake/mingw-toolchain.cmake -DCMAKE_BUILD_TYPE=Release
cmake --build build-windows -j$(nproc)
```
.exe линкуется статически — запускается на чистой Windows без установки
рантайма MinGW. Проверено сборкой (кросс-компиляция всего проекта, включая
ImGui/ImGuizmo/entt/sol2, под `x86_64-w64-mingw32-g++`), CI гоняет ту же
сборку на каждый push.
