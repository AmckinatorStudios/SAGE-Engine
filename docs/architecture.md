## Архитектура (ключевые решения)

| Слой | Что это | Где |
|---|---|---|
| **Application / Layer** | Движок владеет окном, главным циклом и таймингом; игра/редактор подключаются как слои (`OnAttach/OnUpdate/OnRender`). Точку входа даёт макрос `SAGE_MAIN`. | `sage/core/Application.h`, `Layer.h`, `GameModule.h` |
| **ECS (entt)** | Сцена — это `entt::registry`; сущности собираются из компонентов (`Name`, `Transform`, `MeshRenderer`, `Hierarchy` (родитель/дети), `Script`, ...). `GameObject` — дешёвый дескриптор поверх. Мировые матрицы — композицией по иерархии (`Scene::WorldMatrix`). Системы обходят сущности (`sage/ecs/RenderSystem.h`). | `sage/scene/Scene.h`, `Components.h`, `sage/ecs/` |
| **RHI (абстракция графики)** | Движок обращается не к OpenGL напрямую, а к интерфейсу `GraphicsDevice`. Реализация бэкенда (сейчас OpenGL) изолирована в `engine/src/rhi/opengl/`. Чтобы добавить Vulkan/D3D — реализуют интерфейс, код движка/игр не трогают. | `sage/rhi/GraphicsDevice.h`, `Resources.h`, `engine/src/rhi/opengl/` |
| **Скриптинг (Lua)** | Управление сущностями и логикой уровня из `.lua` без перекомпиляции. | `sage/scripting/ScriptEngine.*` |

```
    src/PlayerLayer.*            редактора: грузит проект + главную сцену,

  editor/                     → exe SageEditor (редактор на ImGui, см. раздел ниже)
    src/EditorLayer.*         — ядро: сцена/проект/Play/undo/рендер превью
    src/EditorHost.h          — контракт операций редактора для панелей
    src/EditorTheme.*         — темы оформления (роли/метрики/шрифт, themes/*.json)
    src/panels/               — панели: Hierarchy, Inspector, Viewport, Game,
                                Console, Assets (каждая — свой класс)
    src/ProjectLauncher/      — стартовое окно проектов: отдельный экран со
                                своей базой проектов (~/.config/sage/projects.json),
                                карточками, обложками и созданием проекта
    src/PluginAPI.h, PluginManager.*  — система плагинов редактора (см. ниже)
    plugins/example_stats/    — плагин-пример (собирается в plugins/ рядом с exe)

  games/sandbox/              → exe Sandbox (минимальный showcase движка)
    src/  main.cpp (тонкий), SandboxLayer.*
    assets/ shaders/basic.*, scripts/spin.lua

  games/testgame/             → exe TestGame (боевая игра-стресс-тест, см. ниже)
    src/  main.cpp, TestGameLayer.*, GameComponents.h (кастомные ECS-компоненты)
    assets/ shaders (тени+пост), scripts/*.lua, audio/*.wav, models/monument.obj

  scripts/                    — упаковка релиза + ci_smoke_test.sh (см. ниже)

```

Сборка даёт: библиотеку `sage::engine`, exe `Sandbox`, exe `TestGame` и exe
редактора `SageEditor`. Граница строгая и проверяемая: код движка нигде не включает
игровой код (см. `## Как разрабатывать движок и игру(ы) параллельно` ниже), а
`#include <glad/...>` на уровне устройства есть только в `engine/src/rhi/opengl/`.
Следующую игру можно собрать, слинковав ту же библиотеку и написав свой слой +
`CreateApplication`.

## Как сделать новую игру
```cmake
# games/mygame/CMakeLists.txt
sage_add_game(
    NAME MyGame
    SOURCES src/main.cpp src/MyGameLayer.cpp
    ASSETS  ${CMAKE_CURRENT_SOURCE_DIR}/assets
)
```
```cpp
// games/mygame/src/main.cpp
#include "sage/core/GameModule.h"
#include "MyGameLayer.h"
sage::Application* sage::CreateApplication(int, char**) {
    auto* app = new sage::Application({.Title = "My Game"});
    app->PushLayer(std::make_unique<MyGameLayer>());
    return app;
}
SAGE_MAIN()
```
Затем добавить `add_subdirectory(games/mygame)` в корневой CMakeLists. Игровой
слой наследует `sage::Layer` и работает с движковой `Scene` (ECS), рендером
через RHI-девайс и т.д. — именно так устроен `games/sandbox/src/SandboxLayer.*`,
самый простой рабочий пример, с которого можно скопировать структуру.

## games/sandbox — минимальный showcase движка
Это не игра, а нарочно упрощённый пример: плоскость-пол + три цветных куба
через ECS (`Scene::CreateObject`/`MeshRendererComponent`) + один куб со
`ScriptComponent` (крутится через `assets/scripts/spin.lua`, доказывая, что
скриптинг работает и вне редактора), авто-облёт камеры, один простой
шейдер с направленным светом (`assets/shaders/basic.*`). Никаких
теней/пост-процесса/аудио/UI — это подсистемы движка, которые игра включает
по мере необходимости (см. соответствующие разделы ниже), не обязательная
часть минимального примера.

`Sandbox` служит и референсом «как сделать игру», и запускаемой fixture для
headless smoke-тестов в CI (сама библиотека `sage_engine` не запускается —
нужен exe). Поддерживает те же env-хуки, что и `SageEditor`:
`SAGE_WINDOW_WIDTH`/`SAGE_WINDOW_HEIGHT`, `SAGE_SCREENSHOT_AT_FRAME`/
`SAGE_SCREENSHOT_PATH`.

## games/testgame — боевая игра-стресс-тест движка

Не игра ради игры, а полигон: маленький, но ПОЛНЫЙ игровой цикл, сознательно
нагружающий каждую подсистему движка: у половины из них иначе не остаётся ни
одного реального потребителя, а «компилируется» не значит «работает». Что внутри и что этим проверяется:

- **Игрок от первого лица** — `sage::input::InputSystem` с векторным
  действием «Движение» (WASD И левый стик геймпада дают один и тот же
  `Vector2`), мышью и `ESC`/`PAD_START` + **своя AABB-коллизия** со стенами в коде игры
  (`MovePlayer`): коллизии — забота игры, движок их не навязывает.
- **Две комнаты-сцены** (`SceneManager`) с переходом по пульсирующему
  порталу: реальная проверка мультисценового API и переноса состояния
  (здоровье игрока переезжает между комнатами).
- **Кастомные ECS-компоненты** (`src/GameComponents.h`: Health, Pickup,
  Patrol, StaticCollider, Portal) — навешиваются через
  `scene.Registry().emplace<T>()` и обходятся обычными entt-view в коде игры.
  Это ОФИЦИАЛЬНЫЙ паттерн расширения: движок не правится. (Ограничение:
  `SceneSerializer` кастомные компоненты не сохраняет — см. «Известные
  ограничения».)
- **Десятки Lua-скриптов одновременно** (монетки, маяки порталов) — стресс
  `ScriptEngine`; сериализация сцены проверяется round-trip-тестом на старте.
- **HUD движковым `UIRenderer`/`Widgets`** — health bar с динамическим
  источником значения, счёт, подсказки.
- **Аудио** (`AudioEngine`): эмбиент-луп + эффекты подбора/урона/портала; в
  headless CI тихо деградирует (нет устройства — no-op, не падает).
- **Модель `.obj` двумя путями**: ECS-энтити через `ResourceManager::GetModel`
  (комната 1) и прямой `Model::Load`+`Model::Draw` (монумент в комнате 2).
- **Тени** (`ShadowMap` + PCF) и **пост-процесс** (HDR `Framebuffer` +
  ACES-тон-маппинг) — первый реальный рендер-прогон обеих подсистем после
  RHI-миграции.

Env-хуки: общие `SAGE_SCREENSHOT_*`, плюс `SAGE_NO_SHADOWS`, `SAGE_NO_POST`,
`SAGE_TESTGAME_START_ROOM=room2` (старт в конкретной комнате для отладки) и
`SAGE_TESTGAME_AUTOPILOT=1` — бот сам собирает монеты и проходит портал; CI
гоняет его каждым коммитом и проверяет лог-маркеры `TESTGAME:` + отсутствие
ERROR-строк (см. `scripts/ci_smoke_test.sh`, тест 4/4).

Уже вскрытые этой игрой и починенные баги движка:
1. `Window` и `InputSystem` оба монопольно занимали GLFW user pointer окна —
   resize с активным вводом кастовал чужой указатель (UB). Теперь колбэками
   владеет `Window`, ввод подписывается через его хуки.
2. `Vec3(...)`/`Vec2(...)`/`Vec4(...)` нельзя было сконструировать из Lua
   (sol2 требует отдельной регистрации `call_constructor`) — ни один прежний
   скрипт векторы не создавал, поэтому баг жил незамеченным.

## Движок — инструмент: что в нём НЕ должно лежать

В `games/` лежат три проекта, и ни один из них движку не принадлежит:
`sandbox` — минимальная сцена «с чего начать», `testgame` — стресс-тест
подсистем на полном игровом цикле, `showcase` — витрина возможностей. Все три
собираются отдельными целями (`SAGE_BUILD_SAMPLES=OFF` — и их нет) и линкуют
движок как библиотеку. Полноразмерные игры живут в СВОИХ репозиториях и
открываются редактором как любой чужой проект.

Граница держится не обещанием, а тем, что нарушения ловятся. Последнее из них
жило в интерфейсе: набор иконок движка (`sage/ui/UIIcons.cpp`) на две трети
состоял из инвентаря ОДНОЙ игры — доска, бревно, ящик, бочка, верёвка, ткань,
пластик, рыба, руда, фонарь, сеть, якорь, багор, удочка, парус, стена, перила,
водоочиститель, лодка, еда, дыхание, волна, компас. Двадцать четыре предмета
чужого мира ехали в каждую сборку каждого проекта, а своих иконок игра добавить
не могла: таблица была зашита в `.cpp` константой.

Теперь движок держит НЕЙТРАЛЬНЫЕ девятнадцать — управление (play, pause, gear,
save, exit), разметку (plus, minus, check, cross, warn), состояние (heart, drop,
flame, clock, sun, moon, bag, hammer, lamp): то, что осмысленно в игре любого
жанра. Предметный набор приносит игра:

```cpp
sage::ui::RegisterIcon("plank", [](const sage::ui::IconPen& p) {
    p.Box(0.10f, 0.36f, 0.80f, 0.28f, 0.04f);   // доли стороны, 0..1
});
```

Перо (`IconPen`) стало публичным — рисовать иконки должна уметь и игра, а не
только движок; координаты по-прежнему нормализованы, так что форма одинаково
резка в 16 и в 64 пикселя. Зарегистрированное имя ничем не отличается от
встроенного: оно попадает в `IconNames()`, а значит и в список иконок в
инспекторе редактора. Игра вправе переопределить и движковую иконку — её
«сердце» может быть не таким, как здесь.

Двадцать четыре переехавшие формы никуда не делись: они лежат в
`games/testgame/src/GameIcons.cpp` — рабочий пример того, как игра приносит
движку свой набор. А `tests/test_ui.cpp` проверяет обе стороны: что нейтральные
иконки на месте, что предметных в движке НЕТ, и что зарегистрированная игрой
иконка работает наравне со встроенными.

## Как добавить графический бэкенд
Реализовать интерфейсы `sage::rhi::GraphicsDevice` (устройство: инициализация,
состояние конвейера, чтение пикселей) и ресурсы из `sage/rhi/Resources.h`
(`ShaderProgram`, `Geometry`, `Texture2D`, `TextureCube`, `RenderTarget`) в новом
каталоге `engine/src/rhi/<backend>/`, добавить ветку в фабрику
`GraphicsDevice::Create()`.

**Что здесь правда.** Движок, игры и редактор обращаются ТОЛЬКО к этим
интерфейсам: за пределами `engine/src/rhi/` во всём репозитории ноль вызовов
`gl*` (единственное исключение — `Window.cpp`, которому нужен контекст от
оконной системы). Это не заявление, а проверяемый факт: границу держит
`scripts/check_rhi_boundary.py`, он гоняется в CI отдельным шагом ДО сборки.

Второе доказательство — **Null-бэкенд** (`engine/src/rhi/null/`): полноценная
реализация того же интерфейса без единого графического вызова. Движок с ним
собирается и работает, что даёт тестам сцену без видеокарты и без xvfb.

Третье — **набор соответствия** (`sage/rhi/Conformance.h`): один исполняемый
контракт, который обязан пройти КАЖДЫЙ бэкенд. Пока реализация одна,
«интерфейс» и «то, что делает OpenGL» неразличимы, и отличить обязательство от
привычки невозможно — любое поведение выглядит правильным, потому что сравнивать
не с чем. Набор выносит контракт из комментариев в код: хендлы, дескрипторы,
безопасность вызова с невалидным аргументом, `Resolve()` на таргете без MSAA,
`nullptr` как легальный ответ на кубический таргет. Два уровня: структурный
проходят все, включая Null; пиксельный — только те, кто действительно
растеризует (Null честно пропускается, а не подделывает результат). Гоняется
из `sage_tests` по Null и из `sage_render_tests` по OpenGL.

Что он ловит на самом деле — видно, если сломать соглашение нарочно: перевёрнутое
начало отсчёта ножниц в GL-бэкенде роняет проверку «ножницы и чтение сходятся в
левом нижнем углу», хотя ни один из 97 эталонных кадров этого не замечает.

### Vulkan-бэкенд

`engine/src/rhi/vulkan/` — второй настоящий бэкенд. **Состояние: в работе.**
Готово: устройство (загрузчик, инстанс, выбор видеокарты, очередь, слой
валидации по `SAGE_VK_VALIDATION=1`), видеопамять через VMA, буферы,
текстуры 2D/3D/куб с кэшем сэмплеров и переходами раскладок, рендер-таргеты
(`VkRenderPass` + `VkFramebuffer`, MSAA с разрешением прямо в проходе).
Компиляция GLSL движка в SPIR-V (glslang) с рефлексией имён униформ, запись
команд, проходы, очистка и чтение пикселей.
Геометрия, кэш конвейеров, наборы дескрипторов — **бэкенд рисует**.
**Набор соответствия RHI бэкенд проходит целиком** — 25 проверок обоих уровней,
структурного и пиксельного, тот же контракт, что у OpenGL и Null
(`tests/test_rhi.cpp`), плюс отдельный тест полного пути «вершины → конвейер →
дескрипторы → пиксели» с проверкой ориентации. Пиксельный уровень — это уже про систему координат: у
Vulkan начало отсчёта СВЕРХУ, у RHI договорено снизу, и бэкенд обязан
переворачивать. Делается это отрицательной высотой viewport'а
(`VK_KHR_maintenance1`, ядро с 1.1) в одном месте, а не правкой каждой матрицы
проекции по всему движку. Диапазон глубины — через `VK_EXT_depth_clip_control`:
у RHI договорён диапазон OpenGL ([-1,1]), у Vulkan он [0,1], и расширение
разрешает попросить первый. Без расширения бэкенд честно не поднимается и
Application берёт OpenGL: правильный OpenGL лучше непроверенного Vulkan.

Нет пока swapchain и `imgui_impl_vulkan` — то есть в окно и в редактор он ещё
не рисует, только в offscreen-таргеты. Именно их и проверяют тесты.

**Как решён вопрос униформ по имени.** Весь движок пишет
`shader->SetMat4("uModel", …)`, а в Vulkan свободных униформ нет вовсе: любая
обязана лежать в блоке и адресоваться смещением. Переписывать под это
одиннадцать тысяч строк рендера значило бы делать другой движок. Держится на
ослабленных правилах glslang (`setEnvInputVulkanRulesRelaxed`): он сам собирает
свободные униформы в блок и раздаёт привязки — исходники шейдеров не меняются
ни на строку, один и тот же текст компилируется и для OpenGL, и для Vulkan.
После линковки берётся рефлексия имя → смещение, и `Set*` пишут в теневую копию
блока. Цена — поиск по хеш-таблице на установку (в GL был кэш локаций, та же
цена) и буфер униформ на кадр.

Проверяется это не игрушечным шейдером, а НАСТОЯЩИМ общим PBR-блоком движка
(`kPbrSharedGlsl` — массивы, `samplerCube`, `sampler3D`, каскады теней) плюс
заведомо битым шейдером, который обязан дать `nullptr`: без второй половины
тест прошёл бы и на реализации, которая всегда возвращает объект. Пока это так, выбор `vulkan` в настройках
откатывается на OpenGL с объяснением в логе, а взять его принудительно можно
переменной `SAGE_VULKAN_EXPERIMENTAL=1`. Гейт стоит в `Application`, а не в
`GraphicsDevice::Available`, намеренно: «Vulkan на машине есть» и «наш Vulkan
умеет рисовать» — разные утверждения, и подменять первое вторым значило бы
соврать в собственной диагностике.

Выбор бэкенда: `graphics.backend` в `sage.cfg` или `SAGE_BACKEND=opengl|vulkan|null`.
Недоступный бэкенд никогда не мешает запуску — движок берёт OpenGL и пишет
почему. Отказ запускаться из-за строчки в конфиге, которую человек не писал, —
самый дорогой из возможных исходов: игрок не полезет в лог, он удалит игру.

**Ни SDK, ни линковки.** Заголовки берутся у Khronos через FetchContent
(header-only), точки входа грузит **volk** из системного загрузчика в рантайме.
Поэтому сборка не требует LunarG SDK, а бинарник запускается и на машине, где
Vulkan не установлен вовсе. Выключается `-DSAGE_VULKAN=OFF`.

**Как решается расхождение моделей.** Форма интерфейса — машина состояний
OpenGL (`SetBlend`, `SetDepthTest`, `BindTexture2D`), у Vulkan состояние
запекается в `VkPipeline` заранее. Сеттеры складывают состояние в структуру, а
в момент отрисовки по ней ищется готовый конвейер и создаётся новый, только
если такого сочетания ещё не было. Реальных сочетаний в кадре — десятки, кэш
прогревается за первые кадры. Что остаётся хуже настоящего Vulkan-рендера:
команды пишутся в один буфер (никакой записи из нескольких потоков, ради
которой Vulkan обычно и берут), униформы ищутся по имени, смена рендер-таргета
закрывает и открывает проход. Это цена совместимости с существующим кодом
движка.

**Граница держится симметрично.** `scripts/check_rhi_boundary.py` теперь
проверяет не только `gl*` вне `rhi/`, но и `vk*` вне `rhi/vulkan/`.
Односторонняя проверка защищала бы первый бэкенд и молча позволила бы второму
протечь наружу.

**Что здесь было неправдой.** Раньше в этом разделе стояло: «смена бэкенда не
затрагивает ни движок, ни игры, ни редактор». Это было не так — и остаётся не
так: интерфейс GL-подобен, и второй бэкенд платит за это (см. выше). Раздел
переписан, когда работа над Vulkan действительно началась, а не когда о ней
рассуждали.

**Что перестало течь.** Хендлы ресурсов были сырым `unsigned int` — то есть
именем объекта OpenGL, торчащим наружу через весь пост-процесс, тени и
отражения. Это была не стилистика: у Vulkan и Metal хендл — 64-битный указатель,
в 32 бита он не влезает, и второй бэкенд упёрся бы не в архитектуру, а в
арифметику. Хуже была вторая половина — число без типа путается с чем угодно, и
хендл текстуры, хендл запроса и номер юнита компилятор различить не мог. Теперь
это `rhi::TextureHandle` и `rhi::QueryHandle` без неявного приведения к числу.
Сырое число осталось ровно в одной, отдельно названной двери — `NativeHandle()`
для `ImGui::Image`: передача текстуры в стороннее API бэкенд-специфична по своей
природе, и делать вид, что это не так, было бы хуже протечки — тогда
бэкенд-зависимое место выглядело бы переносимым.

**Соглашения записаны.** Начало отсчёта прямоугольников (левый нижний угол),
порядок строк `ReadPixelsRGB` (снизу вверх), начало координат текстуры, диапазон
глубины NDC `[-1, 1]`, порядок матриц. Раньше интерфейс об этом молчал, а бэкенд
решал по привычкам OpenGL. Молчание здесь опаснее протечки типа: несовпадение
соглашений не ломает сборку, а даёт перевёрнутую картинку или маску интерфейса,
обрезающую не тот край, — и ищется это неделями, потому что «на OpenGL всё
работает».

**Честная оценка:** Vulkan-бэкенд потребует переписать МОДЕЛЬ интерфейса
(команды, проходы, дескрипторы) и места, где движок эту модель использует, —
прежде всего порядок проходов кадра. Null-бэкенд доказывает изоляцию, а не
переносимость: он выдержан в той же GL-подобной форме и потому не является
свидетельством, что форма годится для Vulkan. Пустышка соглашается с любой
формой — ей нечего возразить.

Два ограничения самого GL 3.3, о которых надо знать заранее:
* **нет вычислительных шейдеров** (появились в 4.3) — всё, что естественно
  ложится на compute (свёртки, отбор на GPU, частицы), делается через
  фрагментные проходы или на CPU;
* **macOS объявил OpenGL устаревшим** и остановился на 4.1 — порт на Apple
  означает Metal или MoltenVK, то есть тот же разговор про модель.

## Порядок кадра (планировщик систем)

`engine/src/sage/core/SystemScheduler.h`. Порядок «скрипты → физика → анимация
→ частицы → звук» был записан РУКАМИ в каждом потребителе: рантайм, редактор,
игры. Копии разошлись — и не гипотетически: в `games/testgame` скрипты
вызывались ПОСЛЕ шага физики, то есть заданная скриптом скорость применялась на
кадр позже, чем в рантайме. Такую разницу невозможно заметить в редакторе и
мучительно ловить в игре, потому что «иногда управление немного залипает» — это
не сообщение об ошибке.

Ровно та же болезнь уже была у проходов рендера, и там её вылечил
`ScenePasses`. Здесь то же лекарство для логики кадра:

```cpp
sage::SystemScheduler sched;
sage::RegisterCoreSystems(sched, {.Scripts = &scripts, .Physics = &physics});
sched.Add(sage::Stage::Update, "мойИИ", [](Scene& s, float dt) { ... });
sched.Run(scene, dt);                       // каждый кадр
```

**Стадии фиксированы, порядок внутри стадии — числом.** Свободный список «систем
с приоритетами» выглядит гибче, но означает, что порядок зависит от того, кто в
каком порядке зарегистрировался, — а именно этого мы и избегаем. Стадия
отвечает на вопрос «до или после физики», и ответ не должен зависеть от порядка
вызовов `Add`.

Что это дало сразу, помимо единого порядка:

* **Игра и плагин могут добавить свою систему в кадр.** Раньше вписать её было
  некуда — только руками в тело каждого слоя.
* **Упавшая система не уносит кадр.** Исключение ловится, остальные системы
  отрабатывают, сообщение уходит в лог: одна опечатка в Lua обязана стоить
  строки в консоли, а не чёрного экрана.
* **Время каждой системы за кадр.** Профайлер движка знает только «Обновление»
  целиком; здесь видно, КАКАЯ система съела кадр, — первый вопрос при просадке.
* **Повторная регистрация заменяет, а не дублирует.** Перезапуск Play
  переподключает скрипты и физику; без замены каждый заход удваивал бы шаг
  физики, и мир пошёл бы вдвое быстрее.

Редактор пользуется этим же планировщиком, и разница режимов выражена явно: в
правке зарегистрированы только анимация и частицы (превью — художник должен
видеть движение модели, не запуская игру), а скрипты с физикой добавляются на
входе в Play и снимаются на выходе.

## Конфигурация и настройки (EngineConfig)
Единый гибкий конфиг движка — `sage::EngineConfig` (`engine/src/sage/core/Config.h`)
— заменяет разрозненное чтение env-переменных одним источником правды. Приоритет
применения (от слабого к сильному):

    значения по умолчанию  →  файл sage.cfg (JSON)  →  env-переменные

Каждое приложение на движке в точке входа делает `cfg.LoadFile("sage.cfg");
cfg.ApplyEnvOverrides(); EngineConfig::Set(cfg);`, после чего окно строится из
конфига, а слои читают `EngineConfig::Get()`.

Что настраивается:

- **Окно**: размер (`width`/`height`), режим (`windowed`/`borderless`/
  `fullscreen`), `vsync`, `resizable`, ограничение кадров `frameCap`,
  сглаживание `msaa` (0/2/4/8).
- **Дисплей**: соотношение сторон `aspect` (`free`/`16:9`/`16:10`/`4:3`/`21:9`
  — фиксированное даёт letterbox/pillarbox чёрными полосами) и масштаб
  внутреннего разрешения `renderScale` (0.25..2.0 — быстрее/чётче).
- **Графика**: `shadows` (+`shadowResolution` 512..4096), `postProcessing`,
  `fog`, `skybox` — любой тяжёлый проход отключается одним флагом.
- **Пост-эффекты**: `exposure`/`gamma`/`saturation`/`contrast`/`vignette`.

**Файл** (`sage.cfg` рядом с игрой). Пример:

```json
{
  "window":  { "width": 1920, "height": 1080, "mode": "borderless", "vsync": true },
  "display": { "aspect": "16:9", "renderScale": 1.0 },
  "graphics":{ "shadows": true, "shadowResolution": 2048, "postProcessing": true }
}
```

**env-переопределения** (поверх файла — для отладки/CI): `SAGE_WINDOW_WIDTH/
HEIGHT`, `SAGE_WINDOW_MODE`, `SAGE_VSYNC`, `SAGE_FRAME_CAP`, `SAGE_MSAA`,
`SAGE_ASPECT`, `SAGE_RENDER_SCALE`, `SAGE_SHADOWS`(+`SAGE_SHADOW_RES`),
`SAGE_POST`, `SAGE_FOG`, `SAGE_SKYBOX` (плюс обратно-совместимые
`SAGE_NO_SHADOWS`/`SAGE_NO_POST`, чьё наличие выключает проход).

**Редактор**: окно **Window → Settings** правит настройки визуально и сохраняет
их в `<проект>/sage.cfg`; **File → Build Game** кладёт файл рядом с собранной
игрой, так что игрок правит настройки, не залезая внутрь. Оконные параметры
(размер/режим/vsync) применяются при следующем запуске игры.

## Стабильность API к 1.0
Текущая версия — ДО 1.0, API ещё может меняться без предупреждения. Номер
версии живёт в ОДНОМ месте — файле `VERSION` в корне; CMake запекает его в
`sage/core/Version.h`, и редактор показывает именно его. Дублировать номер в
тексте не стоит: он расходится первым же релизом, что уже и произошло — README
говорил `0.3.0`, когда в `VERSION` стояло `0.4.0`.
С версии `1.0.0` (когда движок пройдёт боевое тестирование — см. статус в
начале файла) публичный API движка (всё, что включается как `<sage/...>` из
`engine/src/sage/**`) не будет ломаться без повышения мажорной версии. НЕ входит в
этот контракт: внутренности `engine/src/rhi/opengl/` (детали конкретного
бэкенда), внутренности самого `SageEditor` (не библиотека, а приложение) и
`games/sandbox` (пример, может меняться свободно). Версия читается из файла
`VERSION` в корне и запекается в бинарник (`sage::core::Version.h`, константа
`kSageEngineVersion`).

## Как разрабатывать движок и игру(ы) параллельно без переписывания архитектуры
Модульная граница `engine/` ↔ `editor/` ↔ `games/<name>/` уже поддерживает это
— вот как ей пользоваться:

1. **Разрабатывай игру прямо в этом репозитории**, как `games/<name>/`, рядом
   с `games/sandbox/`, пока движок и игра меняются вместе — быстрый цикл без
   версионирования/пиннинга, именно для этого спроектирован `sage_add_game()`.
   Несколько игр могут существовать в `games/` одновременно уже сейчас (сегодня
   это `games/sandbox`, но структура одинаково подходит и для второй, третьей
   игры) — не нужно ничего перестраивать, чтобы добавить ещё одну.
2. **Жёсткое правило границы**, которое нельзя нарушать: код `engine/` и
   `editor/` никогда не включает файлы из `games/*`. Проверяется командой
   (гоняй её перед коммитом, если тронул `engine/`):
   ```bash
   grep -rnE '#include "(\.\./)*games/' engine/ editor/
   ```
   должно быть пусто. Обратное направление — `games/<name>/` включает
   `<sage/...>` из движка — это и есть нормальный, ожидаемый способ
   использования библиотеки.
3. Когда/если конкретная игра станет самостоятельным продуктом и понадобится
   отделить её исходники от движка (например, чтобы поставлять движок другим
   разработчикам без вашей игры внутри) — её `games/<name>/` можно механически
   вынести в отдельный репозиторий, подключив движок как git submodule или
   через `FetchContent` на тегнутую версию (`v1.0.0` и выше). Контракт
   `sage_add_game()`/`CreateApplication`/`SAGE_MAIN` при этом не меняется —
   это перенос файлов, а не переписывание архитектуры.

## Модель многопоточности
Движок использует все ядра там, где это **безопасно и выгодно**, и остаётся
последовательным там, где параллелизм был бы гонкой или не даёт выигрыша —
это осознанная граница, а не недоделка.

- **`JobSystem`** (`sage/core/JobSystem.h`) — единый на процесс пул задач:
  постоянные фоновые воркеры + вызывающий поток разбирают работу. Базовый
  примитив `ParallelFor(count, body)` режет диапазон `[0, count)` на
  непересекающиеся подотрезки; каждый поток пишет только в свой — гонок нет.
  Число воркеров — `EngineConfig.WorkerThreads` (0 = авто, аппаратные потоки − 1),
  общий тумблер — `MultithreadedRender`. Поднимается в `Application` на старте,
  корректно останавливается (join) до разрушения GL/окна. При одном ядре или
  выключенном MT — честный последовательный фолбэк.
- **Рендер — параллельная подготовка кадра, последовательная выдача GL.**
  `RenderBatch::CollectVisible` делает отсечение по фрустуму (матрица·вектор,
  длины столбцов мировой матрицы, 6 плоскостей на сущность) через `ParallelFor`
  — это горячая математика кадра, и она масштабируется по ядрам. Сбор из ECS
  (итерация реестра) и слияние в бакеты — последовательны и в исходном порядке,
  поэтому **результат кадра детерминирован и побайтово совпадает с
  однопоточным**. Сами GL-команды выдаёт только главный поток — контекст один
  (это фундаментальное ограничение OpenGL, а не движка).
- **Физика — уже параллельна.** Бэкенд **Jolt** молотит солвер/бродфазу на
  собственном `JobSystemThreadPool` (аппаратные потоки − 1) — это включено с
  момента интеграции Jolt, шаг физики использует все ядра.
- **Скрипты — последовательны by design, и это правильно.** Игровые Lua-скрипты
  идут через одну `sol::state` и свободно делают структурные правки ECS
  (`SpawnCube`/`DestroyObject`) прямо из тела `OnUpdate`. Параллельный заход в
  один `lua_State` — краш, а одновременные структурные изменения `entt`-реестра
  из нескольких потоков — UB. Поэтому апдейт скриптов исполняется на главном
  потоке — ровно как gameplay-логика в Unity/Unreal/Godot. Это не техдолг:
  безопасная альтернатива потребовала бы N отдельных Lua-VM, запрета spawn/
  destroy в параллельной фазе и командного буфера отложенных правок — что
  сломало бы простой контракт скриптинга ради выигрыша, которого у gameplay-кода
  обычно и нет (узкое место — рендер и физика, они и распараллелены).
