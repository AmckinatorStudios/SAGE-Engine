# SAGE UI — объектный слой

## Что это

Объектное лицо системы интерфейса: `UIContext`, `UIElement` и виджеты, поверх
которых пишут игровой интерфейс и панели редактора.

```cpp
#include "sage/ui/sageui/SageUI.h"
using namespace sage::ui::sui;

UIContext ui;
ui.InstallEngineResources();
ui.SetPixelPerfect();

auto* panel = ui.CreateIn<Panel>(ui.Content());
panel->Vertical(8.0f)->Padding(UIEdges::Uniform(12.0f));
panel->Add(ui.Create<Label>("Меню"));
ui.CreateIn<Button>(panel, "Играть", "menu.play")->OnClick([] { StartGame(); });

// кадр
ui.SetScreen({w, h});
ui.Update(dt);
ui.HandleInput(frame);
ui.Render(renderer);
```

## Почему слой, а не новая система

Ниже уже лежит ядро (`sage/ui/core`, `layout`, `render`, `input`, `style`):
дерево узлов с компонентами, решатель раскладки в два прохода, маски, эффекты,
команды рисования с батчингом, маршрутизатор ввода с фазами capture → target →
bubble, фокус, навигация, темы, сериализация и реестры. Всё это проверено
кадровыми тестами и работает в игре.

Чего у ядра нет — удобного лица. Собрать меню там значит вручную заводить узлы
и компоненты; это правильно для сериализации и редактора и неправильно для
человека, который пишет игру.

Поэтому `UIElement` **не хранит состояния**. Он хранит номер узла, а позиция,
размер, цвет и всё остальное живут в документе. Из этого следует главное:

* интерфейс, собранный кодом, **сохраняется в `.uidoc`** без единой строчки
  кода про сериализацию элементов;
* интерфейс, нарисованный в редакторе, **доступен коду** как объекты;
* раскладка, маски, эффекты, батчинг, фокус и темы достаются даром;
* новый виджет — это класс-наследник, а не правка ядра.

Проверяется это тестом `SageUI_tree_built_by_code_is_a_saveable_document`:
дерево, собранное объектами, сохраняется и читается обратно как обычный
документ.

## Кадр

Три шага и всегда в этом порядке:

| шаг | что делает | почему именно здесь |
|---|---|---|
| `Update(dt)` | обновляет элементы, затем считает раскладку | элемент вправе поменять содержимое, и это обязано попасть в ЭТУ раскладку |
| `HandleInput(frame)` | раздаёт ввод, ведёт фокус | ввод идёт по уже посчитанной раскладке, иначе кнопка ловит мышь там, где была вчера |
| `Render(renderer)` | собирает команды, склеивает в батчи | рисование не меняет дерево |

## Слои

`ui.Layer(UILayer::Popup)` и т.п. Номера фиксированы и идут с шагом 100:

```
Background(-100) → Content(0) → Overlay(100) → Popup(200) → Tooltip(300) → Modal(400) → Debug(500)
```

Порядок задан **числом**, а не порядком создания: добавление панели не должно
ломать чужую расстановку, а подсказка обязана лечь поверх меню независимо от
того, что завели раньше.

## Свой элемент

Ни строчки правок в ядре:

```cpp
struct Radar : UIElement {
    const char* TypeName() const override { return "Radar"; }
    void OnAttach() override { Ensure<UIFill>().Radius = UICorners(8.0f); }
    void Update(float dt) override { /* своё поведение */ }
};

UIElementRegistry::Instance().Register<Radar>("Radar", "Радар", "Свои");
```

После регистрации элемент создаётся и по имени — `ui.CreateByName("Radar")`, —
то есть доступен данным, файлу `.uidoc` и плагину.

## Границы

* `UIElement` не рисует сам: он собирает узел из компонентов ядра.
* Виджет не знает про игру: кнопка сообщает **команду** (строку), а что она
  значит — решает тот, кто подписался.
* Доступ к ядру открыт намеренно (`element->Ensure<T>()`): слой не обязан
  пересказывать все компоненты своими методами, иначе он отстаёт от ядра и
  половина возможностей становится недостижимой.

## Имена

Ядровой `UIContext` переименован в `UIFrameContext`: он про ресурсы кадра
(шрифты, текстуры, размер экрана, время), а не про сцену интерфейса. Имя
`UIContext` занял слой — это то, что видит человек.
