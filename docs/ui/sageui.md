# SAGE UI — объектный слой

## Что это

Объектное лицо системы интерфейса: `UIContext`, `UIElement` и виджеты, поверх
которых пишут игровой интерфейс и панели редактора.

```cpp
#include "sage/ui/sageui/SageUI.h"
using namespace sage::ui::sui;

UIContext ui;
ui.InstallEngineResources();
ui.SetPixelPerfect();

auto* panel = ui.CreateIn<Panel>(ui.Content());
panel->Vertical(8.0f)->Padding(UIEdges::Uniform(12.0f));
panel->Add(ui.Create<Label>("Меню"));
ui.CreateIn<Button>(panel, "Играть", "menu.play")->OnClick([] { StartGame(); });

// кадр
ui.SetScreen({w, h});
ui.Update(dt);
ui.HandleInput(frame);
ui.Render(renderer);
```

## Почему слой, а не новая система

Ниже уже лежит ядро (`sage/ui/core`, `layout`, `render`, `input`, `style`):
дерево узлов с компонентами, решатель раскладки в два прохода, маски, эффекты,
команды рисования с батчингом, маршрутизатор ввода с фазами capture → target →
bubble, фокус, навигация, темы, сериализация и реестры. Всё это проверено
кадровыми тестами и работает в игре.

Чего у ядра нет — удобного лица. Собрать меню там значит вручную заводить узлы
и компоненты; это правильно для сериализации и редактора и неправильно для
человека, который пишет игру.

Поэтому `UIElement` **не хранит состояния**. Он хранит номер узла, а позиция,
размер, цвет и всё остальное живут в документе. Из этого следует главное:

* интерфейс, собранный кодом, **сохраняется в `.uidoc`** без единой строчки
  кода про сериализацию элементов;
* интерфейс, нарисованный в редакторе, **доступен коду** как объекты;
* раскладка, маски, эффекты, батчинг, фокус и темы достаются даром;
* новый виджет — это класс-наследник, а не правка ядра.

Проверяется это тестом `SageUI_tree_built_by_code_is_a_saveable_document`:
дерево, собранное объектами, сохраняется и читается обратно как обычный
документ.

## Кадр

Три шага и всегда в этом порядке:

| шаг | что делает | почему именно здесь |
|---|---|---|
| `Update(dt)` | обновляет элементы, затем считает раскладку | элемент вправе поменять содержимое, и это обязано попасть в ЭТУ раскладку |
| `HandleInput(frame)` | раздаёт ввод, ведёт фокус | ввод идёт по уже посчитанной раскладке, иначе кнопка ловит мышь там, где была вчера |
| `Render(renderer)` | собирает команды, склеивает в батчи | рисование не меняет дерево |

## Слои

`ui.Layer(UILayer::Popup)` и т.п. Номера фиксированы и идут с шагом 100:

```
Background(-100) → Content(0) → Overlay(100) → Popup(200) → Tooltip(300) → Modal(400) → Debug(500)
```

Порядок задан **числом**, а не порядком создания: добавление панели не должно
ломать чужую расстановку, а подсказка обязана лечь поверх меню независимо от
того, что завели раньше.

## Свой элемент

Ни строчки правок в ядре:

```cpp
struct Radar : UIElement {
    const char* TypeName() const override { return "Radar"; }
    void OnAttach() override { Ensure<UIFill>().Radius = UICorners(8.0f); }
    void Update(float dt) override { /* своё поведение */ }
};

UIElementRegistry::Instance().Register<Radar>("Radar", "Радар", "Свои");
```

После регистрации элемент создаётся и по имени — `ui.CreateByName("Radar")`, —
то есть доступен данным, файлу `.uidoc` и плагину.

## Границы

* `UIElement` не рисует сам: он собирает узел из компонентов ядра.
* Виджет не знает про игру: кнопка сообщает **команду** (строку), а что она
  значит — решает тот, кто подписался.
* Доступ к ядру открыт намеренно (`element->Ensure<T>()`): слой не обязан
  пересказывать все компоненты своими методами, иначе он отстаёт от ядра и
  половина возможностей становится недостижимой.

## Имена

Ядровой `UIContext` переименован в `UIFrameContext`: он про ресурсы кадра
(шрифты, текстуры, размер экрана, время), а не про сцену интерфейса. Имя
`UIContext` занял слой — это то, что видит человек.

## Окна, диалоги, всплывающие и подсказки

```cpp
auto* w = ui.CreateIn<Window>(ui.Content(), "Инспектор");
w->SetSize({420, 300})->Center();
ui.CreateIn<Label>(w->Body(), "Содержимое");

Dialog::Confirm(ui, "Удалить?", "Объект исчезнет.", "Удалить", [] { Delete(); });

auto* menu = ui.Create<Popup>();
menu->AddItem("Копировать", [] { Copy(); });
menu->AddSeparator();
menu->AddItem("Удалить", [] { Delete(); });
menu->OpenAt(cursor);
```

### Окно — обычный элемент

Это главное обещание §26, и оно проверяется тестами. Заголовок — узел, тело —
узел, крестик — обычная кнопка. Перетаскивание идёт теми же событиями `Drag`,
что и у ползунка; «поверх всех» — тем же полем `Order`, что и у любого соседа.

Именно здесь чаще всего заводят вторую систему: у окна появляется своё
рисование рамки, свой хит-тест заголовка, свой порядок окон — и через полгода
маски, эффекты, темы и сохранение в файл работают везде, кроме окон.

### Модальность держится затемнением

`Dialog` кладёт в слой `Modal` затемнение на весь кадр, и **это оно** ловит
мышь. Никакой проверки «а не открыт ли диалог» в обработчиках нет: одна забытая
проверка означала бы кнопку, нажимаемую сквозь диалог.

Затемнение — брат окна, а не его ребёнок: ребёнок был бы обрезан рамкой окна и
затемнял бы само окно.

### Закрытие меню ведёт контекст

Щелчок мимо и `Escape` обрабатывает `UIContext`, а не само меню. Иначе каждое
меню заводило бы обработчик на весь экран, и два открытых меню спорили бы, чей
щелчок. Оба способа обязательны: без `Escape` меню не закрыть с клавиатуры.

Меню, не влезающее в кадр, **сдвигается** внутрь, а не отражается: отражённое
появляется не там, куда нажали.

### Подсказки — по данным

Узел объявляет `UIInteraction::TooltipKey`, контекст показывает после задержки.
Ни таймера, ни позиции, ни своего узла подсказки виджету заводить не нужно —
поэтому подсказки работают и у документов, прочитанных из файла, а не только у
собранных кодом.

## Слои: две ошибки, найденные окнами

Обе жили в ядре с самого начала и молчали, потому что до окон отрицательными
слоями никто не пользовался.

**Смещение не помещалось в поле ключа.** К слою и порядку прибавлялось
`0x40000000`, а результат обрезался до 24 и 20 бит — то есть смещение обрезалось
вместе со знаком. Любое отрицательное значение всплывало на самый верх: фон со
слоем `-100` ложился поверх всего, затемнение под окном с порядком `-1` — поверх
окна.

**Слой не наследовался.** `layerBase` приезжал в раскладку и никем не
использовался: слой был свойством одного узла. Положить окно в группу-слой не
значило ничего.

Теперь слой **складывается** с родительским. Узел с нулём наследует слой группы
(обычный случай), а ненулевой сдвигает себя относительно неё — «поднять кнопку
над своей панелью» не выкидывает её из слоя панели.

## Докинг

```cpp
auto* dock = ui.CreateIn<DockSpace>(ui.Content());
dock->Add(ui.Create<DockPanel>("viewport", "Сцена"));
dock->Add(ui.Create<DockPanel>("inspector", "Инспектор"), DockSide::Right, "viewport");
dock->Add(ui.Create<DockPanel>("console", "Консоль"),      DockSide::Bottom, "viewport");

prefs.Set("layout", dock->SaveLayout());   // при выходе
dock->LoadLayout(prefs.Get("layout"));     // при запуске
```

### Раскладка — это данные

`DockNode` — маленькое дерево из «раздели пополам» и «здесь лежат вот эти
панели». **В нём нет ни одного указателя на элемент**: панели названы строками.
Элементы строятся по этому дереву и пересобираются, когда оно меняется.

Наоборот — «дерево элементов и есть раскладка» — не работает: раскладку надо
сохранять, сравнивать, сбрасывать и восстанавливать, а элементы держат
состояние, обработчики и текстуры, и просто так пересоздать их нельзя.
Сериализовать их положение — значит завести вторую, теневую модель. Здесь модель
одна, и она с самого начала та, которую пишут в файл.

Отсюда же и разделитель: он двигает `Ratio` **в модели**, а дерево
пересобирается. Двигай он элементы напрямую — сохранённая раскладка не
совпадала бы с видимой.

### Панель переезжает, а не пересоздаётся

Смена вкладки, перетаскивание, отцепление в окно и возврат — всё это
перевешивание её узла в другое место дерева документа. Содержимое, прокрутка,
выделение и подписки остаются. Иначе переключение вкладок сбрасывало бы работу
человека, и выглядело бы это как «редактор забыл, что я делал».

Закрытая панель уезжает на **стоянку** — выключенный узел, который не
считается, не рисуется и не ловит мышь. Удалять её нельзя: `Окно > Консоль`
обязано вернуть ту же панель, а не новую.

### Что делает перетаскивание

| куда бросили | что происходит |
|---|---|
| середина области | панель становится ещё одной вкладкой |
| край области (пятая часть стороны) | область делится, панель встаёт с этой стороны |
| мимо всех областей | панель отцепляется в своё окно |
| на саму себя | ничего |

Пятая часть **стороны**, а не 40 пикселей: в узкой панели полоса в пикселях
заняла бы её целиком, и «стать вкладкой» стало бы недостижимо.

Место броска подсвечивается заранее — бросок вслепую даёт раскладку, которую
человек каждый раз правит обратно.

### Что переживает перезапуск

Дерево областей, доли разделителей, состав и порядок вкладок, активная вкладка,
плавающие окна с их положением и размером.

Панель, которой в файле нет, **не теряется**: это новая панель редактора,
появившаяся после того, как человек сохранил раскладку. Без этого новая панель
не появлялась бы ни у кого, кто хоть раз двигал окна.

Битый файл — не повод падать: редактор открывается со стандартной раскладкой, а
причина уходит в лог.

## Оболочка инструмента

```cpp
UIContext ui;
ui.Theme() = UITheme::Editor();       // плотная, холодная, почти без скруглений
ui.SetPixelPerfect();

auto* shell = ui.CreateIn<EditorShell>(ui.Content());
shell->Menu()->SetBrand("SAGE Editor");
shell->Menu()->AddMenu("File")->AddItem("Открыть", [] { Open(); });
shell->Tools()->AddIcon("save", "Сохранить", [] { Save(); });
shell->AddPanel(ui.Create<DockPanel>("hierarchy", "Hierarchy"));
shell->AddPanel(ui.Create<DockPanel>("inspector", "Inspector"), DockSide::Right, "hierarchy");
shell->BuildWindowMenu("Window");
shell->Status()->SetField("FPS", "144");
```

`EditorShell` складывает верх, низ и середину окна — и это **всё**, что она
делает. Ни сцены, ни объектов, ни ассетов она не знает: она знает, что панели
бывают. Обратное — оболочка, знающая про инспектор, — и есть тот самый один
огромный `EditorLayer`, которого просили не делать.

Поэтому она живёт в SAGE UI, а не в редакторе: второй инструмент движка
собирается из неё же.

## Две темы, один фреймворк

| | игра | инструмент |
|---|---|---|
| фон | `#12141A` | `#0D0E10` |
| отступы | 4/8/16/24 | 2/4/8/12 |
| скругления | 4/10/18 | 3/4/6 |
| кегль | 13/17/22 | 12/13/15 |
| строка списка | — | 22 px |

Плотность — решение **темы**, а не кода виджета: «сделать редактор компактнее»
должно быть правкой набора токенов, а не обходом полусотни файлов. Виджеты
берут высоту строки, поля и кнопки из `Size.Row` / `Size.Control` /
`Size.IconButton`; пока каждый выбирал её сам, соседние панели стояли
«в разлинейку».

Золото SAGE — только для того, что человек выбрал или вот-вот нажмёт. Активный
инструмент подсвечивается **приглушённым** акцентом (`Color.AccentMuted`): ряд
ярко-жёлтых кнопок перестаёт показывать, какая из них включена.

## Виджеты оболочки

`Separator`, `IconButton`, `Toolbar`, `MenuBar`, `SearchBox`, `Dropdown`,
`NumericField`, `StatusBar` — в `UIControls.h`; `Tree`, `PropertyGrid`,
`AssetView` — в `UIViews.h`.

Ни один не знает про редактор ни строчки: тулбар — это ряд кнопок с
разделителями, а не «Play/Pause/Stop». Как только «редакторские» элементы
заводят в редакторе, второй инструмент движка начинает писать их заново — и
пишет чуть иначе.

У списков содержимое задаётся **данными**, а строки переиспользуются:
`Tree::SetItems` принимает плоский список с глубиной. Плоский, а не дерево
объектов, намеренно — раскрытие и свёртка это решение того, кто список отдаёт;
виджет со своим представлением дерева обязан его синхронизировать и однажды
разойдётся с настоящим.

`NumericField` тянется мышью: правку позиции объекта делают сотни раз за сеанс,
и набирать цифры на каждую — это не работа.
