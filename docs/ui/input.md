# Ввод

## Граница, которую нельзя переходить

Здесь мышь и клавиатура превращаются в события интерфейса — и на этом всё. Что
означает нажатие кнопки, решает игра, снаружи, подписавшись на события. Ни одной
строки вида «если нажали Play — начать игру» в этом модуле быть не может.

```
Input layer:  мышь        → событие интерфейса
Game layer:   событие UI  → игровое действие
```

## Кадр ввода

```cpp
UIInputFrame in;
in.Pointer = {x, y};
in.Buttons[0] = leftDown;
in.Scroll = {0, wheel};
in.KeysDown = {...};  in.TextInput = "…";
in.NavX = 1; in.NavSubmit = true;      // клавиатура ИЛИ геймпад — всё равно

UIInputReport r = ui.HandleInput(in);
if (r.PointerOverUI) { /* игра не берёт этот щелчок себе */ }
for (const std::string& cmd : r.Commands) { /* menu.play, settings.open… */ }
```

Навигация приходит отдельно от клавиш: одна и та же «вправо» бывает и со
стрелки, и со стика, и интерфейс не должен знать, с какого устройства.

## Компонент взаимодействия

Узел без `UIInteraction` не ловит мышь вовсе и не стоит системе ввода ничего.

```cpp
UIInteraction& ia = node.Ensure<UIInteraction>();
ia.Focusable = true;
ia.Draggable = true;
ia.Hit = UIHitShape::RoundedRect;   // Rect | RoundedRect | Ellipse | ImageAlpha | Polygon | None
ia.HitPadding = UIEdges::Uniform(4.0f);
ia.AlphaThreshold = 0.01f;
ia.Command = "menu.play";           // строка наружу; UI её не толкует
ia.NavUp = "VolumeSlider";          // явный маршрут перекрывает геометрию
```

Состояние (`Hovered`, `Pressed`, `Focused`, `Disabled`, `Selected`, `Checked`)
живёт в `Runtime` и в таблице свойств не значится — его нельзя сохранять в файл,
иначе документ помнит, что кнопка была под курсором.

## Попадание курсором

Учитывается: видимость, включённость, порог прозрачности, маски предков, форма
попадания, преобразование узла, порядок.

Прямоугольник — не единственный способ. Круглая кнопка, скруглённая карточка,
значок с прозрачными углами, шестиугольник карты по прямоугольнику ловят мышь
там, где ничего не нарисовано: подсказка выскакивает рядом с иконкой, а не на
ней.

Порог прозрачности отвечает на классическое «кнопка не нажимается, а почему —
непонятно»: невидимая панель с альфой 0 больше не перехватывает клики.

## Распространение событий

Три фазы, как в любой зрелой системе интерфейса:

```
Canvas → Panel → Button      (Capture: предок может перехватить)
                 Button      (Target)
Canvas ← Panel ← Button      (Bubble: список узнаёт о нажатии на строку)
```

Без фаз каждая такая задача решается «глобальным флагом», а два таких флага уже
не уживаются.

```cpp
ui.Events().On(buttonId, UIEventType::Click, [](UIEvent& e) { … });
ui.Events().OnAny([](UIEvent& e) { … });   // так игра слушает все команды сразу
```

Обработчики живут в `UIEventBus`, а не в узле: узлы сериализуются, а функции —
нет. Обработчик в узле означал бы либо несохраняемый узел, либо молча теряемый
обработчик.

## Захват указателя

Пока кнопку держат, события идут ей, даже если курсор ушёл в сторону. Без этого
ползунок «отваливается» на первом же резком движении мыши.

Перетаскивание начинается только после порога в несколько пикселей: иначе любой
щелчок дрожащей рукой превращается в перетаскивание, и клик не срабатывает.

## Фокус и навигация

`Tab`/`Shift+Tab` идут по `TabIndex`, при равенстве — в порядке обхода дерева,
то есть в том, что человек видит в редакторе.

Стрелки и стик ищут соседа геометрически: вдоль направления — важно, поперёк —
штраф, иначе «вправо» уводит по диагонали в дальний угол и навигация ощущается
случайной. Явные `NavUp`/`NavDown`/… перекрывают геометрию — сложное меню
невозможно провести по задуманному маршруту одной геометрией.

Клик мимо интерфейса снимает фокус: поле ввода, которое держит клавиатуру после
клика по сцене, ломает управление игрой.
