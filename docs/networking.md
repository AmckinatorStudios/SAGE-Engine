# Сеть

Мультиплеер: сервер, клиент, репликация.

## Мультиплеер (сеть, sage/net)

Серверно-авторитарный мультиплеер уровня движка (`engine/src/sage/net/`),
прокачиваемый из главного цикла (без фоновых потоков) и доступный из Lua:

- **Транспорт** — свой протокол поверх UDP (`UdpSocket` — единственное место с
  системными заголовками сети, POSIX/Winsock): пакеты с seq/ack/ack-битами,
  НАДЁЖНЫЙ канал (доставка В ПОРЯДКЕ отправки: msgId, переотправка по таймеру,
  дедупликация и сборка на приёме) и ненадёжный (свежесть важнее доставки —
  снапшоты). Сообщения больше MTU прозрачно фрагментируются и собираются (до
  256 КБ). Keepalive и таймауты, рукопожатие с отказом (сервер заполнен),
  выдача clientId — наименьшего свободного из 1..255, потому что на проводе он
  один байт (см. разбор ниже).
- **Репликация сцены** (`NetworkSystem`): сущности с `NetReplicatedComponent`
  сервер рассылает снапшотами 20 раз в секунду (позиция/поворот/масштаб, цвет,
  вид примитива); клиент обновляет сущности С ТЕМ ЖЕ id (кооп: обе стороны
  загрузили одну сцену), отсутствующие создаёт «призраками», исчезнувшие
  удаляет. Движение сглаживается снапшот-интерполяцией с задержкой 100 мс.
  Компонент ставится в инспекторе (Add Component → Logic → Net Replicated) и
  сохраняется в `.sage`.
- **Lua API** (после `BindNetwork`; в SagePlayer привязан из коробки):
  `Net.Host(port)`, `Net.Connect(ip, port)`, `Net.IsServer/IsClient/IsConnected`,
  `Net.Send(name, data)` (клиент → сервер), `Net.SendTo(clientId, ...)` и
  `Net.Broadcast(...)` (сервер), `Net.Clients()`. `data` — любое Lua-значение
  (число/строка/таблица, рекурсивно), кодируется компактным бинарным кодеком, а
  не JSON: сообщения летят каждый кадр, и разбор текста был бы самой дорогой
  частью сети. Хуки скриптов: `OnNetMessage(name, data, senderId)`,
  `OnClientConnected(id)`, `OnClientDisconnected(id)`, `OnNetConnected()`,
  `OnNetDisconnected()`.

```lua
-- сервер (правила уровня): счёт всем при подборе монеты
function OnNetMessage(name, data, sender)
    if name == "coin" then Net.Broadcast("score", {player = sender, total = data.n}) end
end
-- клиент: Net.Connect("192.168.1.10", 7777); Net.Send("coin", {n = 3})
```

Сеть тикает по НЕмасштабированному времени и вне паузы игрока: транспорт живёт
в реальных секундах (таймауты, темп снапшотов), и замедление игры не должно
замедлять её связь с сервером, а пауза одного игрока — рвать соединение.

**Что чинилось после первого прогона под нагрузкой.** Одиночный куб на чистом
loopback не проверяет ничего из того, ради чего сеть и пишут. Шесть дефектов,
и каждый виден только на сцене больше одной сущности или на сети хуже идеальной:

- **Интерполяции не было вовсе.** Показ отстаёт от приёма на 100 мс, а хранилось
  ДВА последних состояния — то есть один интервал между снапшотами (50 мс).
  Момент показа всегда оказывался старше обоих, и код честно защёлкивался на
  более старом. Со стороны: мир едет рывками двадцать раз в секунду при любой
  частоте кадра. Теперь на сущность хранится очередь состояний, и берутся два,
  между которыми лежит момент показа. Замер: 80 разных положений за 80 кадров
  вместо двадцати.
- **Снапшот ехал одним куском.** Больше ~19 сущностей — и он не помещался в
  пакет, то есть фрагментировался. Но снапшот идёт НЕНАДЁЖНЫМ каналом: потеря
  одного фрагмента убивала снапшот целиком, и чем больше сцена, тем реже до
  клиента доезжал хоть один. Теперь снапшот бьётся на самостоятельные части по
  шестнадцать сущностей, каждая внутри одного пакета. Потерялась часть — не
  обновились её шестнадцать, остальные приехали.
- **Устаревший снапшот откатывал объекты.** Части едут ненадёжно и вправе
  прийти не в том порядке; номера у снапшота не было, и старый пакет
  применялся наравне со свежим. Теперь у снапшота есть номер, старые части
  отбрасываются, а удаление пропавших сущностей делается ТОЛЬКО по собранному
  целиком снапшоту — иначе объекты мигали бы на каждой потере.
- **Призраки оставались в сцене после разрыва.** Чужие сущности, которыми
  некому управлять и которые игрок не может удалить, — и они же уезжали в
  сохранение. Теперь разрыв (и явный `Net.Stop`, и таймаут) снимает их
  ближайшим кадром.
- **Поворот интерполировался через длинную дугу.** Линейная смесь эйлеровых
  углов 170° → −170° идёт не на двадцать градусов вперёд, а на триста сорок
  назад, через ноль: объект на переходе через 180° разворачивался кругом.
  Разница приводится к (−180°, 180°].
- **Id клиента переполнял свой байт.** На провод (`ConnectAccept`) он уходит
  ОДНИМ БАЙТОМ, а сервер держал его как растущий счётчик: после 255 подключений
  за сессию сервер помнил 256, а клиенту уезжал 0. Дальше клиент считал бы
  своими чужие объекты — реплицируемые сущности адресуются владельцем. Сессия
  сервера длиннее матча, и 256 входов и выходов набираются за вечер. Теперь id
  берётся из СВОБОДНЫХ (наименьший незанятый из 1..255): вышедший клиент
  возвращает номер в оборот. Заодно `maxClients` зажат по 255 — 256-й получает
  честный отказ, а не чужой номер.
- Плюс сборка фрагментов: при переполнении таблица очищалась ЦЕЛИКОМ, унося
  заодно ту сборку, которой не хватало одного куска. Теперь выбрасываются
  старейшие.

Покрытие (`tests/test_net.cpp`, 15 проверок) — на НАСТОЯЩИХ UDP-сокетах
(loopback, headless): подключение и обмен, отказ при заполнении, доставка и
порядок при 35% симулированных потерь в обе стороны, фрагментация 10 КБ,
жизненный цикл реплицируемого «призрака», репликация тридцати сущностей (то
есть заведомо не в один пакет), сходимость сцены при трети потерь, отсутствие
отката на устаревшем снапшоте, уборка призраков после разрыва, короткая дуга
поворота, плавность движения, триста подключений подряд без выхода id за байт,
потолок в 255 одновременных клиентов (260 настоящих сокетов, принято ровно 255,
все номера разные) и полный путь Lua → сеть → Lua. Часы в тестах ручные:
никаких ожиданий по настенным часам.

**Панель Game показывает кадр В РАЗРЕШЕНИИ ИГРЫ** (из настроек игры) и вписывает
его с полями по краям. Раньше игра рисовалась ровно в размер панели, и от этого
было две беды. Первая видна сразу: панель почти никогда не совпадает по
соотношению сторон с окном игры, а интерфейс сверстан под ЕГО пропорции — то
есть «игровое окно» показывало не то, что увидит игрок. Вторая всплыла вместе с
редактором интерфейса: он тоже просит игровой кадр, но в разрешении игры, и два
размера дрались бы каждый кадр — буфер пересоздавался бы по два раза за кадр, а
картинка доставалась бы тому, кто попросил последним. Курсор для ввода в
Play-режиме переводится в пиксели кадра делением на масштаб показа.
