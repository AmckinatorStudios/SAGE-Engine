# Многопоточность: единая система задач

Вся параллельная работа движка, редактора и игры идёт через одну систему
задач — `sage::JobSystem` (`engine/src/sage/jobs/`). Своих потоков у подсистем
нет: ни у физики, ни у кэша ресурсов, ни у задач скриптов, ни у миниатюр
редактора. Это проверяет `scripts/check_threads.py` в CI.

## Зачем одна система

До неё у движка было пять независимых пулов: пул кадра, пул Jolt («ядра − 1»),
поток декодирования текстур, пул задач скриптов («ядра − 2»), свои потоки у
упаковщика и запекания света — плюс по потоку у миниатюр, превью, импорта,
сборки игры и обложек проектов. На восьми ядрах это три-четыре десятка
потоков, которые ничего не знают ни о кадре, ни друг о друге: планировщик ОС
переключает их посреди кадра, длинное запекание отнимает ядра у отсечения, а
профилировщику их не видно.

Одна система даёт одно планирование, одни приоритеты, зависимости между
задачами разных подсистем и одну диагностику.

## Устройство

| Часть | Что делает | Почему так |
|---|---|---|
| Воркеры | `доступные ядра − 1` потоков (главный тоже считает). Ядра — с учётом маски сродства и квоты контейнера | 64 воркера на двух выделенных ядрах — это только переключения контекста |
| Дек Чейза–Лева у каждого воркера | своя подзадача кладётся в свой дек (LIFO), свободный воркер крадёт у занятого (FIFO) | без замков; подзадача горячая в кэше; украденная — самая крупная |
| Общие очереди по приоритетам | задачи извне (главный поток, другие полосы) — High / Normal / Low | короткая секция под замком, пустая проверяется атомиком без замка |
| Против голодания | каждая 16-я выборка воркера начинается с низкого приоритета | иначе под постоянной кадровой нагрузкой Low не шёл бы никогда |
| Засыпание | короткое кручение, затем «счётчик событий» (eventcount) | без потерянных пробуждений; пока кто-то ищет работу, спящего не будят — нет вызова ядра ОС на каждую задачу |
| Зависимости | счётчик невыполненных предшественниц | задача может зависеть только от уже созданных — цикл в графе задач невозможен по построению |
| Ожидание | ждущий воркер и главный поток выполняют чужие кадровые задачи | вложенный `ParallelFor` и «задача ждёт подзадачу» не могут занять все потоки и повиснуть |

Запись задачи — одно выделение памяти вместе с телом и результатом; живёт,
пока на неё есть ссылки (ручки, планировщик, предшественницы). Висячей ручки не
бывает, повторного выполнения тоже (переход Queued → Running — один
compare-exchange).

## Полосы исполнения

| Полоса | Где идёт | Для чего |
|---|---|---|
| `Lane::Worker` | воркеры | короткий счёт кадра: отсечение, системы ECS, физика, анимация, частицы |
| `Lane::Background` | воркеры, но не больше `BackgroundLimit` разом (по умолчанию половина) | долгий счёт: запекание света, задачи скриптов, разбор моделей для превью |
| `Lane::IO` | свои потоки (2, растут до `MaxIoThreads`, когда все заняты) | ожидание диска, процесса, сети: чтение и декодирование файлов, импорт, сборка игры |
| `Lane::Main` | главный поток, `PumpMainThread` раз в кадр | результат в интерфейс, сцену, Lua |
| `Lane::Render` | поток графического контекста, `PumpRenderThread` перед отрисовкой | заливка текстур и буферов |

Планирование, приоритеты, зависимости и диагностика у полос общие: задача
главного потока может ждать задачу ввода-вывода, а та — кадровую.

На слабых процессорах: одно ядро — воркеров нет, `ParallelFor` идёт
последовательно, кадровые задачи без ожидающего выполняют потоки
ввода-вывода; меньше трёх воркеров — долгие задачи идут на потоках
ввода-вывода, чтобы не отнимать единственный воркер у кадра.

## API задач

```cpp
#include "sage/jobs/JobSystem.h"
using namespace sage::jobs;

// Задача с результатом. Полоса, подсистема, приоритет — в настройках.
Future<Image> img = Async([file] { return Decode(file); },
                         JobOptions("decode", Category::Resources, Lane::IO));

// Продолжение: начнётся, когда готов результат; получит его ссылкой.
Future<Thumb> th = img.Then([](Image& i) { return Shrink(i); });

// Результат — в главный поток (интерфейс трогать только там).
th.ThenOnMain([this](Thumb& t) { m_icon = Upload(t); });

// Зависимости и точка сборки графа.
JobHandle a = Run(BuildNavmesh);
JobHandle b = Run(BakeProbes, JobOptions().DependsOn(a));
JobHandle all = WhenAll({a, b});

// Группа: общее ожидание и общая отмена.
TaskGroup group;
for (auto& chunk : chunks) group.Run([&chunk] { chunk.Process(); });
group.Wait();          // помогает выполнять, а не спит
group.CancelAndWait(); // в деструкторе подсистемы

// Ручное обещание — для обратного вызова ОС, ответа сети.
Promise<Packet> p;
Future<Packet> f = p.GetFuture();
socket.OnReceive([p = std::move(p)](Packet pk) mutable { p.SetValue(pk); });

// «Не больше N разом» без своего пула; N = 1 — последовательная очередь.
Throttle decoders(2, JobOptions("thumb", Category::Editor, Lane::IO));
decoders.Async([path] { return DecodeThumb(path); });
```

**Результат без ожидания.** Главный поток не ждёт задачи — он проверяет
`IsReady()` / `TryGet()` раз в кадр или получает результат продолжением
`ThenOnMain`. Каждое блокирующее ожидание в главном потоке считается в
профилировщике («Главный поток ждал задачи»).

**Ошибки.** Исключение задачи сохраняется: `Future::Get()` и `Rethrow()`
бросают его, `Error()` отдаёт. Упавшая предшественница не запускает
продолжение — оно наследует её исключение, и `Get()` в конце цепочки бросит
исходную ошибку. Задача-уборщик (`RunIfDependencyFailed`) запускается всё
равно. Ошибка, которую никто не прочёл, уходит в лог при освобождении задачи и
всегда видна в профилировщике.

**Отмена — кооперативная.** `Cancel()` у ручки, `TaskGroup::Cancel()`,
`CancellationSource` с жетоном в `JobOptions::Token`. Не начатая задача
завершается как `Canceled`, не начавшись (и её последователи тоже); идущая
видит запрос через `ThisJob::IsCancelled()` и выходит сама. Насильно оборвать
идущий код нельзя ни в одном языке без порчи данных.

**Захваты отпускаются до завершения.** Когда ожидание задачи или группы
вернулось, замыкание задачи уже разрушено. Подсистема, ждущая свои задачи в
деструкторе, не получит их `Release` после себя.

## Параллельные проходы

```cpp
JobSystem::Get().ParallelFor(count, [&](size_t begin, size_t end) {
    for (size_t i = begin; i < end; ++i) out[i] = f(in[i]);
}, /*grain*/ 256);
```

Диапазон режется на куски (не меньше `Grain` элементов, не больше четырёх на
поток), куски разбираются атомарным счётчиком: вызывающий и несколько
задач-помощниц берут следующий свободный. Поэтому медленный кусок не держит
остальные, вызывающий никогда не ждёт воркера, который не придёт, а помощниц
не больше, чем воркеров. Тело трогает только свой отрезок — результат совпадает
с последовательным побайтово.

`ParallelOptions::Prio = Priority::Low` — для фонового счёта, который не должен
вставать впереди кадра (запекание света так и делает). `ParallelForAsync` —
то же без блокировки, `Batch` — множество мелких операций одним заданием,
`Dispatch` — несколько разнородных.

Код, который живёт и в инструментах без движка (упаковщик шаблонов),
зовёт свободную функцию `sage::jobs::ParallelFor` (`sage/jobs/ParallelFor.h`):
в движке её исполняет система задач, без него — последовательно.

## Главный поток и поток рендера

Главный поток — тот, что поднял систему (`Application`). Он же пока поток
графического контекста; `SetRenderThreadToCurrent()` переназначит, когда рендер
уедет в свой поток.

- `PumpMainThread(4.0)` — в начале кадра, с бюджетом 4 мс: сотня накопившихся
  ответов не даст один кадр в полсекунды, остаток уйдёт в следующие.
- `PumpRenderThread(4.0)` — перед отрисовкой.
- `PostToMain(f)` / `PostToRender(f)` / `Future::ThenOnMain` — способы туда
  попасть.

**GPU — только из потока устройства.** `GraphicsDevice` запоминает поток,
вызвавший `Init`, а бэкенд OpenGL сверяется с ним на входах, создающих
GPU-объекты (`CheckThread`): вызов из чужого потока — строка в логе и счётчик
`GraphicsDevice::ThreadViolations()`, а не молчаливая порча состояния драйвера.
Фоновой задаче, которой нужна видеокарта, — `PostToRender`.

**Deadlock главного потока.** Ждать с главного потока задачу главного потока
— верный deadlock; ожидание видит это и разбирает очередь главного потока само.
Если главный поток ждёт кадровую задачу, которая в свою очередь ждёт главный
поток, — ожидание, затянувшееся дольше 5 мс, тоже начнёт разбирать очередь и
напишет предупреждение: так строить код не надо.

## Системы ECS параллельно

Планировщик систем (`SystemScheduler`) строит граф каждой стадии по
объявлениям доступа (`sage/core/SystemAccess.h`):

```cpp
sched.Add(Stage::PostPhysics, "boids", UpdateBoids,
          SystemAccess::Parallel().Read<Transform>().Write<Boid>());
sched.Add(Stage::Effects, "audio", UpdateAudio,
          SystemAccess::MainThreadOnly().Write<AudioSourceComponent>().WriteResource("audio"));
```

- **Конфликт** — две системы трогают одно и то же, и хотя бы одна пишет
  (компонент или общий ресурс вроде `"physics"`, `"audio"`, `"lua"`).
  Конфликтующие идут в порядке регистрации, независимые — одновременно.
- **Без объявления система эксклюзивна и идёт в главном потоке** — старый код
  ведёт себя ровно как раньше. Граница стадий остаётся барьером.
- `RunAfter("имя")` — явный порядок. Цикл из явных правил — ошибка в лог и
  `GraphError()`, кадр не теряется: граф строится без них.
- **Проверка в работе.** Пока система выполняется, её объявление доступно
  потоку; `sage::ecs::ParallelEach<const A, B>` и `CheckRead/CheckWrite`
  сверяются с ним. Необъявленный доступ — строка в лог (один раз на пару
  «система — компонент») и счётчик `ComponentAccessViolations()`.
- **Структурные правки** (создать/удалить сущность, добавить/снять компонент)
  из параллельного кода — только через `sage::ecs::CommandBuffer`;
  `Flush(registry)` в главном потоке применяет их по ключу, то есть в
  одинаковом порядке при любом числе потоков.

Встроенные системы: частицы объявили доступ и идут на воркере одновременно со
звуком (главный поток). Скрипты, физика, твины, время суток — эксклюзивны:
Lua-состояние одно, а скрипт вправе создать сущность из `OnUpdate`.

## Синхронизация: правила

`sage/jobs/Sync.h` — один набор примитивов на весь код.

1. Сначала — не делить данные: каждый поток пишет своё (отрезок
   `ParallelFor`), результат сливается у вызывающего.
2. Один счётчик или флаг — `std::atomic`, не замок.
3. Секция в несколько инструкций без вызовов наружу — `sync::SpinLock`.
4. Обычная секция — `sync::Mutex("имя")`: `std::mutex` плюс учёт ожиданий;
   имя видно в профилировщике (захватов, с ожиданием, суммарно и дольше всего).
5. Много читателей, редкий писатель — `sync::SharedMutex`.
6. «Дождаться N событий» — `Latch`; «все дошли до шага» — `Barrier` (с
   действием завершения фазы); «не больше N разом» — `Semaphore`;
   «случилось» — `Event` (ручной или автосброс). Своих `condition_variable` с
   флагом рядом не заводить — это `Event` с багом потерянного пробуждения.
7. Под замком не ждать задачу и не звать чужой код — ждущий держит замок,
   которого ждёт задача.
8. Воркер не спит на примитиве, если может помочь: `JobHandle::Wait` и
   `TaskGroup::Wait` сами выполняют чужие задачи. Блокирующие ожидания
   примитивов — для потоков ввода-вывода и кода вне системы задач.

Примитивы свои, а не `std::counting_semaphore`/`std::barrier`: те есть лишь с
C++20 и на macOS требуют новой системы, а движок собирается C++17 под три ОС.

**Передача данных между потоками.** Задача захватывает КОПИИ (строки, пути,
`shared_ptr` на состояние), а не `this` подсистемы. Если `this` необходим —
подсистема держит свои задачи в `TaskGroup` или `Throttle` и ждёт их в
деструкторе. Результат в главный поток — значением через `Future`.

## Жизненный цикл и остановка

`EngineContext` владеет системой; `Application` поднимает её из `EngineConfig`
до слоёв и останавливает до разрушения окна и устройства. `Shutdown()`:

1. новые задачи отклоняются (сразу `Canceled` — `Future` не повиснет);
2. ждущие зависимостей отменяются (зависимость может не наступить никогда —
   обещание, которое никто не выполнит);
3. стоящие в очередях (всех полос и деках воркеров) отменяются;
4. идущие видят запрос остановки (`ThisJob::IsCancelled()`) и дорабатывают;
5. потоки присоединяются.

После остановки `ParallelFor` идёт последовательно на вызывающем потоке.
Повторный `Initialize` поднимает систему заново.

**Выгрузка модуля.** Задачи, чей код живёт в модуле игры или плагине,
ставятся в `TaskGroup` модуля; перед выгрузкой — `CancelAndWait()`.

## Как подсистемы используют систему задач

| Подсистема | Как |
|---|---|
| Рендер | отсечение по фрустуму — `ParallelFor` (`RenderBatch::CollectVisible`); выдача GL — главный поток |
| Физика (Jolt) | мост `physics/jolt/JoltJobs.cpp`: задачи солвера и бродфазы — кадровые задачи движка, высокий приоритет, подсистема Physics; барьер Jolt помогает выполнять их сам |
| Анимация | подготовка и корневое движение/IK — последовательно; счёт позы всех аниматоров — `ParallelFor` |
| Частицы | шаг самодостаточных эмиттеров — параллельно, деревья с дочерними эмиттерами — следом в прежнем порядке; лучи в физику — под замком |
| Кэш ресурсов | `GetTextureAsync`: чтение и декодирование — задача полосы ввода-вывода, заливка — `PumpAsyncUploads` в главном потоке; очистка кэша отменяет и дожидается своих задач |
| Задачи скриптов | `Throttle` долгой полосы; у каждого потока, взявшего задачу, своё Lua-состояние |
| Упаковщик | сжатие и шифрование файлов — `sage::jobs::ParallelFor` |
| Запекание GI | `ParallelFor` низкого приоритета: кадр редактора идёт впереди кусков бейка |
| Редактор | миниатюры (два разборщика стека на полосе ввода-вывода), превью моделей (долгие), импорт и сборка игры (ввод-вывод), обложки проектов (`Throttle` 1), запекание (долгая) |

Звук: поток обратного вызова аудиоустройства принадлежит драйверу
(miniaudio), это не пул движка; система задач его не трогает.

## Диагностика и профилировщик

`JobSystem::Stats()` — снимок без остановки потоков: потоки (занятость,
выполнено, украдено, что выполняет сейчас), очереди по полосам, ждущие
зависимостей, подсистемы (задач, среднее и максимальное время, время в
очереди, упавшие и отменённые), замки, зависшие задачи (идут дольше
`HungJobMs`; для долгих и ввода-вывода — свой порог), последние ошибки,
ожидания главного потока. Счётчики пишет каждый поток в свои ячейки:
общий атомик на каждую задачу перекидывал бы линию кэша между ядрами.

`SetTracing(true)` + `Trace(мс)` — шкала времени задач по потокам.

В редакторе: **Окно → Профилировщик → вкладка «Потоки»** — всё перечисленное,
шкала времени (цвет — подсистема) и граф систем кадра: кто где выполняется и
кого ждёт. Шкала пишется, только пока вкладка открыта.

## Настройки

`sage.cfg`, секция `system`:

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `workerThreads` | 0 (авто: ядра − 1) | число воркеров |
| `multithreadedRender` | true | выключенное — `ParallelFor` последовательно |
| `ioThreads` | 0 (авто: 2, на одном ядре 1) | потоков ввода-вывода на старте |
| `maxIoThreads` | 0 (авто: 8) | предел роста |
| `backgroundJobLimit` | 0 (авто: половина воркеров) | сколько воркеров разом могут занять долгие задачи |
| `hungJobMs` | 2000 | порог «зависшей» кадровой задачи |

  вложенном ожидании, остановка, стресс «ни одна задача дважды».
- `tests/test_jobs_sync.cpp` — примитивы синхронизации и дек (каждый элемент
  достаётся ровно одному из владельца и трёх воров).
- `tests/test_jobs_ecs.cpp` — граф систем, конфликты, параллельный результат
  равен последовательному, проверка объявлений, `CommandBuffer`.
- `tests/test_jobs_integration.cpp` — Jolt на воркерах движка, фоновая текстура
  через полосу ввода-вывода, GPU-вызовы только из потока устройства.
- `SAGE_TEST_FILTER=Jobs ./build/tests/sage_tests` — только они (сотни прогонов
  подряд ловят редкую гонку).
- `./build/tests/sage_bench jobs` — цена задачи, кражи, цепочки зависимостей и
  ускорение `ParallelFor` на этой машине.
