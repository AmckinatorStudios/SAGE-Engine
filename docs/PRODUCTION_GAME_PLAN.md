# «Emberfall» — план полноценной продакшен-игры на SAGE

> Это не техдок движка, а **проектный план игры**: конкретная крупная игра,
> целиком выполнимая на текущих возможностях SAGE, разбитая на фазы так, чтобы
> её можно было разрабатывать отдельным проектом `games/emberfall/` — рядом с
> движком, тем же способом, что `games/testgame` и `games/sandbox`, но
> существенно крупнее.
>
> Документ отвечает на вопрос «как мне сделать на движке полноценную большую
> игру»: сначала — что это за игра и почему она ложится ровно на SAGE, затем —
> структура проекта, кастомные системы, контент и **пофазовый роадмап**, где
> каждая фаза собирается, запускается headless и проверяется, как весь остальной
> код в этом репозитории.

---

## 1. Концепт

**Emberfall** — одиночная экшн-адвенчура с видом от третьего лица: спуск по
руинам угасающего мира-«кузницы», где игрок собирает осколки угасшего огня
(Ember), сражается в ближнем бою со скелетно-анимированными врагами, прокачивает
навыки и открывает связанные комнаты-арены, переходя между ними через порталы.

**Жанровый ориентир:** «souls-lite» arena crawler — не открытый мир, а
последовательность вручную собранных боевых и исследовательских комнат
(«кузниц»), объединённых хабом. Это осознанный выбор масштаба: большая по объёму
контента игра, но **без систем, которых у движка пока нет** (стриминга открытого
мира, навмеша, сети).

**Столпы (design pillars):**
1. **Читаемый ближний бой** — анимационно-управляемые атаки, тайминги, уклонения;
   попадание = окно кадров анимации + физический overlap, а не хитскан.
2. **Свет как настроение** — угасающий мир: направленный свет + тени + туман +
   пост-процесс; собранный Ember временно «зажигает» комнату (динамика света).
3. **Рост персонажа** — здоровье/выносливость/сила, дерево навыков, лут, билд.
4. **Комнаты-вертикали** — каждая «кузница» самодостаточна: своя сцена, свои
   враги, своя награда; хаб связывает их порталами.

**Ядро цикла (core loop):** хаб → выбрать портал в кузницу → бой + сбор Ember →
босс/награда → вернуться в хаб → потратить Ember в дереве навыков → следующая
кузница. 8–12 кузниц + хаб + финальная арена = «полноценная» по объёму игра,
которая при этом строится повторением одного отлаженного вертикального среза.

## 2. Почему это ложится ровно на SAGE

Каждый столп опирается на уже существующую и проверенную подсистему движка —
ничего не нужно «дописывать в ядре», только собирать игру поверх публичного API
`<sage/...>`.

| Нужно игре | Подсистема SAGE | Где в движке |
|---|---|---|
| Герой и враги как анимированные модели | Скелетная анимация + **FBX/glTF** (`SkinnedModel`, `Animator`, кросс-фейд клипов) | `sage/anim/*`, `sage/render/SkinnedModel.*` |
| Смерть врага/босса «в тряпку» | Ragdoll + constraints (Jolt) | `src/physics/Ragdoll.*`, `physics/jolt/` |
| Движение, удары, толчки, падение | `PhysicsWorld` (Jolt), составные формы, джойнты | `src/physics/*` |
| Комнаты-кузницы, хаб, переходы | Сцены + сериализация + порталы | `SceneManager`, `SceneSerializer`, паттерн `PortalComponent` из testgame |
| Мрачный свет, тени, туман, тонмаппинг | PBR + directional/point/spot, `ShadowMap`, `PostFX`, `Skybox`+туман | `sage/render/*`, `LightComponent` |
| HUD, инвентарь, дерево навыков, меню | UI-тулкит v2 (SDF-скругления, слои, клип-маски) + `UIShowcase` (инвентарь/дерево уже собраны) | `sage/ui/*` |
| Логика врагов/предметов/скриптовых событий | Lua (`ScriptEngine`, полный доступ к ECS) | `sage/scripting/*` |
| Музыка, SFX, эмбиент | `AudioEngine` (miniaudio) | `sage/audio/*` |
| Искры удара, магия, пыль, огонь | Частицы (ECS-частицы) | `sage/render/Particle*` |
| Плавные эффекты (вспышки, тряска, всплытие урона) | Tween (`TweenManager`, easing) | `sage/core/Tween.*` |
| Кастомные данные на сущностях (Health/Stats/AI/Loot) | ECS-расширение через `registry.emplace<T>()` | паттерн из `games/testgame/src/GameComponents.h` |
| Много одновременных врагов/частиц | JobSystem (параллельный куллинг/апдейт) | `sage/core/JobSystem.*` |
| Прокачка/производительность | Пресеты качества, кэш юниформ, бюджет VRAM | `EngineConfig`, `ResourceManager` |

Единственное, что игра берёт на себя (осознанно, как и `PlayerController` в
удалённой The Boat и как коллизии в testgame): **свой контроллер персонажа и
своя боевая логика** — движок даёт физику и анимацию как кирпичи, но не диктует
геймплей. Это и есть граница «движок универсален / игра конкретна».

## 3. Структура проекта `games/emberfall/`

По образцу `games/testgame`, но крупнее. Подключается одной строкой через
`sage_add_game()` — движок не правится.

```
games/emberfall/
  CMakeLists.txt                 — sage_add_game(NAME Emberfall SOURCES ... ASSETS ...)
  src/
    main.cpp                     — тонкий вход: SAGE_MAIN(EmberfallLayer)
    EmberfallLayer.{h,cpp}       — корневой Layer: владеет игрой, сценами, HUD, циклом
    GameComponents.h             — кастомные ECS-компоненты (см. §4)
    player/
      PlayerController.{h,cpp}    — ввод -> движение (Jolt capsule) + состояние боя
      CombatSystem.{h,cpp}        — окна атак, хитбоксы (overlap), урон, стамина
      CameraRig.{h,cpp}           — орбитальная камера от 3-го лица + лок-он
    ai/
      EnemyBrain.{h,cpp}          — конечный автомат (idle/chase/attack/stagger/dead)
      SpawnDirector.{h,cpp}       — волны/расстановка врагов в кузнице
    world/
      RoomManager.{h,cpp}         — загрузка комнаты-сцены, порталы, спавн-точки
      LootSystem.{h,cpp}          — выпадение Ember/предметов, подбор
    ui/
      Hud.{h,cpp}                 — здоровье/стамина/Ember, всплытие урона
      InventoryScreen.{h,cpp}     — сетка предметов (на UIShowcase)
      SkillTreeScreen.{h,cpp}     — дерево навыков (на UIShowcase)
      PauseMenu.{h,cpp}
    save/
      SaveGame.{h,cpp}            — JSON поверх nlohmann: прогресс, билд, открытые кузницы
  assets/
    scenes/                       — hub.sage, forge_01.sage ... forge_10.sage, final.sage
    models/                       — hero.fbx, enemy_*.fbx, props/*.glb (реальные ассеты!)
    scripts/                      — event_*.lua (скриптовые триггеры комнат)
    audio/                        — music/*.ogg-wav, sfx/*, ambient/*
    shaders/                      — при необходимости кастомные (иначе движковые)
    ui/                           — иконки предметов/навыков (текстуры-атласы)
```

Всё под `src/` — код **игры**; ни один файл не попадает в `engine/`. Проверяется
тем же правилом границы, что и весь репозиторий:
`grep -rnE '#include "(\.\./)*(player|ai|world)/' engine/` → пусто.

## 4. Кастомные ECS-компоненты (живут в игре)

Тот же официальный паттерн, что `games/testgame/src/GameComponents.h`: структуры
навешиваются через `scene.Registry().emplace<T>(entity, ...)`, обходятся
entt-view в системах игры, движок про них не знает.

```cpp
struct Health      { float Current=100, Max=100; float RegenPerSec=0; };
struct Stamina     { float Current=100, Max=100, RegenPerSec=25; };
struct Attributes  { int Strength=5, Vitality=5, Focus=5; int Level=1, Ember=0; };
struct EnemyTag    { enum Kind { Grunt, Archer, Brute, Boss } Kind; };
struct EnemyBrainState { int State; float Timer; entt::entity Target; };
struct Hitbox      { float Radius; float Damage; float ActiveFrom, ActiveTo; bool Enemy; };
struct LootDrop    { int EmberMin, EmberMax; std::string ItemId; float Chance; };
struct Interactable{ std::string Kind; float Radius; }; // рычаг, сундук, портал
struct PortalComponent { std::string TargetScene; glm::vec3 SpawnPos; float Radius; };
struct AnimStateTag{ int State; }; // idle/run/attack/hit/death -> клип аниматора
```

**Известное ограничение (наследуется от движка, документируется здесь честно):**
`SceneSerializer` сохраняет только встроенные компоненты движка
(Name/Id/Transform/MeshRenderer/Script/Light/Camera/...). Кастомные компоненты в
`.sage` **не попадают**. Отсюда два следствия для дизайна сохранений:
- Планировка комнаты (геометрия, свет, спавн-маркеры) — в `.sage` (движковые
  компоненты + пустые сущности-маркеры с известными именами).
- Динамика игры (какие враги живы, инвентарь, билд, открытые кузницы) — в **своём**
  `SaveGame` (JSON поверх nlohmann), не в `.sage`. Это чистое разделение
  «уровень (данные движка) / прогресс (данные игры)», а не костыль.

## 5. Контент-план

- **Хаб (`hub.sage`)** — безопасная «кузница-очаг»: порталы в открытые кузницы,
  NPC-кузнец (дерево навыков), сундук (инвентарь). Спокойный свет, музыка-тема.
- **8–10 кузниц (`forge_01..10.sage`)** — боевые/исследовательские комнаты
  с нарастающей сложностью. Каждая: планировка (props через `Model::Load`/FBX),
  свет+туман под настроение, 1 скриптовый событийный триггер (`.lua`), волны
  врагов (`SpawnDirector`), награда (Ember + предмет), выход-портал.
- **Финальная арена (`final.sage`)** — босс с ragdoll-смертью, фазами (Lua),
  сменой освещения на «зажжённое».
- **Бестиарий:** Grunt (ближний), Archer (дистанция, снаряд-частица+physics),
  Brute (медленный тяжёлый), Boss. Все — `SkinnedModel` из FBX с клипами
  idle/run/attack/hit/death, кросс-фейд между ними по `AnimStateTag`.
- **Предметы/навыки:** ~20 предметов (оружие/броня/реликвии) и дерево ~15 навыков
  (сила удара, стамина, окно уклонения, регенерация, урон стихией).

## 6. Пофазовый роадмап

Тот же принцип, что во всём репозитории: **каждая фаза собирается, запускается
headless и проверяется** (env-хуки `SAGE_SCREENSHOT_AT_FRAME`/`SAGE_*` +
скриншот, лог без ERROR), каждая — отдельный коммит. Порядок — от вертикального
среза к контенту к полишу: сначала одна кузница играется целиком, потом их
становится много.

### Фаза 0 — каркас проекта
`games/emberfall/` через `sage_add_game`, `main.cpp` + `EmberfallLayer`, пустая
сцена-хаб, орбитальная камера, движковый рендер-проход. Хук авто-скриншота.
**Проверка:** headless-скрин непустой, exit 0. (Точная копия того, как заводился
`sandbox`/`testgame` — риск нулевой, но это фундамент.)

### Фаза 1 — управляемый герой (вертикаль ввода/движения/камеры)
`PlayerController` на Jolt-капсуле (WASD + прыжок/уклонение), камера от 3-го лица
с лок-оном, `SkinnedModel` героя из FBX с клипами idle/run, переключение по
скорости через кросс-фейд `Animator`. **Проверка:** headless-автопилот прогоняет
героя по маршруту, скрин показывает анимированную модель; лог перехода
idle↔run.

### Фаза 2 — бой (главная механика)
`CombatSystem`: атака запускает клип, `Hitbox` активен в окне кадров, overlap с
врагом → урон + tween-вспышка + партикл-искры; стамина тратится/регенерит;
уклонение даёт i-кадры. Манекен-враг с `Health`. **Проверка:** headless-сценарий
«ударить манекен N раз → Health падает до 0», лог урона по кадрам.

### Фаза 3 — враг и ИИ (одна полноценная кузница)
`EnemyBrain` (idle→chase→attack→stagger→dead) на Lua+C++, `SpawnDirector` ставит
волну, смерть → ragdoll (Jolt) + `LootDrop` (Ember). Собираем **одну** кузницу
`forge_01.sage` целиком: планировка, свет+туман, враги, награда, выход-портал.
**Проверка:** headless-автопилот проходит кузницу (убил волну, забрал Ember,
дошёл до портала), скрин + лог без ERROR. Это и есть играемый вертикальный срез.

### Фаза 4 — HUD и экраны (UI-вертикаль)
`Hud` (здоровье/стамина/Ember, всплытие урона на tween), `InventoryScreen` и
`SkillTreeScreen` на базе `UIShowcase` (сетка/дерево уже собраны), `PauseMenu`.
**Проверка:** headless-скрин HUD поверх боя; открыть инвентарь/дерево, клики по
ячейкам логируются.

### Фаза 5 — мир из комнат (масштабирование контента)
`RoomManager` + порталы: хаб ↔ кузницы через `SceneManager`, спавн в целевой
точке. Прогресс (открытые кузницы, билд, инвентарь) в `SaveGame` (JSON).
Наполняем 3–4 кузницы, чтобы отладить пайплайн «новая комната = новый .sage +
Lua-триггер», после чего остальные — рутинное повторение. **Проверка:**
headless-прогон «хаб → кузница → назад в хаб», save/load round-trip.

### Фаза 6 — контент-наполнение
Оставшиеся кузницы, бестиарий, предметы/навыки, финальный босс с фазами (Lua) и
сменой освещения. Настоящие FBX-ассеты вместо плейсхолдеров. Это самая длинная,
но самая механическая фаза — весь инструментарий уже отлажен фазами 1–5.

### Фаза 7 — полиш и продакшен-сборка
Аудио (музыка/SFX/эмбиент), пост-процесс и пресеты качества, баланс, экран
титров/сохранений, упаковка через существующий `SagePlayer`/пайплайн сборки игр
(`scripts/`), финальный headless-прогон E2E. **Проверка:** собранный exe
запускается, проходит первую кузницу автопилотом (как E2E-smoke №6 сейчас).

## 7. Как это разрабатывается «отдельной игрой» рядом с движком

Организационный ответ — тот же контракт, что уже задокументирован в README
(«Как разрабатывать движок и игру(ы) параллельно»):

1. **Пока идёт совместная разработка** — `games/emberfall/` живёт соседней
   папкой в этом репозитории (как `sandbox`/`testgame`), подключается
   `sage_add_game()`, собирается общим CMake, гоняется в том же CI и через те же
   headless-хуки. Никакого версионирования/пиннинга движка не нужно — граница
   `engine/ ↔ games/` уже проведена и проверяется grep-инвариантом.
2. **Движок остаётся универсальным.** Всё, что игре не хватает и что по природе
   общее (например, встроенный контроллер персонажа, навмеш, сеть), — попадает в
   `engine/` как отдельная движковая задача с чистым `<sage/...>` API, а не
   протекает из `games/emberfall/`. Игра потребляет только публичный API.
3. **Когда игра созреет в самостоятельный продукт** и публичный API движка
   стабилизируется — `games/emberfall/` механически выносится в отдельный
   репозиторий, движок подключается git-submodule/FetchContent на тегнутую
   версию. Контракт `sage_add_game()` при этом не меняется: это перенос файлов,
   а не переписывание. Именно ради этого спроектирована модульная граница.

**Практический рабочий цикл (как я это исполняю по фазам):** каждая фаза — ветка
работы → реализация игрового кода в `games/emberfall/` (движок правлю только если
всплывает честно движковая нехватка, отдельным коммитом с тестом) → headless-
проверка тем же механизмом, что весь репозиторий → коммит фазы. Игра растёт
играемыми срезами, а не «большим взрывом»: после Фазы 3 уже есть, во что играть.

## 8. Что осознанно НЕ входит (границы масштаба)

Чтобы «полноценная и крупная» не превратилась в «бесконечную»: открытый мир со
стримингом, навигационные меши/pathfinding «из коробки» (ИИ ходит по
расставленным точкам + простому обходу препятствий через физику, как патруль в
testgame), мультиплеер/сеть (движок пока однопользовательский — заявлено в
roadmap README), процедурная генерация уровней (комнаты собираются вручную —
это осознанный «souls-lite» дизайн, а не ограничение). Всё это — кандидаты в
движковый roadmap ПОСЛЕ того, как Emberfall докажет вертикали на текущем ядре.
